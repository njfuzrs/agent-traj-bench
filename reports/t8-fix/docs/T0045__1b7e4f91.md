## 2. P0 差距详解（已建未接线 + 高影响，成本低）

> P0 的共性：**能力已经写好了，只差接线或收尾**。ROI 最高。

### G1 — 主循环工具并发无 cap 【工具编排，低成本】

- **claude**：`toolOrchestration.ts:8-12` `getMaxToolUseConcurrency()` 默认 10（env 可调），`all(gens, 10)` 限流。
- **sid**：`query/tool-executor.ts:260 Promise.allSettled(concurrent.map(...))` 一次性全发，无 cap。sid 自己在 `agent/tool.ts:79` 注释里承认了这点，且**只给子代理层加了信号量**（`SID_SUBAGENT_MAX_CONCURRENT` 默认 3），主循环普通工具并发仍无限制。
- **后果**：模型一次派 10+ 个 grep/read 时全部同时打，claude 限 10 排队。资源峰值 + 潜在文件句柄耗尽。
- **补齐**：主循环工具执行加信号量，复用 `agent/tool.ts` 已有模式。**成本低。**

### G2 — auto 模式 ToolClassifier 从未接线（死档）【权限，低成本】

- **claude**：auto 模式（yoloClassifier）是完整生产路径，含 allowlist + gate 可用性检查 + 熔断。
- **sid**：`ToolClassifier`（tool-classifier.ts 全实现）+ `checker.ts:652-681` 的 auto 分支都写好了，但 **`setToolClassifier` 生产代码零调用**——`cli.ts:989` 只 `setBashClassifier`，从不 `setToolClassifier`（`checker.ts:228` 仅定义 setter）。作者自己在 `app.ts:2293-2295` 注释承认"classifier 恒 null → auto 分支整段短路、行为等价 default，是「死档」"，并在 Shift+Tab 循环里主动跳过 auto 档（`app.ts:2297`）。
- **后果**：auto 模式对用户不可达；泛化工具分类器（非 bash 工具的 LLM 安全判断）整个模块闲置。
- **补齐**：`cli.ts` 加一次 `new ToolClassifier` + `setToolClassifier`，复用 BashClassifier 的 provider 注入路径。**纯接线遗漏，成本低。**

### G3 — MCP Elicitation stub 未注册到 Client 【MCP，中成本】

- **claude**：`elicitationHandler.ts:68 registerElicitationHandler` 真正 `client.setRequestHandler(ElicitRequestSchema, ...)`，支持 form/url 双模式 + hook 前置应答 + abort + UI 渲染。
- **sid**：`mcp/elicitation.ts` 全文仅 49 行孤立 handler，form 模式直接 `return { action: 'cancel' }`（"表单交互暂不支持"）。**关键**：`grep setRequestHandler / ElicitRequestSchema` 全仓零命中；`mcp/client.ts:119` 建 Client 时 `capabilities: {}`——**从未声明 elicitation 能力，也从未把 handler 注册到 Client**。`cliElicitationHandler` 无任何调用点。
- **后果**：sid **完全无法接收 MCP server 的 elicitation 请求**（server 发 `elicitation/create` 时 Client 未声明能力）。需要交互式补充信息（表单/OAuth URL 确认）的 MCP server 在 sid 上不可用。第一轮记为"薄"，实读发现更准确是"stub 未接线"。
- **补齐**：① `client.ts` 声明 `capabilities.elicitation` ② 注册 `ElicitRequestSchema` handler ③ form 模式接 UI（复用已有 `DialogManager` + `ask-user-question` 结构化对话框）④ url 模式已有半成品。**成本中。**

### G4 — sed 权限门未接（detectSedWrite 零调用）【Bash 安全，低-中成本】

- **claude**：`sedValidation.ts:644 checkSedConstraints` 把 `sed -i` 当**文件写入**做权限门（非 acceptEdits 一律 ask），正向 allowlist 只放行 `p`/`s///`，denylist 拦 `w`(写任意文件)/`e`(执行 shell)/`y`。
- **sid**：`tool/bash/sed-validation.ts:23 detectSedWrite` 能解析出 `sed -i` 的目标文件和替换内容——但 **全仓只有定义、零调用点**。`read-only-validation.ts:50` 只把带 `-i` 的 sed 判为"非只读"走普通 bash 确认，**没有接进 PathValidator 做路径权限校验**，也没有 `s///e`/`s///w` denylist。
- **后果**：`sed -i 's/x/y/' ~/.ssh/config` 这类通过 sed 改工作区外/敏感文件的操作，走"普通 bash 破坏性确认"而非"文件写入权限门 + 敏感文件拦截"；`sed 's/x/y/e'`（执行 shell）无专门拦截。
- **补齐**：解析能力已有，接进 PathValidator + 加 w/e denylist。**成本低-中。**

### G5 — 工具 onProgress 死字段 【工具编排，低成本】

- **claude**：`toolExecution.ts:492-570` 把工具执行中的 progress 回调桥接成流，长时间工具能实时吐进度。
- **sid**：`tool/types.ts:184 onProgress?: (event: Progress) => void` **声明了但没接线**——`query/tool-executor.ts:410 tool.execute(effectiveInput, deps.getAbortSignal())` 只传了 input + signal，没传 onProgress。`grep onProgress` 执行路径零命中。
- **后果**：长跑工具（大 bash、大 web_fetch）执行期间 UI 无中间进度，只有最终结果。
- **补齐**：执行器把 onProgress 接线到 UI 事件。**接口已留位，成本低。**

## 3. P1 差距详解（真能力缺口 + 中等价值）

### G6 — Read 富媒体支持（图片/PDF/Notebook）【工具，中成本】

- **claude** `FileReadTool.ts`：原生支持图片（base64 + imageResizer，`:249-295`）、PDF（分页 `pages` 参数 + extractPDFPages，`:431-436`）、Notebook（返回 cells 结构，`:300-305`）、二进制检测。
- **sid** `read.ts`：`.png/.jpg/.pdf/.ipynb` 全在 `BINARY_EXTENSIONS`（`:58-69`），命中 `hasBinaryExtension`（`:212`）**直接拒绝**返回错误。
- **后果**：模型无法读截图、PDF、notebook——多模态/数据科学场景硬缺。
- **补齐**：接 vision 内容块 + PDF 库 + image resize。**成本中。**

### G7 — `toAutoClassifierInput` 钩子缺失 【工具/权限，低成本】

- **claude**：`Tool.ts:556`，10+ 工具用——每个工具自报"给风险分类器看的精简语义"（如 Edit 报 `/tmp/x: new content`，无安全关联的工具返回 `''` 跳过）。
- **sid**：`permission/tool-classifier.ts:140-143` 对所有工具统一喂**原始完整 input** + toolName + cwd，无此钩子。
- **后果**：分类器上下文更臃肿、无法让工具主动降噪/跳过。与 G2 相关——auto 分类器接线后，这个钩子能显著提升分类质量。
- **补齐**：加一个可选钩子 + 分类器优先读它。**成本低。**

### G8 — OpenAI 路径 rate-limit header 未提取 【API，低成本】

- **sid**：`api/rate-limit.ts` 实现完整（`extractRateLimitFromHeaders` 解析 `anthropic-ratelimit-*` + retry-after + 利用率/warning），`app.ts:3144` 也接了 UI 显示。**但 `updateRateLimitStatus` 只在 `llm/anthropic.ts:224` 调用**——`llm/openai.ts` 全程不提取 rate-limit header，`openai.ts:717` 只取 content-type。
- **后果**：跑 OpenAI-wire provider（sid 主力场景之一）时，rate-limit 状态**永远显示 ok**，用户在 OpenAI/网关限流时处于盲区。注：`fallback.ts` 的 retry-after 靠 error header 解析仍工作，所以**重试不受影响，受影响的是限流状态可见性/预警**。
- **补齐**：`openai.ts` 拿到 `response.headers` 后调 `updateRateLimitStatus`，并补 OpenAI 系 header 名（`x-ratelimit-remaining-tokens/-requests/-reset`，当前 `extractRateLimitFromHeaders` 只认 `anthropic-ratelimit-*`）。**成本低。**

### G9 — 补 4-5 个注入校验器 【Bash 安全，低-中成本】

sid `bash-security.ts` 的 15 个校验器（`checkInjectionPatterns:776` 实调：controlCharacters/unicodeWhitespace/carriageReturn/IFS/procEnviron/heredocInSubstitution/processSubstitution/zshDangerous/obfuscatedFlags/braceExpansion/newlines/midWordHash/commentQuoteDesync/quotedNewline/backslashEscapedOperators）已覆盖攻击面最大的一批。逐项对照 claude 26 校验器，**真缺口**：

| claude 校验 | claude file:line | 判定 |
|---|---|---|
| `validateMalformedTokenInjection`（HackerOne eval-reparse `echo {"hi":"hi;evil"}`）| bashSecurity.ts:1082 | 🔴 高（有实战/CVE 绕过记录）|
| `validateJqCommand`（jq `system()`/`-f`/`--rawfile` 任意执行+读文件）| bashSecurity.ts:742 | 🔴 中 |
| `validateShellMetacharacters`（引号内 `;`/`&`/`\|` + find `-name` 内元字符）| bashSecurity.ts:783 | 🔴 中 |
| `validateBackslashEscapedWhitespace`（转义空格→双 token 差异）| bashSecurity.ts:1583 | 🔴 中 |
| `validateDangerousVariables` / `validateIncompleteCommands` | bashSecurity.ts:823/244 | 🔴 低 |

- **补齐**：每个校验器是纯函数，照 claude 模式移植，**无需 tree-sitter**。成本低-中。
- **注**：`validateSafeCommandSubstitution`/`isSafeHeredoc`（正向放行安全 heredoc）sid 选择保守全拦（误报多但更安全）=有意取舍，不补。

### G10 — autoDream 自主记忆巩固 【Memory，中成本】

- **claude**：`services/autoDream/autoDream.ts` 三级 gate（时间≥minHours → 累积会话≥minSessions → 跨进程锁）后**自主 fork 一个后台子代理**跑 `/dream`，做记忆巩固/剪枝（orient/gather/consolidate/prune 四阶段），`DreamTask` 在 footer 可视化。这是 claude 真正的"主动性"实体。
- **sid**：`grep consolidat|autoDream|dream` 在 memory/agent 目录零命中。sid 有被动 `extractMemories`（turn-end 触发 `loop.ts:1861`）+ `updateSessionMemory`，但**没有跨会话的自主巩固/剪枝**——记忆只增不理，长期膨胀/陈旧。
- **补齐**：sid 已有 forked-agent 基础设施（`agent/forked-agent.ts`）+ freshness（`memory/freshness.ts`），缺"时间/会话 gate + 巩固 prompt + 后台触发"。**成本中。**
- **注**：claude 此快照的 `proactive/` 全是 no-op 桩，autoDream 才是"主动性"唯一真实落点。

### G12 — outputStyles 用户可插拔输出风格 【系统提示，低成本】
