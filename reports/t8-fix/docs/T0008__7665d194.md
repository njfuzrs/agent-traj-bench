## 1. P0 —— matcher 过度匹配（静默行为错误，必须优先修）

### G8　matcher 无条件 regex-first 且不锚定

**问题**

我们的 `matchesToolName`（`planner.ts:68-82`）对任意 matcher 都走 `new RegExp(pattern).test(toolName)`，**且不加锚点**：

```typescript
// planner.ts:68
private matchesToolName(matcher: string, toolName: string): boolean {
  let pattern = matcher;
  if (pattern.startsWith("/") && pattern.endsWith("/") && pattern.length > 2) {
    pattern = pattern.slice(1, -1);
  }
  try {
    const regex = new RegExp(pattern);        // ← 无条件正则 + 未锚定
    return regex.test(toolName);
  } catch {
    return matcher === toolName;              // 仅非法正则才回退精确
  }
}
```

**实测复现**（`bun -e` 已确认）：

```
new RegExp("Edit").test("NotebookEdit")  // = true  ← 误命中
new RegExp("Edit").test("MultiEdit")     // = true  ← 误命中
```

用户写 `matcher: "Edit"` 意图只 hook `Edit` 工具，结果 `NotebookEdit`、`MultiEdit` 全被命中。格式化 / 拦截 / 审计 hook 会在意料之外的工具上触发——**静默的行为错误，无任何报错**。这与权限系统里 `Bash(*)` minimatch 不跨 `/` 是同一类隐患（见 [权限系统对标§7差距]）。

**CC 怎么做**（`utils/hooks.ts:1346-1381` `matchesPattern`）

CC 分三档，**精确匹配优先，正则是兜底**：
1. `''` 或 `'*'` → 匹配全部。
2. matcher 仅含 `[a-zA-Z0-9_|]`（纯字母数字下划线管道）→ **精确匹配**：含 `|` 按管道拆成精确列表（`Write|Edit` → `["Write","Edit"]` 逐个 `===`）；否则单值 `===`。
3. 含其他字符（`.` `*` `(` `[` 等）→ 才当正则 `new RegExp(matcher)`，**大小写敏感**（无 `i` flag），非法正则记日志返回 false。

即 `Edit` 精确只命中 `Edit`；`Notebook.*` 才走正则命中 `NotebookEdit`。

**修复方案**

改写 `planner.ts` 的 `matchesToolName`，对齐 CC 三档逻辑：

```typescript
private matchesToolName(matcher: string, toolName: string): boolean {
  // 兼容旧格式 /pattern/ 包裹 → 强制正则
  if (matcher.startsWith("/") && matcher.endsWith("/") && matcher.length > 2) {
    const pattern = matcher.slice(1, -1);
    try { return new RegExp(pattern).test(toolName); }
    catch { return false; }
  }

  // CC 对齐：纯 [a-zA-Z0-9_|] → 精确匹配（含 | 走管道分隔精确列表）
  if (/^[a-zA-Z0-9_|]+$/.test(matcher)) {
    if (matcher.includes("|")) {
      return matcher.split("|").some((name) => name === toolName);
    }
    return matcher === toolName;
  }

  // 含正则元字符 → 当正则（大小写敏感），非法正则返回 false
  try {
    return new RegExp(matcher).test(toolName);
  } catch (e) {
    getLogger().warn("HOOK", `非法 matcher 正则 "${matcher}": ${e}`);
    return false;
  }
}
```

**注意**：这是**破坏性语义变更**——现存配置里若有人依赖"`Edit` 命中 MultiEdit"的旧行为会受影响。但该旧行为本身是 bug，且 CC 语义才是用户预期。需在 CHANGELOG 显式说明；如担心存量配置，可加一次性启动告警：检测到"纯字母 matcher 且能正则匹配到多个已注册工具名"时提示用户确认意图。

**验收**
- 单测 `tests/hook/planner-matcher.test.ts`（新增）：`Edit` 不命中 `NotebookEdit`/`MultiEdit`；`Write|Edit` 命中两者但不命中 `Rewrite`；`Notebook.*` 命中 `NotebookEdit`；`*` 命中全部；非法正则 `[` 返回 false。
- `Bash` 精确匹配、`mcp__.*` 正则匹配 MCP 工具的既有用法回归通过。

## 2. P1 —— PreToolUse 决策链断裂（一组关联缺口）

> G1/G2/G3/G9 围绕同一条链路：**PreToolUse hook 的决策如何影响工具执行与权限**。CC 把它设计成一个完整的决策管道，我们目前是断裂的四段。建议一组修复、一组测试。

### G1　PreToolUse 改参字段名 `updatedInput` 不兼容 + 浅合并

**问题**

CC 规范（`utils/hooks.ts:618-620`）：PreToolUse 修改工具参数用 `hookSpecificOutput.updatedInput`，语义是**整体替换** input。

我们的实现两处都偏离：
1. `PreToolUseHookOutput.getModifiedToolInput()`（`types.ts:569-577`）只读 `hookSpecificOutput.tool_input`，**不认 `updatedInput`**。
2. `applyHookOutputToInput`（`runner.ts:518-528`，串行链式传递用）对 PreToolUse 是**浅合并**（`{...old, ...new}`）而非替换。

后果：任何按 CC 规范写、用 `updatedInput` 的 PreToolUse hook，在我们这里**静默失效**——参数不变，hook 作者拿不到任何报错。这是迁移 CC hook 的隐形陷阱。

**修复方案**

`types.ts` 的 `getModifiedToolInput()` 同时认两个字段名，`updatedInput` 优先（对齐 CC），`tool_input` 兜底（向后兼容我们的旧行为）：

```typescript
// types.ts PreToolUseHookOutput
getModifiedToolInput(): Record<string, unknown> | undefined {
  const so = this.hookSpecificOutput;
  if (!so) return undefined;
  // CC 对齐：updatedInput 优先，整体替换
  const candidate = ("updatedInput" in so ? so["updatedInput"] : undefined)
    ?? ("tool_input" in so ? so["tool_input"] : undefined);
  if (candidate && typeof candidate === "object" && !Array.isArray(candidate)) {
    return candidate as Record<string, unknown>;
  }
  return undefined;
}
```

`runner.ts` 的 `applyHookOutputToInput` 对 PreToolUse 改为**替换**（`updatedInput` 整体替换 `tool_input`），保留 `tool_input` 的浅合并仅作旧格式兼容：

```typescript
// runner.ts:518 case HookEventName.PreToolUse
case HookEventName.PreToolUse: {
  const so = hookOutput.hookSpecificOutput;
  if (!so) break;
  if ("updatedInput" in so && so["updatedInput"] && typeof so["updatedInput"] === "object") {
    // CC 语义：整体替换
    (modified as any).tool_input = so["updatedInput"];
  } else if ("tool_input" in so && so["tool_input"] && typeof so["tool_input"] === "object") {
    // 旧格式兼容：浅合并
    (modified as any).tool_input = { ...(modified as any).tool_input, ...(so["tool_input"] as object) };
  }
  break;
}
```

同时补齐环境变量：`runner.ts:454` 注入 `SID_CODE_TOOL_INPUT` 时，command hook 也应能通过 stdout JSON 回传 `updatedInput`（已走 parseJsonOutput，无需额外改）。

**验收**
- 单测：hook 返回 `{hookSpecificOutput:{updatedInput:{command:"safe"}}}` → 工具收到 `{command:"safe"}`（整体替换，原有其他字段被清）。
- 旧格式 `{hookSpecificOutput:{tool_input:{a:1}}}` → 浅合并保留其他字段（回归）。
- `query/tool-executor.ts:762` 的 `hookActuallyModifiedInput` 差异检测在替换语义下仍正确触发 `hookModifiedNotice`。

### G2　PreToolUse `allow` / `ask` 决策未实现

**问题**

CC PreToolUse 的核心是 `permissionDecision` 三值（`utils/hooks.ts:596-613`，消费在 `toolHooks.ts:332-433` `resolveHookPermissionDecision`）：
- `allow` → 跳过交互提示，**但不无条件**：仍跑规则检查，有 `deny` 规则则覆盖、有 `ask` 规则仍弹框、工具 `requiresUserInteraction()` 仍走 `canUseTool`；只有无匹配规则才真正 bypass。
- `deny` → 阻止，stderr/reason 给模型。
- `ask` → 升级为用户确认，弹框展示 hook 的 message。

我们的 `DefaultHookOutput.isBlockingDecision()`（`types.ts:517-519`）**只认 `block`/`deny`**。`allow` 和 `ask` 完全无处理路径：返回 `allow` 不跳弹窗（且因 G3 顺序问题根本来不及），返回 `ask` 被当"无决策"放行。

**修复方案**（与 G3 联动，见下）

1. `types.ts` 扩展 `HookDecision` 与 `PreToolUseHookOutput`：

```typescript
// types.ts
export type HookPermissionDecision = "allow" | "deny" | "ask";

// PreToolUseHookOutput 新增
getPermissionDecision(): HookPermissionDecision | undefined {
  const so = this.hookSpecificOutput;
  const d = so?.["permissionDecision"];
  if (d === "allow" || d === "deny" || d === "ask") return d;
  return undefined;
}
getPermissionDecisionReason(): string | undefined {
  const r = this.hookSpecificOutput?.["permissionDecisionReason"];
  return typeof r === "string" ? r : undefined;
}
```

2. `isBlockingDecision()` 保持只认 block/deny（顶层老式决策），新增 `permissionDecision:"deny"` 也算阻塞（在 PreToolUseHookOutput override）。

3. 决策消费改到权限层（见 G3）：`allow`→ 传 `forceAllow` 给 checker（无匹配 deny/ask 规则则跳弹窗）；`ask`→ 传 `forceAsk` 强制确认；`deny`→ 直接拒绝。

**验收**
- 单测：`permissionDecision:"allow"` 且无规则 → 工具直接执行不弹窗；有 deny 规则 → 仍拒绝；`permissionDecision:"ask"` → 触发 `requestUserConfirmation`；`permissionDecision:"deny"` → 返回 error tool_result。

### G3　主循环 PreToolUse↔权限顺序倒置，且与子代理不一致

**问题**

- **主循环**（`query/tool-executor.ts`）：`resolveToolPermission`（权限检查 + PermissionRequest hook）在 `346` 行**先跑**，`executeSingleTool` 内的 `firePreToolUseEvent` 在 `737` 行**后跑**。
- **子代理**（`agent/sub-agent.ts:823-855`）：PreToolUse 在 `827` 行**先跑**，权限检查在 `849` 行后跑。

CC 规范顺序是 **PreToolUse → 权限**（`toolHooks.ts` 先跑 PreToolUse 拿到 `permissionDecision`，再 `resolveHookPermissionDecision` 把它喂给权限层）。我们主循环把顺序倒了，导致 G2 根本无法实现（等 PreToolUse 跑到时权限早决策完）；且两条路径顺序不一致，行为割裂——同一个 hook 在主循环和子代理里表现不同。

**修复方案**

统一为 **PreToolUse 先行**，其 `permissionDecision` 注入权限决策。主循环重构 `query/tool-executor.ts`：

1. 把 `firePreToolUseEvent` 从 `executeSingleTool`（737 行）**上移**到 `resolveToolPermission`（587 行）之前，或在 `resolveToolPermission` 内部最前段调用。
2. PreToolUse 结果分三路：
   - `permissionDecision:"deny"` 或顶层 block/deny → 直接返回 error，不再走权限检查。
   - `permissionDecision:"allow"` → 记 `hookAllow=true`，传入 `permissionChecker.check`；checker 在无匹配 deny/ask 规则时据此跳过 needsConfirmation。
   - `permissionDecision:"ask"` → 记 `hookAsk=true`，强制走 `requestUserConfirmation`。
3. `updatedInput` 在 PreToolUse 阶段就应用到 `effectiveInput`，后续权限检查用改后的 input（对齐 CC：改参后按新参数鉴权）。
4. 子代理路径（`sub-agent.ts`）已是 PreToolUse 先行，只需把 `permissionDecision` 同样接入其 `permissionChecker.check`，保证两条路径语义一致。

**权限层接口扩展**（`permission/checker.ts`）：

```typescript
// PermissionRequest 或 check 的 options 增加
interface CheckOptions {
  hookDecision?: "allow" | "ask" | undefined;  // PreToolUse 注入
}
// check 内部：
//   hookDecision==="allow" 且规则检查无 deny/ask 命中 → allowed:true
//   hookDecision==="ask" → needsConfirmation:true
//   deny 规则始终覆盖 hookDecision（安全护栏，对齐 CC toolHooks.ts:386）
```

**安全护栏（务必保留）**：`allow` 决不能越过**硬编码危险命令**和 **deny 规则**。CC 明确 hook allow 不覆盖 deny（`toolHooks.ts:386-391`）。我们现有的危险命令熔断、denial 拦截必须在 hookAllow 之上仍然生效。

**验收**
- 单测：主循环与子代理路径对同一 PreToolUse hook 行为一致（deny/allow/ask 各一例）。
- hook `allow` + 存在 deny 规则 → 仍拒绝（安全护栏）。
- hook `allow` + 危险命令 → 仍弹窗/拒绝（熔断不被绕过）。
- `updatedInput` 改参后，权限按新参数鉴权（如把 `rm -rf /` 改成 `ls` 后放行）。

### G9　顶层 `decision:"approve"` 不认

**问题**

CC 支持顶层老式决策字段 `decision:"approve"|"block"`（`utils/hooks.ts:525-543`）：`approve`→allow，`block`→deny+blockingError。我们的 `isBlockingDecision()`（`types.ts:517`）只认 `block`/`deny`，`approve` 落空当"无决策"。虽然 `approve` 是老式写法（新写法用 `permissionDecision`），但为兼容 CC 存量 hook 应支持。

**修复方案**

`DefaultHookOutput` 增加 `isApproveDecision()`，聚合器 `mergeWithOrDecision`（`aggregator.ts:87`）识别 `approve` 等价于 `permissionDecision:"allow"`：

```typescript
// types.ts
isApproveDecision(): boolean {
  return this.decision === "allow" || (this.decision as string) === "approve";
}
```

在 G3 的决策注入里，`approve`/`allow` 走同一 allow 路径。

**验收**：单测 `{decision:"approve"}` → 等价 allow；`{decision:"block"}` → 等价 deny（回归）。

## 3. P2 —— 语义偏差与配置/事件补齐

### G4　退出码 `2+` 全 deny（CC 仅 2 阻塞，且逐事件不同）

**问题**

CC 退出码语义（`utils/hooks.ts:2617-2697` + 逐事件表 `hooksConfigManager.ts:26-263`）：
- `exit 0` → 成功。
- `exit 2` → **阻塞反馈**，把 **stderr** 喂给模型（注意是 stderr 不是 stdout）。
- **其他非零（1/3/4…）→ 非阻塞错误**，仅展示给用户，工具继续。
- 且 `exit 2` 的效果**逐事件不同**：PreToolUse=阻塞工具、PostToolUse=stderr 给模型、UserPromptSubmit=阻塞并**擦除原 prompt**、Stop=stderr 给模型并**继续对话**、PreCompact=阻塞压缩、SessionStart/SubagentStart/Setup=**忽略阻塞**（exit2 无效果）。

我们的实现（`runner.ts:402-409`）：
```typescript
if (exitCode === EXIT_SUCCESS) return { decision: "allow", ... };      // 0
else if (exitCode === EXIT_WARNING) return { decision: "allow", ... }; // 1 → 告警放行
else return { decision: "deny", ... };                                 // 2+ → 全 deny
```

偏差：
1. `exit 3/4/5…` CC 是"继续+告警"，我们是"拒绝"——**过度拦截**。
2. `exit 2` 我们用 stdout（`textToParse`）作 reason，CC 用 **stderr**。
3. 我们没有逐事件差异（UserPromptSubmit 擦 prompt、SessionStart 忽略阻塞等一律没做）。

**修复方案**

1. `parseCommandOutput`（`runner.ts:393`）退出码映射改为：`0`→allow；`2`→block（reason 用 **stderr** 优先）；**其余非零**→ 非阻塞（`decision:"allow"` + `systemMessage` 告警，不 deny）。
2. 逐事件差异化在 aggregator / 各触发点消费层处理：
   - UserPromptSubmit exit2：`engine.ts:196` 分支里，block 时**清空 finalInput**（擦除原 prompt）并把 stderr 作为提示。
   - SessionStart/SubagentStart/Setup exit2：这些事件的聚合忽略 block（`aggregator.ts` 加事件白名单，block 降级为 systemMessage）。
   - Stop exit2：已在 `stop-hooks.ts` 走"注入错误→continue"，对齐 CC"继续对话"，保留。
3. 更新 `runner.ts:44-46` 常量注释，去掉"2+ = 阻塞"的错误描述。

**验收**：单测覆盖 exit 0/1/2/3；exit 2 用 stderr 作 reason；exit 3 不 deny；UserPromptSubmit exit2 擦除 prompt；SessionStart exit2 不阻塞。

### G5　settings.json 只能配 command/url（prompt/agent 无入口）

**问题**

`config/config.ts:68` 的 `HookConfig.type` 联合只有 `"command" | "url"`。`registry.ts` 的 `convertLegacyHook`、`system.ts:164` 的 `convertPluginHook` 也只转 command/url。而 `runner.ts:553/617` 明明实现了 prompt/agent 执行器——**实现了却无配置入口**，用户只能内部代码 `registerHook` 编程式注册。CC（`schemas/hooks.ts`）prompt/agent 是可配置类型。

**修复方案**

1. `config/config.ts:67-77` 扩展 `HookConfig`：
```typescript
export interface HookConfig {
  type?: "command" | "url" | "prompt" | "agent";  // 扩展
  command?: string;   // command
  url?: string;       // url
  prompt?: string;    // prompt / agent
  model?: string;     // prompt / agent：指定模型
  tools?: string[];   // agent：可用工具
  // ... 其余不变
}
```
2. `registry.ts` `convertLegacyHook`、`system.ts` `convertPluginHook` 增加 prompt/agent 分支，校验必填字段（prompt 非空）。
3. `settings/types.ts` 的 zod schema 同步扩展 type 枚举与字段。

**验收**：settings.json 配 `{type:"prompt", prompt:"..."}` → 能被 registry 加载并在 `/hooks list` 显示；prompt hook 触发生效。

### G10　无 `if` 条件过滤

**问题**

CC 在 matcher 之上还有更细的 `if` 条件（`schemas/hooks.ts:19-26` + `utils/hooks.ts:1390-1421`）：用权限规则语法 `Bash(git *)` / `Read(*.ts)` 对 `tool_input` 做模式匹配，仅命中才 spawn hook。仅 PreToolUse/PostToolUse/PostToolUseFailure/PermissionRequest 支持。我们只有工具名 matcher，无 tool_input 级过滤。

**修复方案**

1. `types.ts` `HookDefinition` 增加 `if?: string`（权限规则语法）。
2. `planner.ts` `matchesContext` 在 matcher 通过后，若有 `if` 且事件支持，复用 `permission/rules.ts` 的 `matchRule` 对 `tool_input` 匹配，不命中则过滤掉该 hook。
3. `planner.ts` 需能拿到 `tool_input`——`HookEventContext` 增加 `toolInput?: Record<string,unknown>`，`event-handler.ts` 各 fire 方法透传。

**验收**：单测 `matcher:"Bash", if:"Bash(git *)"` → `git status` 命中、`ls` 不命中。

### G6　`agent` hook 名不副实

**问题**

CC 的 agent hook（`execAgentHook`）是启动**真正的子代理**、可访问 Read/Grep/Glob 做多轮验证（研究文档 §8.11 强调这是独特能力）。我们的 `executeAgentHook`（`runner.ts:617-672`）只是**单次 provider.stream 调用**，无工具、无多轮，和 prompt hook 几乎一样（只是 system prompt 和 maxTokens 不同）。

**修复方案**

`executeAgentHook` 改为调用我们已有的 `SubAgent`（`agent/sub-agent.ts`），传入 `hookConfig.tools`（默认 Read/Grep/Glob 只读集）、`hookConfig.model`（默认 Haiku 类小模型），跑多轮直到子代理产出结构化 `{ok, reason}`：

```typescript
private async executeAgentHook(...) {
  const { SubAgent } = await import("../agent/sub-agent.ts");
  const agent = new SubAgent({
    model: hookConfig.model ?? /* 默认小模型 */,
    tools: hookConfig.tools ?? ["read", "grep", "glob"],  // 只读默认集
    systemPrompt: "你是 Agent Hook 验证器...返回 {ok, reason} JSON",
  });
  const result = await agent.run(processedPrompt, { signal, timeout });
  // 解析结构化输出 → decision
}
```

需注意：hook 内跑子代理有成本与递归风险，务必：超时兜底、禁止 agent hook 内再触发 agent hook（防套娃，复用 `_agentId` 标记）、只读工具集默认。

**验收**：agent hook 能实际读文件验证（如"检查所有改动文件是否有对应测试"），返回结构化决策。

### G11　缺 InstructionsLoaded / TeammateIdle / Elicitation 事件

**问题**

CC 27 事件里我们缺 4 个（`coreTypes.ts:25-53`）：

- `TeammateIdle`：团队代理空闲时（可阻止）。
- `Elicitation` / `ElicitationResult`：hook 反向向用户提问的协议（`types/hooks.ts:674-706`，`action:accept/decline/cancel`）。

**修复方案**

   - `TeammateIdle`：Agent 团队空闲检测处（若已有团队/FleetView 机制）fire，支持 block。

**验收**：InstructionsLoaded/TeammateIdle 能触发并出现在 `/hooks list`；Elicitation 至少枚举存在不报错。

## 4. P3 —— 死代码：接线或删除（技术债）

> 原则：要么接通生产路径实现完整功能，要么删除避免误导。逐个决策。

### G7　async / asyncRewake 纯骨架 → 接线实现

**现状**：`types.ts:105-106` 有 `async`/`asyncRewake` 字段；`async-registry.ts` 有完整 `AsyncHookRegistry`（register/markCompleted/drainRewakeNotifications）。但 `runner.ts` **从不读 `config.async`**，全部同步 await；`AsyncHookRegistry.markCompleted`/`drainRewakeNotifications` 生产代码**零调用**。

**CC**（`utils/hooks.ts` `executeInBackground`）：`async:true` 的 hook 后台跑不阻塞主流程；跑完若 exit 2 且 `asyncRewake`，把 stderr 作为通知**唤醒模型**（注入下一轮上下文）。

**修复方案**（接线，非删除——这是 CC §8.9 实特性）：
1. `runner.ts` `executeCommandHook` 检测 `hookConfig.async===true`：不 await `proc.exited`，立即返回 `{success:true, async:true}`，同时向 `AsyncHookRegistry.register()` 登记，后台 `.then` 里 `markCompleted(id, exitCode, stderr)`。
2. `event-handler.ts` / `system.ts` 持有 `AsyncHookRegistry` 单例。
3. 主循环每轮开始（`query/loop.ts` 或 `engine.ts`）`drainRewakeNotifications()`，有则把 rewake stderr 作为 `<system-reminder>` 注入下一轮（复用 stop-hooks 的注入通道）。
4. `AsyncHookRegistry.cleanup()` 在会话结束或每轮收尾调用，防泄漏。

**验收**：`async:true` hook 不阻塞工具返回；exit2+asyncRewake 的 stderr 在下一轮出现在模型上下文；`AsyncHookRegistry.size` 会话结束归零。

### G12　HookConfigSnapshot 零引用 → 接线或删除

**现状**：`config-snapshot.ts` 整类（capture/update/getHooksForEvent）生产零引用。`executeHooks`（`event-handler.ts:424`）每次直接读 live registry。

**决策**：
- 若要"会话内配置快照防漂移"（配置热更时正在跑的 hook 链不受影响）——接线：`system.ts` 持有 snapshot，会话启动 `capture`，`/hooks` 改配置后 `update`，`planner` 从 snapshot 而非 live registry 取。
- 若认为 live registry 已够（配置变更本就该即时生效）——**删除** `config-snapshot.ts` 及其 export（`index.ts:11`）。

**建议**：倾向删除。我们的 registry 支持运行时 enable/disable，"即时生效"是更符合直觉的行为；snapshot 反而制造"改了配置但不生效"的困惑。除非有明确的并发一致性需求。

### G13　EnterprisePolicyGate（managed-hooks-only）零接线 → 接线

**现状**：`enterprise-policy.ts` 有 `EnterprisePolicyGate`（`allowManagedHooksOnly`/`disableAllHooks`），但生产零接线（`index.ts` export 了但无消费者）。对应 [权限系统对标§7差距] 里记的"企业 policy 层是脚手架未接线"。

**CC**（`hooksSettings.ts:96-101`）：`allowManagedHooksOnly` 开启时**屏蔽 user/project/local 全部 hook**，只跑 managed（企业策略下发的）hook。这是企业安全场景的硬需求。

**修复方案**：
1. `registry.ts` `getHooksForEvent` 在返回前经 `EnterprisePolicyGate` 过滤：`allowManagedHooksOnly` 时只保留 `source===Plugin`（或新增 `ConfigSource.Managed`）的 hook；`disableAllHooks` 时返回空。
2. policy 来源：从 `managed-settings.json`（企业策略路径，若已有）或 `config.enterprisePolicy` 读取。
3. `system.ts` 初始化时构造 `EnterprisePolicyGate` 并注入 registry。

**验收**：`allowManagedHooksOnly:true` 时 user/project hook 不执行、managed hook 执行；`disableAllHooks:true` 时所有 hook 静默不跑。

### G14　permission-race.ts 自标 @deprecated → 清理

**现状**：`permission-race.ts` 文件头明确 `@deprecated`，说已被 `permission/async-decision.ts` 取代、未接入生产。`index.ts:16` 仍 export `handleInteractivePermission`。

**决策**：确认无生产引用后删除文件 + 移除 `index.ts:16` export。若有测试引用先迁移到 async-decision.ts。保留仅供参考的价值不大（async-decision.ts 已是三路竞争的正式实现）。

**验收**：删除后 `bun test` + `make rebuild` 通过，无残留引用。

## 7. 落地顺序建议

1. **第一批（P0，独立低风险）**：G8 matcher 精确匹配。单独一个 commit + 回归测试，先验证不破坏既有 matcher 用法。CHANGELOG 显式声明破坏性语义变更。
