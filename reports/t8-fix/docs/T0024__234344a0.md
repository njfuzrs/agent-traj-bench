## 摘要：一类根因贯穿全部缺陷

**11 条缺陷里有 7 条是同一个病：代码完整、测试通过、调用点为零。**

这与项目已知的两笔债完全同构——「四环防线建好零触发」、「团队记忆能写不能读」。所以本清单的第一个结论不是某个具体 bug，而是：

> **`src/analytics/` 的 1113 行是目前仓库里最大的一块「已建成未接线」资产。**

> **📌 修复后追记（2026-08-07）：本文自身有两条是伪缺陷，值得写在最前面。**
>
> P0-4 与 P2-10 的前提都**不成立**——都源自**分母里混进了空壳会话**：
> 按会话目录数算 traj 覆盖率得 33%（像个 P0），按「有真实 LLM 调用的会话」算是 **100%**。
> 本文 §P2-10 原本已经记过一次同类陷阱（"jq 字段路径写错 → 23/23 全为 0 的假结论"），
> 结果同一份文档又栽了一次，只是从"字段路径"换成了"分母定义"。
>
> 所以这份清单的第二个结论是：
>
> > **「代码建好未接线」会让人**低估**能力；「统计口径没定义」会让人**虚构**缺陷。
> > 后者更危险——它把工程精力导向一个不存在的问题，而且看起来数据充分、证据齐全。**
>
> 纪律沉淀：任何覆盖率/命中率结论，**必须在结论里写明分母定义**。
> 另有一条真 P0（P0-12：落盘脱敏破坏 JSON 数字）是查证 P0-4 时撞见的，
> 不在任何人的计划里——这是「先查后修」这条纪律本身的产出。

> **📌 全部闭环后追记（2026-08-08，批次 D/E）：第三个结论——「测试全绿」本身是一种盲区。**
>
> 批次 D/E 撞见的坑与前两个结论都不同，值得单独立一条：
>
> P2-11 的回放 Provider 在 registry 里接好了、**31 个单测全绿**，但跑一次真实 CLI
> 直接报 `配置验证失败：无效值 "replay"`——因为那些单测都是自己 `new ProviderRegistry`，

> 是同一个病，而它躲过了 31 个测试。
>
> > **「代码建好未接线」会让人低估能力；「统计口径没定义」会让人虚构缺陷；
> > 而「测试绕过了真实入口」会让人误以为已经接线了——三者的共同点是
> > *证据看起来很充分*。**

> 纪律沉淀：**新增一个可配置的东西（provider / exporter / backend / flag），
> 验收必须包含一次「从用户真实入口走」的实测**，而不只是单测里 new 出那个类。

> 参考页的静态扫描器**扫不到**（81→83 只认出两个字面量读取点）。

## P0-1 · Analytics 管道全仓仅 1 个埋点

**证据**

```bash
$ cd /Users/zhourusheng/Code/person/sid-code
$ rg -a -n "logEvent\(" --type ts src/ | grep -v "analytics/index.ts"
src/analytics/sink.ts:95:    logEvent(eventName: string, metadata: EventMetadata): void {   # 定义
src/app.ts:2738:      logEvent("startup_timing", { duration_ms: Date.now() - initStartMs });
```

**生产埋点数 = 1**（`startup_timing`）。承接它的管道是 `src/analytics/` 共 **1113 行**：零依赖事件 API、五阶段过滤 Sink、三个 exporter、磁盘缓存、退避重试、隐私双通道、采样、killswitch、元数据富化、用户分桶——全部为这一个事件服务。

对照 claude-code：`logEvent` 调用点 **1093 处**，`tengu_*` 事件名去重 **1119 个**。

**为什么是 P0 而不是「慢慢补」**

不是「埋点密度不够」，是**整类视角缺失**。sid 现有的 11461 条 `events.jsonl` 事件（23 类）全部服务于「本机单会话故障诊断」，无法回答任何跨会话产品问题：

- 哪个工具失败率最高？
- `/compact` 每天触发几次、触发后用户是否立刻重开会话？
- 权限确认弹了多少次、被拒多少次？
- 哪个 skill 从来没人用？

**这些恰好是「举一反三优化 sid-code」所需要的输入。** 缺了它，优化方向只能靠个案直觉，而不是数据飞轮。

**修复要求**

不要抄 1119 个事件名。先覆盖 5 条核心漏斗，每条都要能回答一个已经想问但目前答不出的问题：

| 漏斗 | 事件 | 回答的问题 |
|---|---|---|
| 工具 | 调用 / 成功 / 失败 + 失败分型 | 哪个工具最不可靠 |
| 权限 | 弹确认 / 允许 / 拒绝 | HITL 打扰了多少次（直接服务「更安全 ↔ 更快」的 trade-off 判断） |
| 上下文 | compact 触发 / JIT 命中 / cache 命中 | 「更省」的效果 |
| 命令 | 斜杠命令使用分布 | 哪些功能是死功能 |
| 错误 | 按 §「归因反模式」的判据分型 | 哪类错误最高频 |

**验收判据**（可机械检查，避免又变成"看起来做了"）

1. `rg -a -c "logEvent\(" --type ts src/` 调用点数 ≥ 30
2. 跑一个真实会话后，`~/.sid-code/telemetry/events.jsonl` 至少出现 5 个不同 `eventName`
3. 新增一条哨兵测试：断言核心漏斗事件名存在且被调用（防止再次退化成死代码）

> 第 3 条是关键。这块债的成因就是「有代码无调用且无人发现」，修复必须同时装上防复发门禁，否则半年后重演。

## P0-2 · Telemetry 的 span/metric 无法经 OTLP 出去 —— ✅ 已闭环（2026-08-07，批次 B）

> **修复**：新增 `src/telemetry/exporters/otlp.ts`（零依赖 OTLP/HTTP + JSON，不引入
> `@opentelemetry/*` 任何包），拆掉三处白名单（`telemetry/types.ts`、`config/config.ts`、
> `config/schema.ts`）并在 `telemetry/index.ts` 的 `createExporter()` 接上 `case "otlp"`。
> 测试：`tests/telemetry/otlp-exporter.test.ts`（26 例）+ `tests/telemetry/otlp-wiring.test.ts`（12 例）。
>
> **验收已按本条要求执行**（不是"看起来做了"）：起本地 collector 收到完整 span 树——
> `invoke_agent`（root）→ `chat`(CLIENT) / `execute_tool` Read / `execute_tool` Bash(ERROR)，
> 同一 traceId、parent 链正确，外加 `gen_ai.client.token.usage` 与 `sidcode.cost.usd` 两个 metric。
>
> **三个编码细节是 OTLP/JSON 的坑，已逐项对官方 `.proto` 机械核验**（不是凭记忆）：
> 1. `traceId`/`spanId` 用**十六进制**字符串，不是标准 protobuf JSON mapping 的 base64
>    ——OTLP 规范对这两个字段专门开了例外。写成 base64 就是 collector 静默拒收。
> 2. 键名一律 lowerCamelCase（`startTimeUnixNano`），枚举用数值
>    （`SPAN_KIND_CLIENT=3` / `STATUS_CODE_ERROR=2` / `AGGREGATION_TEMPORALITY_DELTA=1`）。
> 3. 纳秒时间戳**必须走 BigInt**：`ms * 1e6` 量级 1.7e18 远超 `MAX_SAFE_INTEGER`（9.0e15），
>    普通乘法末几位静默丢精度。这个坑不会报错，只会让时间轴悄悄偏移。
>
> **端点解析遵循 OTel 规范的非对称规则**（企业运维按这套配，配错就发到 404）：
> per-signal 变量（`OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`）**原样使用不追加路径**，
> 而基础变量（`OTEL_EXPORTER_OTLP_ENDPOINT`）才追加 `/v1/traces`、`/v1/metrics`。
> 另支持 `OTEL_EXPORTER_OTLP_HEADERS`、`OTEL_EXPORTER_OTLP_TIMEOUT`、
> `OTEL_SERVICE_NAME`、`OTEL_RESOURCE_ATTRIBUTES`。
>
> **一处刻意的诚实降级**：`MetricPoint` 只带单值、无分桶，所以 `type: "histogram"`
> 按 gauge 上报而非硬造 bucket 边界——造出来的分布是错的，错数据比没数据更坏。
>
> 原始缺陷记录保留在下方。

**证据**——exporter 白名单在两处硬编码，只允许 `console` / `jsonl`：

```
src/telemetry/types.ts:84          type: "console" | "jsonl";
src/config/schema.ts:757           const VALID_EXPORTER_TYPES = new Set(["console", "jsonl"]);
src/telemetry/index.ts:59-67       createExporter() switch 只有两个 case，default → null
```

metric 链路本身是通的（`token-meter.ts:79` 等 5 处 → `bus.recordMetric()` → `bus.ts:244` 批量导出），但终点只能是本地 console/jsonl 文件。

**影响**

体系分析文档反复强调「Span/Metric 严格遵循 OTel GenAI 语义约定」——这句话对，但**只对了一半**：数据模型对齐了，出口没打通。企业客户要的是 span 进他们自己的 Jaeger / Datadog / Grafana，不是本地 jsonl。

这是「深度融合企业级」这个北极星方向上**最短、最直接的一级台阶**：数据模型已经对齐了，缺的只是一个 exporter 实现 + 拆掉白名单。

对照 claude-code：真实依赖 `@opentelemetry/*` **17 个包**，三信号（traces / metrics / logs）× 4 协议（grpc / http / proto / prometheus），全部由标准 `OTEL_*` 环境变量驱动。

**修复要求**

- 拆掉两处白名单，新增 `otlp` 类型
- 支持标准 `OTEL_EXPORTER_OTLP_ENDPOINT` / `OTEL_EXPORTER_OTLP_HEADERS`（企业运维认这套，不认我们自造的键名）
- traces 与 metrics 端点可分设
- **验收**：本地起一个 OTLP collector，跑一次会话，能看到 `invoke_agent` → `chat` → `execute_tool` 的完整 span 树

> `system` / `tools` / `raw_messages` / `text` / `thinking_blocks`，所以采内容一行

>
> 1. **按 hash 去重**：system prompt 每会话每唯一值只发一次全文，span 上永远带
>    `hash + preview + bytes` 供关联。工具 schema 按**单个工具**去重而非列表整体
>    ——整体 hash 会因为「多了一个 MCP 工具」把几十个没变的 schema 全部重发。

>    已实测：30000 个汉字（90000 字节）截断后产物 61438 字节 ≤ 61440，且 emoji
>    （4 字节 + 代理对）截断后不留 U+FFFD 残字。
> 3. **独立开关默认关闭**，四道闸门缺一不可：`SID_CODE_CONTENT_TRACING=1` +
>    Feature Flag `content_tracing` + 隐私级别非 no-telemetry/essential-traffic + 全文过脱敏。
> 4. **compact 后清 hash 状态**：挂在 `runPostCompact`（`query/compact/post-compact.ts`）
>    而非 `auto-compact.ts` 的三个出口——前者是 auto 与手动 `/compact` **共同**的收尾
>    单一事实源（第 2 步重置 microcompact 映射同理）。挂三个出口会漏掉手动路径，
>    而「只有手动压缩之后 hash 不失效」这种缺陷极难被想到去查。

> **之前**。截断响应 / provider 异常返回往往就是没 usage，而那恰恰是最需要看内容的场景；
> 放在守卫后面等于「越是出问题的那一轮，越采不到内容」。
>
> **哨兵已实测有效**（不是写了就算）：手工删掉 `hook-probe.ts` 里一处调用，

> ——代码完整、测试通过、调用点为零——所以行为测试之外必须另有一层静态断言。

> 原始缺陷记录保留在下方。

## P0-12 · 落盘脱敏破坏 JSON 数字，轨迹静默损坏 —— ✅ 已闭环（2026-08-07，批次 C）

> **本条不在原清单里。** 它是执行 P0-4「先查后修」时撞见的，严重度高于 P0-4 本身：
> 它正在**持续损坏已落盘的数据**，并已让 `/trace` 与 `trace-digest` 完全不可用。

**证据**（最小复现）

```
in : {"total_cost_usd": 0.4428123456780257}
out: {"total_cost_usd": 0.4428********0257}     ← JSON.parse 失败
```

那些 `*` 是**真实字节 0x2a**（已 `xxd` 核实，不是终端打码）。根因是
`maskSensitiveData()`（`src/permission/sensitive.ts`）的**信用卡号**规则：

```
/\b(?:4[0-9]{3}|5[1-5][0-9]{2}|3[47][0-9]{2}|6(?:011|5[0-9]{2}))[- ]?[0-9]{4}[- ]?[0-9]{4}[- ]?[0-9]{4}\b/g
```

`0.4428123456780257` 的尾数 `4428123456780257` 恰好 16 位、前缀 `4` —— 命中。
`\b` 挡不住它：`.` 是**非**词字符，所以小数点后的数字串两侧都是合法词边界。

**实测影响**：33 份 `session.traj` 有 1 份彻底不可解析（`20260807-064304-8a21d2a3`）。
`events.jsonl` 8389 行 / `raw.jsonl` 997 行暂无坏行——纯属**运气**：那里的 cost 小数位恰好不够长。

**故障为什么完全静默**（三层各吞一次，这是最值得记的部分）

| 层 | 行为 | 后果 |
|---|---|---|
| 写入 | `Bun.write` 不校验产物可解析 | 损坏直接落盘 |
| 读取 | `readJsonSafe` catch 后返回 `null`（`digest.ts:392`） | 损坏与"文件不存在"不可区分 |
| 消费 | `buildDigest` 拿到 null 直接 `return null`（`digest.ts:758`） | **不产生任何 anomaly** |

结果：`bun scripts/trace-digest.ts` 因**一个**坏文件整体 `rc=1`，一条会话都看不了。
**可观测性工具把自己的诊断入口打死了**，而且不留任何线索。

`src/trace/writer.ts` 文件头当时明确承诺「替换只产生 `*`，不破坏 JSON 转义，落盘后仍可
JSON.parse / jq」——**这句承诺是假的**，且有测试（`writer-redaction.test.ts`）在断言
「脱敏后仍是合法 JSON」却从未用数字试过。测试绿 ≠ 契约成立。

**落地方案**（四层，逐层收窄）

1. **规则层** —— 信用卡号规则加两道二次校验（`SensitivePattern.validate` 新字段）：
   `isolatedNumber()` 排除小数/长数字的一部分；`luhnValid()` 校验位。
   实测判别力：真实测试卡号（`4111111111111111`）全部通过 Luhn，
   而观测到的全部误报（小数尾数）**全部不通过**。
2. **结构层** —— 新增 `maskSensitiveJson()`：**词法扫描**（非 parse→stringify），
   只在字符串字面量区间内替换，数字/布尔/null 字节原样保留。
   选词法扫描而非 parse→stringify 有两个硬理由：① 逐字节保持原缩进与键序，
   否则"写入的文本"与"调用方序列化的文本"不再相等；② 不触碰数值表示，
   `JSON.parse` 走 IEEE754 会把 `1e999` 变 `Infinity`、超长整数丢精度。
3. **闸门层** —— `writer.ts` 新增 `maskJsonSafe()`：脱敏后**立即 `JSON.parse` 自校验**，
   失败则**落原文 + 告警**。宁可少脱一次敏，也绝不把损坏数据写进盘
   （损坏是静默、不可逆的，还会连带打死诊断入口）。
4. **可见层** —— `digest.ts` 新增 `readTrajFile()` 区分「不存在」与「损坏」。
   损坏不再返回 `null`，而是降级为 **`traj_file_corrupt`（L0/high）anomaly + 尽力而为的 digest**：
   traj 读不出来，但 events/raw 侧结论照常产出。`--list` 里损坏会话标红为 `corrupt`。
5. **修复层** —— `cost-recompute.ts` 新增情形 A'：traj 损坏时据 `events.jsonl` **重建**
   （原文件另存 `.corrupt` 备份，不静默丢用户数据）。此前这里直接放弃，损坏即永久损坏。

**顺带补漏**：`appendErrorsJsonl()` 是 6 个落盘方法里**唯一没过脱敏的**——
而 writer 文件头写着「本文件的 **5 个**写入方法是全部落盘路径的收口点」。
**数量写进注释却与代码不符，于是第 6 个被漏掉**，而错误对象恰恰最容易带凭证
（异常消息常把请求头/URL 原样拼进去）。已接上脱敏并把注释与代码对账。

**存量修复**：`20260807-064304-8a21d2a3` 已据 events 重建，
恢复出 `cost=0.4428223060000257`（被抹掉的 8 位是 `22306000`），原文件存为 `.corrupt`。
现状：**33/33 份 traj 全部可解析**，`trace-digest` `rc=0`。

**测试**（44 例，全部锁不变量而非锁实现）

| 文件 | 锁住什么 |
|---|---|
| `tests/permission/sensitive.test.ts` | 5 个**真实造成过损坏**的 cost 值不被改写；真卡号仍脱敏；无命中时逐字节保持原文；超长数字/科学计数法不被 IEEE754 改写；**300 轮随机属性测试**：任意含数字对象脱敏后必定可 `JSON.parse` |
| `tests/trace/writer-redaction.test.ts` | 落盘产物必定可解析且数字不失真；`errors.jsonl` 也脱敏 |
| `tests/trace/digest.test.ts` | 损坏 → 报 `traj_file_corrupt` 而非返回 null；一个坏文件不影响其它会话 |
| `tests/trace/cost-recompute.test.ts` | 损坏 traj 被重建、原文件备份、幂等、events 也无数据时不制造半成品 |

其中 `digest.test.ts` 原有一条测试**断言「损坏 JSON → buildDigest 返回 null」**——
那正是把 `/trace` 打死的行为。断言已反转，并在原处留注释记着
「我们曾把静默失败当成正确行为固化进测试」。

**属性测试是这里的关键**：信用卡号这条已修，但任何**未来新增**的数字类规则
（手机号、身份证、订单号…）都会重踩同一个坑。逐条打补丁挡不住下一条，
所以第 2/3 层从**类型上**消灭这一整类 bug，属性测试守住那个不变量。

## 与北极星的对应

修完这批之后，能量出来的朝向感：

| 北极星方向 | 修复前 | 修复后可回答 |
|---|---|---|
| **可度量·底座** | 1 个产品埋点，~~67% 会话无终态~~（分母含空壳） | 5 条核心漏斗可聚合；**分母定义写进结论**，终态覆盖 27/27；轨迹损坏不再静默（有 `traj_file_corrupt` 信号） |
| **深度融合企业级** | span 只能落本地 jsonl | span/metric 进客户自有 OTel 栈 |

| **更安全** | essential-traffic 静默无效 | 三级隐私真实生效 |
| **更快** | TTFT 已有纯净埋点，但只能本地查 | 经 D2 的 OTLP 出口后可外部聚合 |

**本批不新增「更快」的采集能力，但它已不是空白——这点需要纠正一个流传中的旧说法。**

`docs/summary/北极星路线图.md` 写的「翻遍记忆无一条 latency / TTFT 基线」在撰写时（2026-07-24）之后已经推进。实测现状：

- TTFT 埋点在 `src/llm/stream-lifecycle.ts:362-371`，经 `StreamPhase("first_content").ttft_ms` 落盘，谓词覆盖 thinking + text，每次 fetch 独立计算、不受重试污染
- 两个消费方都已迁移到纯净源：`src/trace/digest.ts:1617`（`/trace`）与 `src/telemetry/provider-health.ts:137-138`（`/trace --health`，注释明确记录了 P0-1 迁移）
- `digest.ts:183-185` 提供 `ttft_p50/p95/p99` 分位

**所以「更快」的第 0 级（先能测）已经站上去了**，卡点前移到第 1 级「立基线 + 对照 CC」——需要的是同任务跑双方取 delta，不是补埋点。

真正剩下的 latency 缺口有两个，都不在本批范围，需要时另立任务：
