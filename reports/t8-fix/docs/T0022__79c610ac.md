## 1. P0 —— 规则匹配正确性，必须优先修

这两项是「用户按文档配了规则却不生效」的正确性问题，且 deny 侧失配是安全问题，最高优先。

### P0-1　Bash 规则用 minimatch，`*` 不跨 `/`

**现状（bug）**：`src/permission/rules.ts:76` 对 Bash 参数模式用 `minimatch(value, pattern, { dot: true })`。minimatch 是**文件系统 glob** 匹配器，`*` 按设计**不跨越 `/`**，还带 brace/bracket/extglob 语义。而 shell 命令里路径极常见，导致规则大面积失配。

**实测复现**（`bun -e`，已验证）：

```
"*"         vs "ls /tmp"              => false   ← Bash(*)「所有命令」哨兵失效
"cat *"     vs "cat src/foo.txt"      => false
"git *"     vs "git push origin/main" => false
"npm run *" vs "npm run build"        => true    ← 不含 / 才碰巧对
"ls *"      vs "ls -la"               => true
"ls *"      vs "lsof"                 => false   ← 空格+* 语义碰巧对（因空格不是 /，非机制正确）
```

**双向危害**：
1. **allow 规则静默漏放**：`Bash(*)`「放行所有 bash」对任何含路径的命令失效。更矛盾的是 `rule-loader.ts:47` 的 `DANGEROUS_SELF_AUTHORIZATION_PATTERNS` 专门把 `Bash(*)` 当危险自授权来剥离——认知（"它能放行一切"）与运行时行为（"它几乎放行不了带路径的命令"）完全对不上。
2. **用户 deny 规则含 `/` 静默失配（安全问题）**：用户写 `Bash(rm -rf /*)`、`Bash(*/secrets/*)` 之类自定义拦截规则会无声失效。所幸硬编码 `DANGEROUS_PATTERNS`（checker.ts:44-79）是独立正则，`rm -rf /` 等仍拦得住，但用户自定义 deny 不受此保护。

**CC 做法**：`claude-code/src/utils/permissions/shellRuleMatching.ts:90 matchWildcardPattern` 用自研正则：
- 先处理转义 `\*`（字面星号）、`\\`（字面反斜杠），用占位符暂存；
- 用 `replace(/[.+?^${}()|[\]\\'"]/g, '\\$&')` 转义正则元字符（**保留 `*`**）；
- 把未转义 `*` → `.*`；
- **尾部 ` *`（空格+唯一通配符）特判**：`git *` 的正则尾 ` .*` 改为 `( .*)?`，使 `git *` 同时匹配 `git add` 和裸 `git`（对齐 `git:*` 前缀语义）；多通配符如 `* run *` 不做此优化，避免 `npm run` 误匹配；
- 用 dotAll `s` flag 建 `^...$` 全串正则——`.` 匹配换行，使通配符能匹配含内嵌换行的命令（heredoc 拆分后场景）；
- 支持 caseInsensitive 参数。

**实施方案**：
1. 新增 `src/permission/shell-rule-matching.ts`，移植 CC 的 `matchWildcardPattern(pattern, command, caseInsensitive=false)` 与其转义/尾部特判/dotAll 逻辑（纯函数，无外部依赖，便于单测）。
2. 改 `rules.ts:matchRule`：**当 `toolName === "bash"`（或规则的 value 来自 `input.command`）时**，参数匹配走 `matchWildcardPattern` 而非 minimatch；文件路径类工具（read/write/edit）仍暂留原路径匹配（P0-2 统一改造，见下）。区分依据：请求的 `req.toolName` 或提取到的 value 来源。
3. 保留现有 `prefix:` 扩展（`rules.ts:70-73`）作为兼容；额外补 CC 的 `git:*` 前缀语法（可选，低优先）。
4. `Bash(*)` 经新 matcher 后能正确匹配一切 bash 命令，`DANGEROUS_SELF_AUTHORIZATION_PATTERNS` 剥离它的语义才成立——两处认知统一。

**验收标准**：
- 单测覆盖上表全部用例，`Bash(*)` 匹配 `ls /tmp`、`cat src/foo.txt`、`git push origin/main` 均为 true；`ls *` 匹配 `ls -la` 为 true、`lsof` 为 false；`git *` 匹配裸 `git` 为 true。
- deny 侧回归：`deny: ["Bash(*/secrets/*)"]` 能拦截 `cat app/secrets/key`。
- 转义：`Bash(echo \*)` 只匹配字面 `echo *`，不匹配 `echo foo`。
- `bun test` 全量 pass；`sc-dev` 手工验证 `Bash(*)` allow 规则对含路径命令生效。

### P0-2　Read/Edit 四种 gitignore 风格路径前缀全未实现

**现状（缺口）**：CC §7.4 定义 Read/Edit 路径规则四种前缀：

| 模式 | 含义 | 示例 |
|------|------|------|
| `//path` | 文件系统绝对路径 | `Read(//Users/alice/secrets/**)` |
| `~/path` | 主目录 | `Read(~/Documents/*.pdf)` |
| `/path` | 项目根相对 | `Edit(/src/**/*.ts)` |
| `path` 或 `./path` | 当前目录相对 | `Read(*.env)` |

sid-code 的 `matchRule`（rules.ts:65,76）对这四种**一个都没解析**：直接拿请求的 `input.file_path`（通常已是解析后的绝对路径）丢给 `minimatch(value, pattern, {dot:true})`。后果：
- 无 `//` → 绝对路径处理；
- 无 `~/` → home 展开（`~` 字面丢给 minimatch）；
- 无 `/` → 项目根解析（前导 `/` 只是 glob 锚点，不 resolve 到 workspace root）；
- 无 `./` → cwd 归一化（实测 `minimatch("/Users/x/.env", "./.env")` = false）。

`checker.ts:361 isPathHidden` 有个「绝对+workspace 相对都试一遍」的绕过办法，**证明作者知道前缀解析缺失**，但该 workaround 只用在 glob/ls 过滤，主 deny/ask/allow 匹配（`matchRule`）没有。`*`/`**` 在 minimatch 内部语义是对的（`src/**` 递归、`src/*` 单层），但前缀不解析导致整体不可靠。

**CC 做法**：`claude-code/src/utils/permissions/` 里路径规则先按前缀 resolve 成绝对路径再做 gitignore-风格匹配（`//`→绝对、`~/`→home、`/`→项目根、其余→cwd），四种前缀统一归一化到同一坐标系后比对。

**实施方案**：
1. 新增 `src/permission/path-rule-matching.ts`：`resolvePathRulePattern(pattern, { workspaceRoot, homeDir, cwd })` → 返回归一化后的绝对 glob 模式：
   - `//abs` → 去一个 `/` 作为文件系统绝对路径；
   - `~/x` → `join(homeDir, "x")`；
   - `/x`（单前导斜杠）→ `join(workspaceRoot, "x")`；
   - `./x` / `x` → `join(cwd, "x")`。
2. `matchPathRule(pattern, filePath, ctx)`：先 resolve 前缀，再用 minimatch（gitignore 语义，`dot:true`）比对**请求的绝对 file_path**。注意请求 value 需先 `realpath`/`resolve` 归一（复用 path-validator 已有解析），避免符号链接/相对路径绕过。
3. 改 `matchRule`：文件类工具（`FILE_TOOLS`：read/write/edit）走 `matchPathRule`；bash 走 P0-1 的 `matchWildcardPattern`；MCP/其它保持现状。
4. 把 `isPathHidden` 的「双候选」workaround 收敛到统一的 `matchPathRule`，消除重复逻辑。

**验收标准**：
- `Read(./.env)` 匹配 cwd 下 `.env` 的绝对路径；`Read(~/Documents/*.pdf)` 匹配 home 下 pdf；`Edit(/src/**/*.ts)` 匹配项目根 src 下任意深度 ts；`Read(//etc/**)` 匹配 `/etc/passwd`。
- `**` 递归、`*` 单层语义正确；`dot:true` 使 `.env` 类隐藏文件可匹配。
- deny 侧：`deny: ["Read(//Users/*/.ssh/**)"]` 拦截读 `~/.ssh/id_rsa`。
- `bun test` 全量 pass。

## 2. P1 —— 规则表达能力与模式行为缺口

### P1-1　`Agent` / `Agent(type)` 规则族缺失

**现状（缺口）**：CC §7.4：`Agent` 匹配所有子代理调用，`Agent(explore)` 匹配特定类型。sid-code：
- 子代理工具名是 **`sub_agent`**（`agent/tool.ts:234`），不是 CC 的 `Agent`；
- `matchRule` 只提取 `input.file_path || input.command || input.pattern`（rules.ts:65），子代理 input 的 `type`/`subagent_type` 字段不在其中，无法按类型做 arg 匹配；
- 子代理类型门控只有 plan 模式下的硬编码「只放行 explore」（checker.ts:1127），非可配置规则。

**实施方案**：
1. 在 `matchRule` 的 value 提取里，为 `sub_agent` 工具增加对 `input.subagent_type`（或 `input.type`）的提取：当规则 toolName 归一为 `Agent`/`sub_agent` 且带括号参数时，用子代理类型做匹配值。
2. 建立规则名别名：`Agent` ↔ 内部工具名 `sub_agent`（在 `matchRule` 或 rule-loader 归一层做双向映射），使用户写 `Agent(explore)` 能命中 `sub_agent` 调用。
3. `Agent`（无参）匹配所有子代理；`Agent(explore)` 用 `matchWildcardPattern`（支持 `Agent(verify*)` 等）匹配类型串。
4. 将 plan 模式硬编码的 explore 白名单改造为「默认注入一条 `allow: Agent(explore)` + `deny: Agent`」的等价规则（或保留硬编码但复用同一匹配函数），消除两套逻辑。

**验收标准**：`allow: ["Agent(explore)"]` + `deny: ["Agent"]` 下，explore 子代理放行、其它类型走 deny；`Agent(verify*)` 通配匹配 `verify`/`verify-x`。单测覆盖。

### P1-2　`WebFetch(domain:*)` 规则不可用 + web_fetch 无条件自动放行

**现状（缺口）**：CC 默认 WebFetch = **ask**（`WebFetchTool.ts:104 checkPermissions` 无匹配规则时 `behavior:'ask'`），并支持 `WebFetch(domain:example.com)` 规则 + preapproved-host 白名单（`preapproved.ts`，代码类域名 GET 免确认）。sid-code：
- `web_fetch` 在 `READ_ONLY_TOOLS`（checker.ts:133）→ Step 10 直接**无条件自动放行**，从不询问；
- 工具名 `web_fetch` ≠ 规则名 `WebFetch`；input 字段是 `url` 不被 `matchRule` 提取；
- 全库 `domain:` 0 命中，规则语法完全不支持。

sid 的 SSRF 防护是好的（`web-fetch.ts:55 isPrivateOrLocalhost` 拒私有 IP/localhost、:81 拒重定向到内网/metadata），但那是固定内置保护，**缺 domain 粒度的用户授权**——用户无法「只允许 github.com、其它询问」。

**判定与取舍**：CC 默认 WebFetch=ask 是「网络出站需人类把关」的契约。sid 当前默认全放行更激进。是否改默认需拍板：
- **方案 A（对齐 CC，推荐）**：把 `web_fetch` 移出 `READ_ONLY_TOOLS`，改为在其 `checkPermissions` 里实现 domain 规则匹配 + preapproved-host 白名单，无匹配 → ask。
- **方案 B（保守增强）**：保留默认放行，但**支持** `WebFetch(domain:x)` 的 deny/ask 规则（让用户能收紧），不改默认放行基线。

**实施方案（以 A 为例）**：
1. 新增 `src/tool/web-fetch/permission.ts`：`webFetchInputToRuleContent(input)` → `domain:${hostname}`（对齐 CC `WebFetchTool.ts:60`）。
2. `matchRule` 支持 `WebFetch(domain:hostname)` 语法：toolName 归一 `WebFetch` ↔ `web_fetch`，参数以 `domain:` 前缀时用 hostname 匹配（支持 `domain:*.example.com` 通配）。
3. 移植 CC `preapproved.ts` 的代码类域名白名单（github.com/raw.githubusercontent.com/npmjs.com/pypi.org/docs 类），`isPreapprovedHost(hostname, pathname)` 命中即 allow。
4. `web_fetch.checkPermissions`：先 preapproved → deny 规则 → ask 规则 → allow 规则 → 默认 ask（方案 A）或 allow（方案 B）。从 `READ_ONLY_TOOLS` 移除（方案 A）。
5. 同步 `WebSearch`（如有）评估是否需要同类处理。

**验收标准**：`WebFetch(domain:github.com)` allow 下 github 免确认、其它 ask（方案 A）；preapproved 域名默认免确认；deny `WebFetch(domain:evil.com)` 拦截。SSRF 防护回归不破。单测 + `sc-dev` 手工验证。

### P1-3　acceptEdits 不覆盖文件系统 bash 命令

**现状（缺口）**：sid 的 acceptEdits 只自动接受 `FILE_TOOLS`（read/write/edit，checker.ts:585-589）。CC 的 acceptEdits 还自动放行 cwd 内的文件系统命令 `mkdir/touch/rm/rmdir/mv/cp/sed`（`modeValidation.ts:7 ACCEPT_EDITS_ALLOWED_COMMANDS`），且带路径校验（命令操作的路径必须都在 cwd 内）。后果：sid 用户在 acceptEdits 下每个 `mkdir dist` 还得点确认，体验落后 CC。

**CC 做法**：`modeValidation.ts checkPermissionMode`：acceptEdits 模式 + baseCmd 是 fs 命令 → `behavior:'allow'`（decisionReason mode:acceptEdits）；配合 `pathValidation.ts` 校验命令路径参数都在 cwd（`mode:'acceptEdits'`，pathValidation.ts:773）——**跨 cwd 的 mv/rm 不自动放行**（bashSecurity.ts:2088 注释明示这是刻意的攻击面权衡）。

**实施方案**：
1. 新增 `ACCEPT_EDITS_FS_COMMANDS = ["mkdir","touch","rm","rmdir","mv","cp","sed"]`（与 CC 一致）。
2. 在 checker.ts Step 11（acceptEdits）扩展：`req.toolName === "bash"` 时，拆分复合命令（复用 `splitCompoundCommand`），对每个子命令取 baseCmd；**全部**是 fs 命令**且**其路径参数经 path-validator 校验都在 cwd 内 → 自动放行；任一不满足 → 落回 ask。
3. 危险命令层（Step 2）在 acceptEdits 之前，故 `rm -rf /` 等仍先被拦——保持 bypass-immune 语义不破。
4. `rm` 虽在白名单，但结合危险模式检测与 cwd 路径校验，只有「cwd 内普通 rm」才自动放行，跨目录/递归根仍拦。

**验收标准**：acceptEdits 下 `mkdir dist`、`mv a.txt b.txt`（均 cwd 内）免确认；`mv a.txt /etc/`（跨 cwd）仍 ask；`rm -rf /` 仍 deny；`curl x`（非 fs 命令）仍 ask。单测覆盖复合命令（`mkdir a && rm b` 全 fs 且 cwd 内 → 放行；`mkdir a && curl x` → ask）。

## 3. P2 —— 企业化与配置层

### P2-1　企业/managed policy 层未接进 RuleLoader（含三路径冲突 + 两套加载器）

**现状（缺口/隐患）**：
- 类型层声明 8 个源（`types.ts:80-100`）：session<command<cliArg<userSettings<projectSettings<localSettings<flagSettings<policySettings。
- 但 `RuleLoader.loadAll()`（rule-loader.ts:77-90）**只加载 3 个**：user/project/local。`flagSettings`/`policySettings`/`cliArg` 从不填充。`setCliArgRules()`（rule-loader.ts:195-207）**零调用者**——`--allow-tool`/`--deny-tool` CLI 规则从未接线。
- **企业策略权限规则永远进不了 checker。**
- **三个冲突的 policy 文件路径**互不调和：settings-module 的 policySettings → `/etc/sid-code/policy.json`（constants.ts:52）；`PolicyManager`/`ManagedFileLoader` → `~/.sid-code/managed-settings.json`（policy.ts:45）；`config.ts:1206 loadPermissionRules` 读第三个 `/etc/sid-code/policy.yaml`。`PolicyManager` 从不实例化（全库无 `new PolicyManager`）。
- **两套并行加载器**（系统 A：RuleLoader；系统 B：`config.ts:1201 loadPermissionRules`，cli.ts:1151 调用后作为初始 rules 传进 checker 构造器）读不同文件、格式（JSON/YAML）也不同，是维护隐患。

**实施方案**：
1. **统一 policy 文件路径**：确定单一企业策略来源（建议 `/etc/sid-code/managed-settings.json` + 可选 MDM 路径），废弃另外两个路径或做迁移别名；文档明确。
2. **RuleLoader 接入 policy/flag/cliArg 三源**：
   - `loadAll()` 增加读取 policySettings（最高优先级）、flagSettings（`--settings` 内存）；
   - 接线 `setCliArgRules()`：cli 解析 `--allow-tool`/`--deny-tool` 后调用；
   - 保持既有 source 优先级排序（rule-loader.ts:263-276）。
3. **企业策略以最高优先级 + 不可被下层放行覆盖**：policy 的 deny 恒生效；policy 若设 `allow` 也应可被理解为「仅企业可自我授权」（企业是可信源，不走 `DANGEROUS_SELF_AUTHORIZATION_PATTERNS` 剥离）。
4. **两套加载器合一**：以 RuleLoader 为唯一事实源，将 `config.ts:loadPermissionRules` 的职责并入 RuleLoader（或让 B 仅做初始占位、initRules 后以 A 为准），消除双读。落地前用单测锁定合并后各源的合并/去重/优先级行为。
5. **PolicyManager 真正实例化**：在 app 启动接线 `PolicyManager` 读 managed 文件（保留 0o600 权限校验 policy.ts:50-55），供 P2-2 的 `disableBypassPermissionsMode` 与 `disabledModes` 消费。

**验收标准**：`/etc/sid-code/managed-settings.json` 里的 `permissions.deny` 能拦截命令且不被 user/project 的 allow 覆盖；`--deny-tool Bash(curl *)` CLI 规则生效；单一加载器路径下 `bun test` 全量 pass；`/permissions` 展示的规则含 policy 源分组。

> ⚠️ 注意 CC §7.5 声明的优先级是 **Enterprise > user > project**（user 高于 project），而 sid 当前是 policy>local>project>user（更具体优先，project 覆盖 user）。这是**已知的刻意设计差异**（sid 走「更具体优先」如多数工具）。落地 P2-1 时**保持 sid 现有 user/project/local 相对序不变**，只把 policy 正确置顶——不要为对齐文档而反转 user/project（会破坏现有用户预期）。本差异在文档「非缺口」章节备案。

### P2-2　`disableBypassPermissionsMode` 管控缺失

**现状（缺口）**：全库无 `disableBypassPermissionsMode` 字段。bypass 可用性只由启动期快照 `bypassAvailableAtLaunch = config.skipPermissions === true`（app.ts:252）门控，管理员**无法**通过 managed settings 禁用 bypass 模式。`mode.ts:22 isBypassAvailable` 注释写「企业策略可禁用」但无 policy 路径实际设置它。`PolicySettings.disabledModes`（policy.ts:27）存在但 `PolicyManager` 从不实例化，`isModeDisabled()` 从不被调用。

**实施方案**（依赖 P2-1 的 PolicyManager 接线）：
1. managed settings schema 增加 `disableBypassPermissionsMode: "disable" | "allow"`（对齐 CC `utils/settings/types.ts:67`）。
2. app 启动读 policy 后，若为 `"disable"`：
   - `bypassAvailableAtLaunch` 强制 false（即使传了 `--dangerously-skip-permissions`）；
   - Shift+Tab 循环跳过 bypass 态；
   - 启动时若 CLI 传了 bypass 相关 flag，明确报错退出（对齐 CC `permissionSetup.ts` 的 fail-fast）。
3. 复用 `PolicySettings.disabledModes` 做更通用的「禁用任意模式」，`isModeDisabled()` 接进 `cyclePermissionMode` 与 CLI 校验。

**验收标准**：managed 设 `disableBypassPermissionsMode:"disable"` 后，`--dangerously-skip-permissions` 启动被拒/降级，Shift+Tab 循环不出现 bypass 态。单测 + 手工验证。

### P2-3　「始终允许(a)」只写会话内存，不落盘

**现状（缺口）**：CC §7.1 分层模型明确 Bash 的 "Allow always" 是「**按项目目录+命令永久记住**」，文件编辑的 "Allow always" 才是会话内。sid-code：`requestUserConfirmation`（app.ts:2510）在用户选 "always" 时只调 `rememberDecision`（checker.ts:412）写 `sessionMemory`；`rule-persistence.ts persistRule`（支持写 user/project/local settings）**零调用者**。用户想跨会话持久化只能手动 `/allow <rule> -p`。

**实施方案**：
1. 权限确认 UI（`PermissionPrompt.tsx`）在 Bash 工具时，把 "a 始终允许" 拆为两档（对齐 CC）：
   - **a**：本会话始终允许（现有 sessionMemory 行为）；
   - **A / 另一键**：持久化到项目 settings（写 `Bash(<归一命令模式>)` 到 project settings.json）。
   - 文件编辑类只保留会话档（对齐 CC「Edit always 仅会话」）。
2. 接线 `persistRule`：选持久档时，由命令生成合理的规则模式（如 `git status` → `Bash(git status)`，避免过宽），调 `rule-persistence.persistRule("project", "allow", rule, workspacePath)`，并热更新当前 checker 规则。
3. 命令→规则模式的归一策略需保守（默认精确匹配整条命令，不自动加 `*`），避免一次 always 放行过宽。可提供「精确/前缀」二选提示。

**验收标准**：Bash always 持久档写入 project settings.json 且下次会话生效；文件编辑 always 仅本会话；`persistRule` 有真实调用者；写入的规则经 P0-1 新 matcher 能正确命中原命令。
