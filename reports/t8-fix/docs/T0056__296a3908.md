### 第二阶段阻塞（缺正确的判据）—— **当前状态**

按上述分布实现了候选方案 A（ambient 改走独立尾部消息），结果：
`msg[0]` 断裂 **4 → 0**、26 个测试全绿、机理讲得通 —— **但真实命中率变差，已整体回滚。**

| 工作负载（同量配对） | 修复前 | 修复后 | 差值 |
| --- | --- | --- | --- |
| glm-5.2（6 步） | 81.9% | 81.6% | -0.2pp |
| glm-5.2（8 步） | 84.7% | 75.9% | **-8.8pp** |
| deepseek（7 步） | 79.2% | 68.0% | **-11.2pp** |

**根因：服务端按 token 前缀匹配，不按 message 对象匹配。**
OpenAI 族把多 text block `join("\n")` 成单 string（`openai.ts:568-573`），
"独立 block"与"独立 message"在 wire 上塌缩成同一串字节 —— 实测共同前缀长度前后都是 15 字符，
**理论收益为零**。`msg[0]→0` 是探针按 message 切段造成的**度量假象**：
加一条尾部消息让所有下标 +1，作废比例几乎没动（13.3%→12.9%）。

**连带作废候选表的 A/B 两行**（都只改 message 结构），只剩 C（注入回放）站得住，
而 C 要在"缓存命中"与"上下文占用"之间权衡，不是纯优化。

**新的解锁条件**：先给 `prefix-break-probe.ts` 加 **token/字符级共同前缀长度**度量，
与现有 message 级判据**并排落盘**，两者不一致时以 token 级为准。
否则继续在 message 层做优化，只会不断产出"看起来更好但实际更差"的改动。

> ⚠️ 这条教训已固化进记忆 `proxy-metric-rewards-relabeling-waste`：
> **判据与目标不同层时，目标指标归零 + 测试全绿 + 机理讲得通，三者同时成立仍可能是错的。**
> 救回来的唯一原因是回到账本真实命中率，而不是相信探针的 `wasted_ratio`。

## 1. 前置调查结论（2026-08-08 实测，已完成）

⚠️ **本节是本方案最重要的部分。调查推翻了博客的 3 个结论，其中 2 个是必须先修的 P0。**
后续所有实施步骤都建立在这些事实上，**执行前请先复跑验证脚本确认没漂移**。

### 1.1 【P0-A】gpt-5.6-luna 的 2.2% 是**漏采**，不是"后端不支持"

博客第 182-206 行断言 luna 的 2.2% 是"网关后端不支持前缀缓存"，判据是"67/67 次响应都有该字段、值恒 0"。
**这个结论是错的。** 真相是 sid-code 在 Responses API 路径上完全没有实现缓存字段提取。

证据链：

| 步骤 | 事实 | 证据 |
| --- | --- | --- |
| 1 | luna 在 registry 声明 `protocolKind: "openai-responses"` | `src/llm/model-registry.ts:127` |
| 2 | 该声明的优先级**高于**端点启发式，所以经 uniapi 网关也走 `POST /v1/responses` | `src/llm/openai.ts:1109`（优先级 2 短路）、`:1134` 注释明确说明 |
| 3 | Responses API 把命中放 `usage.input_tokens_details.cached_tokens`，**不是** `prompt_tokens_details` | 实测见下 |
| 4 | `parseResponsesStream` 只映射 `input_tokens` / `output_tokens`，**从不读任何 cache 字段** | `src/llm/openai-responses.ts:303-306`；`ResponseObject.usage` 类型声明 `:77-81` 只有三个字段 |
| 5 | `extractOpenAICacheHit` 的三级兜底链**不含** `input_tokens_details.cached_tokens`，且只在 Chat 路径被调用 | `src/llm/openai.ts:83`（定义）、`:1536`（非流式 chat）、`:1771`（流式 chat）—— Responses 路径零调用 |

实测（uniapi 网关，`POST /responses`，全新随机前缀）：

```
r1 usage: {"input_tokens":18017,"input_tokens_details":{"cached_tokens":0},    ...}
r2 usage: {"input_tokens":18017,"input_tokens_details":{"cached_tokens":17152},...}
r3 usage: {"input_tokens":18017,"input_tokens_details":{"cached_tokens":17152},...}
```

**luna 的真实命中率是 95.2%（17152/18017），账本记的 2.2% 是采集缺陷。**
同理 `gpt-5.4`（`model-registry.ts:130` 同样声明 openai-responses）的 6.3% 也是同一个 bug。

**受影响面比博客提到的两个模型大得多**（脚本数，非目测）：registry 里声明
`protocolKind: "openai-responses"` 的共 **11 个**模型 ——
`gpt-5.2 / gpt-5.4 / gpt-5.4-mini / gpt-5.4-nano / gpt-5.4-pro / gpt-5.5 / gpt-5.5-pro /
gpt-5.6 / gpt-5.6-luna / gpt-5.6-sol / gpt-5.6-terra`。
**这 11 个模型的缓存命中全部漏采**，只是账本里目前只用过 luna 与 gpt-5.4。
所以 P0-1 不是"修两个模型"，是修**一整个协议族**。

账本中已受影响的两个模型合计 43 会话、8733 万输入 token，占账本总量的 18.3%。

除缓存命中外，**同一路径还漏采 reasoning token**：实测 Responses 响应带
`output_tokens_details.reasoning_tokens`，而 `openai-responses.ts` 对
`extractOpenAIReasoningTokens`（`openai.ts:107`）零调用，`ResponseObject.usage` 类型声明
（`:77-81`）也只有 `input_tokens / output_tokens / total_tokens` 三个字段。
→ P0-1 要一并补上，否则 thinking 模型的隐藏成本在这一族上同样测不出。

> 方法论教训（值得写进博客）：博客那个"找同代码路径对照组"的判据本身是对的，
> 但**它认错了代码路径** —— glm-5.2 走 Chat Completions，luna 走 Responses，
> 两者从来不是同一条路径。"67/67 都有该字段"这个观察也是错的：
> 读的是 `prompt_tokens_details`，而 Responses 响应里根本没有这个键，读到的是 `undefined` 而非 0。
> **判断"同代码路径"必须核实协议分派，不能只看 provider 与 base_url 相同。**

### 1.1b 【P0-E · 新发现】非流式路径不做 Responses 分派 → GPT-5.x 降级时走错协议

调查 P0-1 时撞到的独立缺陷，**博客完全没提到**。

事实：`shouldUseResponsesAPI` 只在流式入口 `sendMessageStreamInner`（`src/llm/openai.ts:738`）
被调用；非流式 `sendMessageNonStreamingInner` **无条件** `fetch(`${baseURL}/chat/completions`)`
（`src/llm/openai.ts:1422` 附近，全函数内 `/responses` 零命中）。

这不是疏漏——`openai.ts:365-371` 的注释已明确记录了它，并为此在
`isUnknownFamily` 判据里加了一道补丁（避免把 Responses 专属的 `xhigh`/`max` 档位
当普通 `reasoning_effort` 发到 Chat 线上）。**但补丁只挡住了 effort 字段，没解决协议错配本身。**

触发路径（三条，都是真实的）：
1. **流式传输错误降级** —— `src/api/stream-handler.ts:174-192`，流式失败且未产出内容时降级
2. **空流降级** —— `stream-handler.ts:58`，`degradeOnEmptyStream`
3. **ModelFallback** —— `src/llm/fallback.ts:1547-1587`

后果分三层，**第三层与本方案直接相关**：
- 请求以 Chat Completions 线格式发出，丢掉 Responses 专属能力（reasoning 档位、instructions 语义）
- 网关若不为该模型提供 Chat 端点，降级会**二次失败**——而降级恰好发生在网关已经异常的时刻
- **缓存与用量口径分裂**：同一个模型，流式走 Responses（命中在 `input_tokens_details`）、
  降级走 Chat（命中在 `prompt_tokens_details`）。修完 P0-1 后两条路径读不同字段，
  若不一并处理，就会出现"同一模型同一会话，取决于当时是否降级而命中率口径不同"——
  这正是 `openai.ts:1332-1339` 那段注释批评过的"行为取决于当时走了哪条路，无法解释也无法复现"。

**修法（P0-5）**：在 `sendMessageNonStreamingInner` 里同样做 `shouldUseResponsesAPI` 分派。
Responses API 支持非流式（`stream: false`），需新增一个非流式 Responses 请求分支
（可复用 `mapResponseEvent` 的 usage 提取逻辑，**不要写第二份**）。
若判定改造过大，**退路是显式拒绝**：GPT-5.x 走非流式时直接抛明确错误而不是静默换协议——
静默走错协议比失败更糟。两种选择都要在提交信息里说明理由。

⚠️ 这条改完要回头删掉 `openai.ts:365-371` 那段补丁注释所依赖的前提说明（或改写为"已修"），
否则注释与代码漂移。

### 1.2 【P0-B】cache-breaks 落盘丢弃了 hash 字段，博客的 418/232 分母是错的

博客第 208-230 行说"650 条里 418 条带 hash 判据"。实测：**676 条记录里带 `previousPrefixHash` 字段的是 0 条。**

根因：`emitCacheBreakTelemetry`（`src/telemetry/cache-telemetry.ts:49-60`）手写字段拷贝列表，
**漏了 `previousPrefixHash` / `currentPrefixHash`**。检测器算出来了（`src/api/cache-detection.ts:277-278`），
落盘时被丢掉。

实测落盘字段只有 8 个：
`ts / model / dropTokens / dropPercent / changes / previousCacheReadTokens / currentCacheReadTokens / precededByRetry`

那么博客的 418 从哪来的？从 `changes[]` 的**人类可读文案**里 grep "hash 未变"：

```
服务端波动(hash未变，从 changes 文案推断)  442
未知原因（判据上线前的旧记录）              232
模型变化                                      2
```

所以"99.5% 是服务端波动"这个**结论方向是对的**（442/444），但它依赖对中文文案做子串匹配，
不是结构化字段 —— 这正是记忆 `attribution-decoupled-from-signal-antipattern` 批评的反模式。
文案改一个字，所有历史统计就断。

### 1.3 【P0-C】ppchat 网关（月卡）伪造 Anthropic usage，数据不可用于度量

用户提供的 `https://code.ppchat.vip` 渠道，**Anthropic 协议的 usage 是编造的**。三重判据全部命中：

判据 A —— 全新随机前缀（服务端必然从未见过），r1 就报大量 `cache_read`：
```
[ppchat anthropic sonnet-4-6] 全新前缀 nonce=1786152040-a7f3
  r1 in=225 read=13860 create=2485 sum=16570   ← r1 就命中 13860，不可能
```

判据 B —— **完全不打 `cache_control`**，仍报命中：
```
  r1 in=700 read=12239 create=3439 sum=16378   ← 没打断点也"命中"
```

判据 C —— 同一前缀连发 5 次，三个数**随机跳动而总和恒定**（这是铁证：网关把一个固定总数随机三等分）：
```
[ppchat claude-sonnet-5] 同一前缀 ×5
  r1 in= 31 read=8654 create=4474 sum=13159
  r2 in=710 read=7317 create=5132 sum=13159
  r3 in= 53 read=8896 create=4210 sum=13159
  r4 in=929 read=8941 create=3289 sum=13159
  r5 in=409 read=9724 create=3026 sum=13159
```

对照 —— 同款判据下的 uniapi 网关（公司网关）**行为完全正确**：
```
[uniapi anthropic sonnet-4-6] 全新前缀
  r1 in=25 read=0 create=39966    ← r1 正确报 0 命中、全量写入
  r2 in=13 read=0 create=39601    ← 注意：r2 仍 read=0（见下）
```

**这条直接污染了博客的 anthropic 族数字。** 账本里 `claude-sonnet-5`（3 会话、8444 万 token、82.2%）
和 `claude-opus-5`（4 会话、73.8%）**都配在 ppchat 渠道**（`settings.json` 实测）。
也就是说博客表格里 anthropic 族那 81.4%、以及"cacheWrite 1578 万"这个"印证协议差异"的证据，
**建立在一个会编造 usage 的网关上，全部不可用。**

三个次生结论：
- 月卡渠道**不能作为度量数据源**，只能作为功能可用性验证。要度量必须用 uniapi 或官方直连。
- 需要一个**渠道可信度探针**，把这类网关自动标记出来，否则脏数据会持续流进账本。
- 博客"anthropic 族样本太少（能力边界 #4）"这条要重写成更严重的版本：**样本不仅少，而且脏。**

### 1.4 uniapi 的 anthropic 通道 r2 仍 read=0 —— 待查

## 6. 风险与约束

- **实测会花钱**。T2/T3 都要真实请求。每个脚本必须有硬成本上限 + `max_tokens` 护栏。
- **实测会污染账本**。所有实测脚本必须自设 `SID_CODE_USAGE_LEDGER` / `SID_CODE_CACHE_BREAKS`
  到临时路径。T0 备份 + T6 行数核对是兜底。
- **ppchat 是月卡渠道**，用于验证功能可用性可以，**不可作为任何博客数字的来源**。
- **账本是滚动窗口**，任何"修复前 vs 修复后"的对比都必须用 T3 的受控脚本同参数跑，
  不能拿两天的账本聚合相减（博客第 153-160 行已有此教训，别再犯）。
- **不要碰与本任务无关的文件**（CLAUDE.md §0 铁律）。当前 git status 里
  `website/blog/ref-claude-code.md`、`ref-codex.md`、`ref-opencode.md` 是并行工作，禁止动。
