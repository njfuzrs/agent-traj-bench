# 前缀断裂分布实测（T4 / P1-2 产出，为 P1-3 定向）

> 实测日期：2026-08-08
> 数据来源：4 个 `sid-code -p` 无头会话（glm-5.2 ×3 + origin-deepseek-v4-pro ×1）
> 埋点：`src/trace/collector.ts:747` → `src/trace/prefix-break-probe.ts`
> 复现：`bun scripts/trace-digest.ts` 看「前缀断裂」段落

## 0. 结论：只有一个该修的地方

**29 个比较轮次，10 次断裂（34.5%），100% 是 `message` 段类型。**
`system_static` / `system_dynamic` / `tools` **零断裂** —— 系统提示词的静态/动态切分
（`DYNAMIC_BOUNDARY`）与工具区排序是稳定的，那三处不用动。

按**浪费量**（而非次数）排序，答案唯一：

| 断点位置 | 次数 | 平均作废 | 最差 | **占总浪费** |
| --- | --- | --- | --- | --- |
| `msg[0]` | 4 | 13.3% | 14.1% | **81.6%** |
| `msg[2]` | 4 | 1.9% | 2.3% | 11.5% |
| `msg[16]` | 1 | 2.9% | 2.9% | 4.5% |
| `msg[14]` | 1 | 1.6% | 1.6% | 2.4% |

**次数相同（4 vs 4），浪费差 7 倍。** 这正是 P1-2 设计时坚持"按浪费量排序而非次数"
的理由 —— 只看次数会把 `msg[0]` 和 `msg[2]` 当成同等重要。

## 1. 根因：reminder 的挂载目标随 tool_result 迁移

`injectReminders`（`src/query/reminder-inject.ts:108`）倒序找**最后一条 user 消息**挂 reminder。
而 tool_result 是以 `role: "user"` 入历史的（`src/query/loop.ts:3562`）。
于是"最后一条 user 消息"这个锚点**每轮都在往后移**：

```
第 1 轮  messages[0] = [用户指令, <system-reminder>延迟工具列表</system-reminder>]  ← 挂在这
第 2 轮  messages[0] = [用户指令]                                                  ← 没了！
         messages[2] = [tool_result, <system-reminder>…</system-reminder>]          ← 挂到这了
```

**断裂不是"加了东西"造成的，是"上一轮加的东西这轮没了"造成的。**
第 1 轮发出去的 `messages[0]` 带 reminder，第 2 轮发出去的不带 → 服务端看到前缀在第 0 条就变了
→ **其后全部历史作废**。

离线复现（不打网络，纯函数）：

```
=== 第1轮 messages[0] ===
[{"type":"text","text":"用户的真实指令"},{"type":"text","text":"<system-reminder>…</system-reminder>"}]
=== 第2轮 messages[0] ===
[{"type":"text","text":"用户的真实指令"}]
messages[0] 跨轮是否一致 : false
```

段数签名也印证是同一机制：4 次 `msg[0]` 断裂全部是 `segs=4→6`，
4 次 `msg[2]` 全部是 `segs=6→8`（segments = static + dynamic + tools + 每条消息一段）。

**这是滚动断裂**：每一轮都会让"上一轮的最后一条 user 消息"失去 reminder。
所以断点位置随会话推进（0 → 2 → 14 → 16）。
越靠后的断点浪费越小（只作废尾部），**而 `msg[0]` 那一次作废的是整个历史** ——
在 50 轮的长会话里，这一次断裂的代价远不止实测的 13%。

## 2. 为什么排除了其它候选

方案 §2 P1-3 列的四个候选，实测把三个排除掉了：

| 候选 | 实测判决 |
| --- | --- |
| **reminder 挂载点迁移** | ✅ 命中。占总浪费 81.6% + 11.5% = **93.1%** |
| 动态区顺序稳定化 | ❌ `system_dynamic` 零断裂，动态区本身是稳的 |
| 工具集合/顺序不稳定 | ❌ `tools` 零断裂 |
| JIT 淘汰 | ❌ 本批会话未触发 JIT 注入（`msg[14]/[16]` 是同一个 reminder 机制的尾部表现） |

⚠️ **样本局限**：4 个会话都是"逐步调工具"的形态，没有覆盖
`/compact` 后、JIT 注入密集、子代理并发这几类。JIT 淘汰这条**不能算证伪，只能算未观测到**。

## 2.5 ⚠️ 方案 A 已实测，**无效，已回滚**（2026-08-09）

把 ambient 从"splice 进最后一条 user 消息"改成"独立尾部消息"，
单测与集成测试全绿、`msg[0]` 断裂从 4 次降到 **0 次**。看起来成功了。

**但真实命中率变差了。** 同工作负载配对（promptTotal 相差 < 300 token）：

| 工作负载 | 修复前 | 修复后 | 差值 |
| --- | --- | --- | --- |
| glm-5.2（m1-m4.js 6 步） | 81.9% | 81.6% | -0.2pp |
| glm-5.2（s1-s6.ts 8 步） | 84.7% | 75.9% | **-8.8pp** |
| origin-deepseek-v4-pro（p1-p5.py 7 步） | 79.2% | 68.0% | **-11.2pp** |

### 为什么无效：服务端按 token 前缀匹配，不按 message 对象匹配

把 ambient 挪个位置，**wire 上的共同 token 前缀长度完全没变**（实测都是 15 字符）：

```
修复前 共同前缀: "system\n用户的真实指令\n"   （15）
修复后 共同前缀: "system\n用户的真实指令\n"   （15）
```

OpenAI 族把多 text block `join("\n")` 成单 string（`openai.ts:568-573`），
"独立 block" 与"独立 message"在 wire 上都塌缩成同一串字节。
**理论收益为零。**

而 `msg[0] → 0` 那个"改善"是**探针的度量假象**：探针按 message 切段
（`prefix-break-probe.ts:111` 每条消息一段），加一条尾部消息会让所有下标 +1，
于是断裂从 `msg[0]` 变成 `msg[1]` —— 作废比例几乎没动（13.3% → 12.9%）。

逐轮断裂序列前后**形态完全一致**，只是下标平移：

```
修复前  Y(13%@0) Y(1%@2) · · · · · · Y(2%@14)
修复后  Y(13%@1) Y(1%@3) · · · · · · Y(1%@17)
```

> **这一课比这个 bug 本身值钱：我优化的是仪器的读数，不是仪器测的东西。**
> `msg[0]` 归零 + 测试全绿 + 一个讲得通的机理，三件事同时成立，
> 却仍然是错的 —— 因为判据（message 级下标）和目标（token 级前缀）不同层。
> **拿代理指标当验收标准，会奖励"把浪费重新贴个标签"的改动。**
> 救回来的唯一原因是去查了账本的真实命中率，而不是相信探针的 wasted_ratio。

### 对 P1-3 的影响：候选方案 A/B 全部作废

A（独立尾块）与 B（并入 OpenAI 族已有动态尾块）**都只改 message 结构**，
在 token 前缀匹配下等价于什么都没做。**§3 那张表里只有 C 还站得住。**

## 3. 修法有三条路，且都有真实代价（需决策）

难点在于：**断裂的成因是"移除"，所以修法必须让历史消息跨轮字节一致**，
而现有设计有三条带实测事故背书的不变量（见 `reminder-inject.ts` 头注），不能硬改。

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **A · 独立尾块** | ambient 不再splice 进最后一条 user 消息，改为**追加一条独立尾部消息** | 改 wire 形态。Anthropic 连续 user 消息有 role 交替约束、部分网关拒；这正是当初否决"独立 message"的原因（头注已记录） |
| **B · 并入已有动态尾块** | OpenAI 族已经有 `prependSystemMessage` 造的独立 `<system-reminder>` 尾部消息（`openai.ts:286`），ambient 并进去 | 只修 OpenAI 族（恰好是本仓库主力），Anthropic 保持现状 → 引入 provider 行为分叉 |
| **C · 注入回放** | 记录"第 N 条消息当时注入了什么"，后续轮次原样回放，保证历史字节一致 | reminder 会在发送副本里逐轮累积 → token 膨胀，正是 `reactive-compact` / `auto-compact` 现在刻意剥离它的原因 |

~~**倾向 B**~~ —— **上面这张表的 A/B 两行已被 §2.5 实测推翻，勿再照此选型。**

A/B 都只改 message 结构，而服务端按 **token 前缀**匹配：多 text block 与多 message
在 wire 上都被 `join("\n")` 塌缩成同一串字节（`openai.ts:568-573`），共同前缀长度不变，
**理论收益为零**。A 已实测：真实命中率 -0.2 / -8.8 / -11.2pp。

剩下 C（注入回放）是唯一在 token 层真正让历史字节一致的路，但它的代价也在 token 层：
reminder 逐轮累积 → 上下文膨胀，正是 `reactive-compact` / `auto-compact` 现在刻意剥离它的原因。
**等于要在"缓存命中"和"上下文占用"之间做权衡，不是纯优化。**

### 真正该先回答的问题（比选方案更靠前）

`msg[0]`/`msg[1]` 那 13% 的作废**到底是不是可回收的**？

现在还不知道。已知的是：把它从 `msg[0]` 挪到 `msg[1]` 毫无收益，
说明 13% 这个数字**本身就是 message 级判据的产物**，未必对应 token 级的真实损失。
下一步应该先给探针加一条 **token 级（字符级）共同前缀长度**的度量，
与 message 级判据并排落盘 —— 两者对不上的时候，以 token 级为准。

**否则继续在 message 层做优化，只会不断产出"看起来更好但实际更差"的改动。**

**未做，等决策。**
