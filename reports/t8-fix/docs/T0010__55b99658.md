# 单测污染用户遥测数据 —— 隔离缺口根治 + prompt cache 博客

> **文档性质**：待开发设计（**只记录，不改代码**）。
> **本文档覆盖两件事，都没做完**：
>   1. **第一～七节**：单测往用户真实遥测文件写假数据的缺陷，及其修复与验证方案。
>   2. **第八节**：prompt cache 那篇博客——**这才是原始任务**，第 1 件事只是做它时撞上的障碍。
>      修完 bug 只是解锁了数据源，文章一个字都还没写，已采集的事实存在第八节备用。
> **发现路径**：为博客采集 prompt cache 实测数据时，发现 `~/.sid-code/cache-breaks.jsonl`
>   里 847 条记录**全部**是测试构造的假数据（时间戳 `1700000000` = 2023-11-15），
>   顺着写入方回溯到两个未做隔离的单测。
> **证据基础**：本机真实数据文件 + 源码调用链 + 只读统计脚本（命令见第四、八节，可复现）。
> **⚠ 别只看前七节就当结项**：那样等于修好了取数的路，却没去取数。

---

## 零、一句话

两个单测直接调了会**同步落盘**的 `recordCacheBreak()`，而没有设置项目已经提供的
隔离环境变量 `SID_CODE_CACHE_BREAKS`，于是每跑一次 `bun test` 就往用户真实的
`~/.sid-code/cache-breaks.jsonl` 灌一批假记录。用户 `/cache --history` 看到的
最近 20 条里有 16 条是这些假数据，时间显示 2023-11-15。

这不是「测试写了个临时文件没删」这种量级的问题：**它污染的是一条可观测性数据链**，
而「更省」是项目四个北极星方向里唯一有硬数据支撑的那个。

## 一、现象

### 1.1 数据文件的实际状态

```bash
wc -l ~/.sid-code/cache-breaks.jsonl ~/.sid-code/cache-breaks.jsonl.1
#    847 cache-breaks.jsonl
#  60701 cache-breaks.jsonl.1
```

主文件头两行（`ts` 是 `1700000000`，即 2023-11-15，一个典型的测试固定值）：

```json
{"ts":1700000000,"model":"deepseek-v4-pro","dropTokens":5,"dropPercent":60,"changes":["System prompt 变化"],"previousCacheReadTokens":5000,"currentCacheReadTokens":2000}
{"ts":1700000000,"model":"deepseek-v4-pro","dropTokens":29,"dropPercent":60,"changes":["System prompt 变化"],"previousCacheReadTokens":5000,"currentCacheReadTokens":2000}
```

精确统计（判据：`ts === 1700000000`，或 `ts < 1e9` 即早于 2001 年——真实 epoch 不可能这么小）：

| 文件 | 总行 | 假数据 | 真实 | 真实数据区间 |
| --- | --- | --- | --- | --- |
| `cache-breaks.jsonl` | 847 | **847（100%）** | **0** | — |
| `cache-breaks.jsonl.1` | 60701 | 60109（99.0%） | **592** | 2026-06-29 → 2026-08-02 |

也就是说：**当前文件里一条真实记录都没有**，全站仅存的 592 条真实中断记录在轮转文件里。

假数据有两种形态，来自不同的测试写法：

- `ts: 1700000000`（2023-11-15），`model: "deepseek-v4-pro"` —— 56917 条
- `ts: 1000 / 2000 / 3000`，`model: "opus"` / `"sonnet"` 这类占位名 —— 3192 条

⚠ 第二种形态一度被我误判为「`ts` 单位被当成毫秒写入」，实测否证：
`ts > 1e11` 的记录数为 0，它们就是测试里写死的小整数字面量。
**清理脚本的判据必须同时覆盖这两种形态**，只过滤 `1700000000` 会漏掉 3192 条。

### 1.2 用户可见的后果

`/cache --history` 的实现（`src/command/builtins.ts:1487-1500`）读尾部 20 条做明细、
尾部 500 条做归因聚合。实测这两个窗口里的假数据占比：

按 `queryCacheBreakHistory` 的真实读取路径复刻（读当前文件尾部，不足 limit 时回补 `.1` 尾部）：

| 读取窗口 | 假数据条数 | 占比 |
| --- | --- | --- |
| 尾部 20 条（明细列表） | 20 | **100%** |
| 尾部 500 条（归因聚合） | 500 | **100%** |

也就是说这个命令**当前完全不可用**，不是"掺了些假数据"而是**一条真的都看不到**：
用户看到一屏 `[2023/11/15 ...] deepseek-v4-pro: 下降 60%`，归因清一色「System prompt 变化」
——全是测试构造的形状。那 592 条真实记录被压在 `.1` 的更早位置，两个窗口都取不到。

### 1.3 影响面的边界（别夸大）

必须写清楚**没有**被污染的部分，否则会误导后续排查：

| 文件 | 状态 | 说明 |
| --- | --- | --- |
| `~/.sid-code/cache-breaks.jsonl` | ❌ 已污染 | 本文主题 |
| `~/.sid-code/usage-ledger.jsonl` | ✅ 干净 | 265 行，`ts === 1700000000` 计数为 0。**「更省」的真正度量源在这里**，缓存命中率/成本口径不受影响 |

CLAUDE.md 里「deepseek 受控 0→83.2%、anthropic 族 99.5%」这两个数字的口径是
`usage-ledger.jsonl` 的 `cacheHit / promptTotal`
（出处：`docs/bugfixes/todo/企业级能力/企业级能力规划.md:313`），因此
**那两个数字不受本问题影响**，不需要重测。受影响的只有「中断归因」这一路。

## 二、根因

### 2.1 调用链：`recordCacheBreak` 无条件落盘

```
tests/api/cache-detection.test.ts:213      recordCacheBreak(rec({...}))
tests/command/clear-resets-cache-state.test.ts:77
  → src/api/cache-detection.ts:421         recordCacheBreak()
      :422  recentBreaks.push(record)               // 内存环形缓冲（测试真正想验的）
      :428  emitCacheBreakTelemetryFireAndForget()  // ⚠ 顺带落盘（测试不想要的副作用）
  → src/telemetry/cache-telemetry.ts:50    emitCacheBreakTelemetry()
      :41  cacheBreaksPath()
      :42    process.env.SID_CODE_CACHE_BREAKS ?? sidPaths.cacheBreaks()
                                                    // 未设 → ~/.sid-code/cache-breaks.jsonl
```

函数本身没有错：内存缓冲 + 落盘遥测本来就该一起发生，`:426` 的注释写明了这是
G13 的设计意图。问题在**测试侧没有隔离这个副作用**。

### 2.2 隔离机制存在，但只有一个测试用了

`src/telemetry/cache-telemetry.ts:15` 的文件头注释已经明确写了：

> 存储位置：~/.sid-code/cache-breaks.jsonl（可经 `SID_CODE_CACHE_BREAKS` 环境变量重定向，**测试隔离用**）。

全仓引用情况：

```bash
grep -rln "SID_CODE_CACHE_BREAKS" tests/ src/
# tests/telemetry/cache-telemetry-rotation.test.ts   ← 唯一设了的测试
# src/telemetry/cache-telemetry.ts                    ← 定义方
```

三个会触发落盘的测试文件里，只有轮转测试做了隔离（`mkdtempSync(join(tmpdir(), ...))`，
见其 `:39`）。另外两个一次都没设：

| 测试文件 | 落盘调用点 | 设了隔离吗 |
| --- | --- | --- |
| `tests/telemetry/cache-telemetry-rotation.test.ts` | 直接调 emit | ✅ tmpdir |
| `tests/api/cache-detection.test.ts` | `:213/214/221/228/233/239/249` 等 | ❌ |
| `tests/command/clear-resets-cache-state.test.ts` | `:77/86/105/116` | ❌ |

`cache-detection.test.ts:221` 有一处 `for (let i = 0; i < 60; i++) recordCacheBreak(...)`
——单个用例一次写 60 行，这是量能堆到 5.7 万的原因。

### 2.3 为什么一直没被发现

三个条件叠加，让它成为一个静默故障：

1. **落盘是 fire-and-forget 且吞异常**（`cache-detection.ts:427-431`、
   `cache-telemetry.ts` 的读写均容错）。设计上「遥测失败绝不阻断主流程」是对的，
   代价是写错位置也不会有任何提示。
2. **测试断言的是内存缓冲**（`getRecentCacheBreaks()`），落盘那一路不在断言范围内，
   所以测试全绿也说明不了落盘去了哪。
3. **10MB 才轮转**（`cache-telemetry.ts:73` `MAX_BYTES`），污染先静静堆积，
   堆满一轮后 `renameSync` 到 `.1`，看起来像"正常有历史数据"。

### 2.4 这是一类问题，不是一个 bug

值得记录的是**判据**，而不只是这两个文件：

> 只要一个函数除了返回值还有「写用户家目录」这种进程外副作用，
> 调它的测试就必须显式隔离；而"必须记得隔离"这件事不能只靠人记住。

同类风险点（本次**未逐一核实**，属后续待查，别当成已确认的结论）：
`~/.sid-code/` 下其余 append-only 遥测/审计文件，尤其
`audit.log`、`permissions-audit.log`、`usage-ledger.jsonl`、`history.jsonl`、
`protocol-violations/`。判据同上：找 `sidPaths.*()` 的写入方，再看它的测试有没有重定向。

## 三、修复方案

分三层，**建议按 A → B → C 顺序做，每层可独立验证、独立提交**。
A 是止血，B 是根治，C 是防复发；只做 A 会复发，只做 B/C 不清历史数据。

### A. 清理已污染的数据（一次性，需用户确认）

不是代码改动，但要先做，否则 B/C 完成后 `/cache --history` 依然是脏的。

两个选项，**推荐 A1**：

- **A1｜按判据剔除假行，保留真实记录**。剔除条件：`ts === 1700000000` **或** `ts < 1e9`
  （两种形态都要覆盖，见 1.1 节；只过滤前者会漏 3192 条）。
  预期结果：主文件 847 → **0 行**（当前文件里没有任何真实记录），
  `.1` 60701 → **592 行**。
  ⚠ 主文件会被清空，这是对的——真实数据全在 `.1` 里，而读侧
  `queryCacheBreakHistory` 在当前文件不足 limit 时会自动回补 `.1` 的尾部
  （`cache-telemetry.ts:138-143`），所以清空主文件不会让 `/cache --history` 失忆。
- **A2｜整体归档为 `.bak` 后清空**。更简单，代价是丢掉 `.1` 里那 592 条真实记录——
  而它们是全站仅存的真实中断样本，**也是第八节那篇博客「什么操作会打断缓存」一节的唯一数据源**。
  除非清理脚本写不对，否则不建议走这条。

⚠ 这两个操作都写用户数据目录，**属于不可逆操作，实施前必须向用户确认**，
并且先 `cp` 一份备份再动手。本文档不代替那次确认。

### B. 给测试补隔离（根治写入源）

对 `tests/api/cache-detection.test.ts` 与
`tests/command/clear-resets-cache-state.test.ts` 各加一段 `beforeAll/afterAll`：

```ts
// 与 tests/telemetry/cache-telemetry-rotation.test.ts:39 同构
let tmpDir: string;
let savedEnv: string | undefined;

beforeAll(() => {
  savedEnv = process.env.SID_CODE_CACHE_BREAKS;
  tmpDir = mkdtempSync(join(tmpdir(), "cache-detection-"));
  // recordCacheBreak 会同步落盘（cache-detection.ts:428）。不重定向就会写进
  // 用户真实的 ~/.sid-code/cache-breaks.jsonl —— 历史上已污染 5.7 万行。
  process.env.SID_CODE_CACHE_BREAKS = join(tmpDir, "cache-breaks.jsonl");
});

afterAll(() => {
  if (savedEnv === undefined) delete process.env.SID_CODE_CACHE_BREAKS;
  else process.env.SID_CODE_CACHE_BREAKS = savedEnv;
  rmSync(tmpDir, { recursive: true, force: true });
});
```

两个注意点：

- **必须存/恢复原值**而不是无条件 `delete`：`bun test` 同进程跑多文件，
  直接删会影响后续测试文件的环境。
- 环境变量在 `cacheBreaksPath()` 里是**每次调用时读**（`cache-telemetry.ts:41-45`），
  不是模块加载时快照，所以 `beforeAll` 里设置是有效的，不需要动 import 顺序。

### C. 加一道防复发门禁（让下一个人不必记得）

B 只修了当下这两个文件，**判据没有被固化**——下一个调 `recordCacheBreak`
的测试仍然会踩。三个候选，建议 **C1 + C3**：

- **C1｜哨兵单测**（成本最低，收益直接）。新增
  `tests/telemetry/no-real-path-writes.test.ts`：断言在未设 `SID_CODE_CACHE_BREAKS` 时，
  `cacheBreaksPath()` 返回的路径位于 `sidPaths` 家目录下，
  **并且**扫描 `tests/` 里所有 import 了 `recordCacheBreak` /
  `emitCacheBreakTelemetry` 的文件都出现了 `SID_CODE_CACHE_BREAKS`。
  静态扫描比运行时探测简单可靠，失败信息也直接指到缺隔离的文件。
- **C2｜生产代码侧在测试环境改默认路径**。即 `cacheBreaksPath()` 里判
  `process.env.NODE_ENV === "test"` 就落到 tmpdir。项目里已有这个判据的先例
  （`src/utils/process.ts:39`、`src/debug/logger.ts:295`）。
  但**不推荐作为主方案**：它让生产代码为测试让路，且掩盖了"测试该声明自己的副作用"
  这个真问题；真要做也应作为 C1 之外的兜底。
- **C3｜文档化判据**。把第 2.4 节那条判据写进 `CLAUDE.md` 的测试约定段，
  一句话即可：「调用会写 `~/.sid-code/` 的函数的测试，必须显式重定向到 tmpdir」。

## 四、如何验证

### 4.1 复现现状（做修复前先跑一遍，确认基线）

```bash
# 污染条数与占比
bun -e '
const fs=require("fs");const p=process.env.HOME+"/.sid-code/cache-breaks.jsonl";
const l=fs.readFileSync(p,"utf8").trim().split("\n");
// 判据必须覆盖两种假数据形态：ts===1700000000 与 ts<1e9（测试字面量 1000/2000/3000）
const bad=a=>a.filter(x=>{try{const t=JSON.parse(x).ts;return t===1700000000||t<1e9}catch{return false}}).length;
console.log("总行:",l.length,"| 假数据:",bad(l));
console.log("读侧尾部20条里假数据:",bad(l.slice(-20)),"/20");
'
```

预期（2026-08-03 本机）：`总行: 847 | 假数据: 847`、`读侧尾部20条里假数据: 20 /20`。
即主文件**没有一条真实记录**。

### 4.2 验证 B（隔离生效）—— 关键一步，必须这么测

**核心手法：记录文件行数 → 跑测试 → 再记录 → 比对必须一致。**
只跑 `bun test` 看绿不绿是**验证不了**这件事的（污染时它也全绿）。

```bash
# 1. 修复前后都可用的探针
before=$(wc -l < ~/.sid-code/cache-breaks.jsonl)
bun test tests/api/cache-detection.test.ts tests/command/clear-resets-cache-state.test.ts
after=$(wc -l < ~/.sid-code/cache-breaks.jsonl)
echo "before=$before after=$after"
```

- 修复前：`after > before`（预计多出 70+ 行）——这一步顺便**证明了根因判断是对的**。
- 修复后：`after == before`，且两个测试仍然全绿。

再补一条全量验证（其他测试文件可能有同样问题，一并暴露）：

```bash
before=$(wc -l < ~/.sid-code/cache-breaks.jsonl)
bun test
after=$(wc -l < ~/.sid-code/cache-breaks.jsonl)
echo "before=$before after=$after"   # 期望完全相等
```

### 4.3 验证 A（数据清理）

```bash
# 清理后应该只剩真实记录，且时间戳落在合理区间
bun -e '
const fs=require("fs");const p=process.env.HOME+"/.sid-code/cache-breaks.jsonl";
const l=fs.readFileSync(p,"utf8").trim().split("\n").filter(Boolean);
const ts=l.map(x=>JSON.parse(x).ts).sort((a,b)=>a-b);
console.log("剩余行:",l.length);
console.log("最早:",new Date(ts[0]*1000).toISOString().slice(0,10));
console.log("最晚:",new Date(ts[ts.length-1]*1000).toISOString().slice(0,10));
'
```

期望：无 `1700000000`、无 1970、区间落在项目真实使用期内。

然后跑一次 `/cache --history`（TUI 内），确认明细里的时间戳都是近期的、
归因分布不再是清一色「System prompt 变化」。

### 4.4 验证 C（门禁有效）

反向验证——**故意制造一次违规，确认门禁会红**：

1. 临时把 B 里加的 `beforeAll` 注释掉一个文件的；
2. 跑 C1 的哨兵单测，**必须失败**，且报错信息点名那个文件；
3. 恢复注释，哨兵回绿。

只验「加了门禁后是绿的」不够：那条门禁可能压根没在检查东西。

### 4.5 回归范围

```bash
bun test tests/api tests/telemetry tests/command   # 直接相关
bun test                                            # 全量，确认无连带
make build                                          # 二进制自检
```

### 未修，留判据

**f｜`HookRegistry.initializeFromNew` 是死代码，且与生产路径要求的形状相反。**

- 生产唯一入口是 `src/app.ts:836` → `initializeFromLegacy`，它认**平铺**形状
  （`type`/`matcher`/`command` 同级）。
- `initializeFromNew` 认**嵌套**形状（`{matcher, hooks:[...]}`），
  但 hook 层之外**零调用方**（`grep -ran initializeFromNew src/ | grep -v '^src/hook/'` 为空）。
- 危险点在于：`validateConfig` 的判断与 `initializeFromLegacy` **正好相反**——
  平铺形状在校验器眼里无错、嵌套形状报「必须指定 command 字段」，
  而实际生效的恰恰是平铺。我排查时就因为先测了这个死函数而误判「文档教错了」。
- 另注 `src/agent/agent-hooks.ts:57-68` 读 agent frontmatter 时用的**是嵌套形状**，
  所以两套形状在设计上就并存，不是 bug——但 settings.json 与 frontmatter 不通用这件事
  必须在文档里写清（已在 `extend/hooks.md` 的 danger 框里写了）。
- 建议：删掉 `initializeFromNew` 与 `system.ts` 的包装，或者反过来让它成为唯一入口。
  两条路都行，**并存是最坏的**——它让「照哪个形状写」这个问题有两个互相矛盾的答案。

**g｜`src/app.ts` 含非 UTF-8 字节，`grep` 判定为 binary 后静默不输出。**

- 现象：`grep -c hook src/app.ts` 返回 0，看起来 app.ts 完全不碰 hook。
- 后果：这轮排查里两次误判。一次是「侧信道从未接线」（已记入
  `memory/app-ts-nul-byte-breaks-grep.md`），一次是差点把 15 个未接线事件误判为已接线
  ——app.ts 恰好是主要触发点所在文件。
- 判据：**搜 `src/app.ts` 必须用 `grep -a` 或 `rg`**。搜索结论与 git 历史/直觉冲突时，
  先怀疑工具而不是先怀疑结论。
- 建议：查清那几个 NUL 字节是什么、能不能清掉。清不掉就在 CLAUDE.md 里立规矩。

**h｜`anthropic.ts` 有两条 cache_control 打标路径并存。**

`:171-179` 手写倒序循环找最后一条 user 消息，没走 `cache-strategy.ts` 的
`addMessageCacheBreakpoint`。功能上没错，但同一件事两种写法，
改断点策略时容易只改一处。属可收口的技术债，也是第八节博客的一个观察点。

## 七、与 claude-code 的差异说明

claude-code 的遥测走的是上报到服务端，本地不落这类明细文件，因此**没有对标对象**——
这是 sid-code「数据全部自主、落在自己基础设施里」这个方向自带的成本：
数据在本地，就得自己管好测试与真实数据的边界。

这条差异本身值得写进博客的「数据自主」那一节：自主不是免费的，
它把一类"服务端替你隔离好了"的问题搬回到了本地。

### 8.2 已采集的事实（都已核对到 file:line，可直接用）

**机制：两族协议的分叉，这是文章的骨架**

| 项 | anthropic 族 | openai 族（含 deepseek/glm/kimi） |
| --- | --- | --- |
| 缓存粒度 | content block 级，显式打 `cache_control` | 从 token 0 起的**整体前缀匹配**，不支持分段 |
| 断点数上限 | 4（`src/api/cache-strategy.ts:308` `MAX_CACHE_BREAKPOINTS`） | 无断点概念 |
| 动态内容处置 | 拆 system 静态区/动态区，各打一个断点 | **把动态区搬到消息序列末尾**，包一层 `<system-reminder>` 作独立 user 消息 |
| `cacheCreationInputTokens` | 有值 | 恒 0（`src/llm/openai.ts:78-80`） |

anthropic 族四个断点的位置（流式 / 非流式各打一遍，代码对齐）：

| 断点 | 流式 | 非流式 | 实现 |
| --- | --- | --- | --- |
| system 静态区尾 | `anthropic.ts:207` | `:684` | `buildSystemBlocks` |
| system 动态区尾 | 同上 | 同上 | 同上（有 `DYNAMIC_BOUNDARY` 才拆两块） |
| 工具数组最后一项 | `:215-217` | `:698-699` | `markLastToolCacheBreakpoint` |
| 最后一条 user 消息末块 | `:171-179` | `:686-690` | **手写倒序循环**，没走 `cache-strategy.ts` 的 `addMessageCacheBreakpoint` |

最后一行那个不一致值得在文章里点一句：两条打标路径并存，是可以收口的技术债。

openai 族为什么要把动态区搬到末尾，`src/llm/openai.ts:276-283` 的注释是现成的一手解释
（大意：动态内容留在 `messages[0]` 内部，它一变就让**其后全部历史消息**即使字节未变
也无法复用缓存）。这段是全文最好的「为什么这么设计」素材。

命中读数的三级兜底链（`src/llm/openai.ts:82-87`）：
`prompt_cache_hit_tokens`（DeepSeek 直连）→ `prompt_tokens_details.cached_tokens`
（OpenAI 标准，公司网关归一到这里）→ `cached_tokens`（Kimi 直连）。

### 8.3 待查项（写文章前必须先弄清，否则会写出错的结论）

1. **gpt-5.6-luna 命中率 2.3% 是不是 bug**（⚠ 优先级最高）。
   实测 24 次调用里绝大多数 `cacheHit` 为 0、`cacheWrite` 也为 0，
   只有一条 1812 万 tok 的记录命中了 7563 tok。要查：是这个网关不支持前缀缓存、
   还是它的 usage 字段名不在 `extractOpenAICacheHit` 的三级兜底链里
   （那就是**漏采**而非真的没命中，属于 CLAUDE.md 说的「cost 采集尚不全」的具体一例）。
   `gpt-5.4` 的 18.4% 同源可疑。
2. **`cache-breaks.jsonl` 清理后的真实归因分布**。这是文章「什么操作会打断缓存」
   一节的核心数据，但要等本文档 A 层清理完才拿得到干净数据——**这是本文档与博客的依赖关系**。
3. **JIT 注入与 prompt cache 的冲突**。`blog/jit-context.md` 提过一句，
   源码依据在 `docs/bugfixes/done/20260731-上下文JIT机制...md:1030`：
   「OpenAI 族这条消息在 messages 末尾，每次 JIT 注入都改写它 → 该位置之后的前缀在本轮断裂」，
   并明确「§10.1 的『安全』只对 Anthropic 族完整成立」。这是现成的「边界照实写」素材。
4. **影子调用绕过埋点的具体路径**。CLAUDE.md 说 cost 采集不全的原因是这个，
   需要定位到是哪几条调用链没走 usage-ledger 埋点。子代理这轮**没查出来，属无数据**。
