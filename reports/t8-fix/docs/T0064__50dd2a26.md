# Skills 系统：对齐 claude-code §18 的缺口修复与实现方案

> 对照《claude-code 深度研究文档》§18「Skills 系统」全章（18.1 概述 → 18.10 插件系统），
> 逐条核对 sid-code 现有实现，参考 `/Users/zhourusheng/Code/person/claude-code/src`（CC 3.31 泄漏源码）。
> 目标：弥补全部缺口，实现高性能、稳定、可运行的完整 Skills 体系，对齐 CC 并在若干维度超越 CC。
>
> **本文只写方案，不改代码。**

## 0. 这篇文档讲什么

sid-code 的 Skills **frontmatter 解析层和两条调用路径（模型 / 用户 `/`）已基本对齐 CC**，变量替换管道（`$ARGUMENTS`/`$1`/`${SKILL_DIR}`/`!` shell）、listing 预算（250 字符/条 + 1% 上下文窗口）、context: fork/inline 子代理执行等都实现了。

但对照检查发现**三类系统性问题**：

1. **架构级偏差（1 处）**：CC 用**单一 `Skill` 元工具**（按名字分发 + 增量 listing 注入），sid-code 用**每个 skill 一个 `skill__<name>` 独立工具**，导致工具池膨胀（靠 `MAX_SKILLS=50` 硬顶）+ 与 skill 摘要列表**信息重复**，且原设计的"两层发现（摘要常驻 + 工具按需调出）"因 skill 工具未声明 `shouldDefer` 而**从未生效**。

2. **写了但没接线的死模块（6 个）**：`conditional.ts`（条件激活）、`dynamic-discovery.ts`（动态发现）、`change-detector.ts`（热重载）、`hooks.ts`（skill 生命周期 hook）、`permission.ts`（skill 权限）、`mcp/skill-discovery.ts`（MCP skill 发现）——这 6 个模块**除自己的测试文件外，`src/` 里零引用**。字段（`paths`/`hooks`/`effort`/`agent`）在 `loader.ts` 老实解析进了 `SkillDefinition`，但下游无任何代码消费——**解析 ≠ 生效**。

3. **字段/机制缺口（若干）**：`effort`/`agent` 解析了但 delegate 不消费；`when_to_use`（下划线）不识别；CC 的 `${CLAUDE_SKILL_DIR}`/`${CLAUDE_SESSION_ID}` 变量名失配；plugin 的 `skillsPaths` 解析了但**无 loader 消费**（插件带的 skills 加载不进来）；存储位置缺企业 managed 层。

### 修复优先级总览

| 优先级 | 项 | 主题 | 影响面 |
|--------|----|------|--------|
| **P0-1** | 单一 `Skill` 元工具重构（或让 `skill__*` 真正 defer） | 架构/成本 | 消除工具膨胀 + listing 信息重复 |
| **P0-2** | 接线 skill 生命周期 hooks（`hooks.ts` 死代码激活） | 正确性 | §18.10 frontmatter hooks 完全不生效 |
| **P0-3** | 接线 skill 权限判定（`permission.ts` 死代码激活） | 安全 | §18.6 安全模型未接入调用路径 |
| **P0-4** | 补 plugin skills 加载（`loadPluginSkills.ts` 缺失） | 能力 | §18.10 插件带的 skills 加载不进来 |
| **P1-1** | delegate 消费 `effort` + `agent`（agentType） | 能力 | 字段写了不起作用 |
| **P1-2** | 接线条件激活 skill（`conditional.ts` + `paths`） | 对齐 | §18.10 文件触发正解 |
| **P1-3** | 变量名/字段兼容（`when_to_use` / `${CLAUDE_SKILL_DIR}` / `${CLAUDE_SESSION_ID}`） | 迁移保真 | 从 CC 迁移的 skill 静默失配 |
| **P2-1** | 补企业 managed skills 层（enterprise > user > project） | 层级 | 企业统一下发/锁定 |
| **P2-2** | 接线动态发现 `dynamic-discovery.ts` | 对齐 | 深层子目录 skill 按需发现 |

| **P3-1** | `argument-hint` 语义修正（勿塞进模型入参 description） | 语义 | 近零成本 |
| **P3-2** | listing 增量注入（按 agentId 跟踪 `sentSkillNames`） | 成本 | 减少每轮重复注入 |

## 1. 架构级偏差 —— 元工具机制

### P0-1　单一 `Skill` 元工具重构（核心架构对齐）

**现状（缺口）**：`src/cli.ts:973-983` 对每个 skill 注册一个独立工具：

```ts
for (const skill of skills) {
  if (!skill.disableModelInvocation) {
    toolRegistry.register(new SkillTool(skill, providerRegistry, toolRegistry)); // skill__<name>
  }
  if (skill.userInvocable !== false) {
    commandRegistry.register(new SkillCommand(skill), "user");
  }
}
```

`SkillTool.name()` 返回 `skill__${this.skill.name}`（`tool.ts:52-54`），每个工具带自己的 `description()`。同时 `src/query/init-helpers.ts:318` 又通过 `collectSkillListingEntries(tools)` 把 skill 摘要注入 system prompt（`generateSkillListingAttachment` → `budget.ts`）。

**问题三连**：
1. **工具池膨胀**：N 个 skill = N 个工具定义常驻首轮上下文。`loader.ts:27` 的 `MAX_SKILLS=50` 硬顶正是为了压制这个膨胀——而 CC 用单一元工具从根上免疫，无需上限。
2. **信息重复**：既注册了 N 个 `skill__*` 工具（每个含完整 description + whenToUse），又额外注入了一份 skill 摘要列表。同一份"有哪些 skill、何时用"的信息进了两次上下文。
3. **两层发现失效**：`tool.ts:64-79` 的 `getListingEntry` 注释声称实现了"摘要常驻发现 + 工具按需调出（skill 工具被 defer 时仍能发现）"。但实测 `src/tool/registry.ts:309-322` 的 `isToolDeferred` **只对 `mcp__` 前缀和运行时 `deferredTools` 名单 defer**；`skill__*` 工具**没有声明 `shouldDefer`**，默认全部首轮可见。所以"按需调出"从未发生——skill 工具本就都在首轮，摘要纯属冗余。

**CC 做法**（`tools/SkillTool/SkillTool.ts`，`constants.ts`，`prompt.ts`）：
- 全局**只有一个**工具 `Skill`（`SKILL_TOOL_NAME='Skill'`）。
- input_schema = `{ skill: string, args?: string }`（`SkillTool.ts:291-298`），按名字分发。
- 工具静态 `prompt`（长描述，`prompt.ts:173-196`）开头即 `"Execute a skill within the main conversation"`，告诉模型"可用 skill 列在 system-reminder 里"，含 BLOCKING REQUIREMENT 措辞。**工具 description 不打包 skill 列表**。
- skill 清单通过独立的 `skill_listing` system-reminder **增量注入**（`attachments.ts:2660-2751`，按 agentId 用 `sentSkillNames` 跟踪只发新增，`messages.ts:3728-3739` 渲染成 `The following skills are available for use with the Skill tool:\n\n${content}`）。

**实施方案**（两条路线，推荐 A）：

**路线 A（推荐，彻底对齐）——改单一 `Skill` 元工具**：
1. 新建 `src/skill/meta-tool.ts`，实现单一 `SkillMetaTool implements Tool`：
   - `name()` 返回 `"Skill"`（或保留 sid 风格 `skill`，但需全链统一）。
   - `zodSchema = z.object({ skill: z.string(), args: z.string().optional() })`。
   - `description()` 返回静态说明文（"Execute a skill by name. Available skills are listed in system-reminder."），**不含 skill 列表**。
   - `execute({ skill, args })`：从注入的 `SkillManager` 按名解析 `SkillDefinition`，校验 `!disableModelInvocation`（命中则返回错误，对齐 CC `SkillTool.ts:411-418` 的 errorCode 4），再按 `context`/`mode` 走 `executeActivate`/`executeDelegate`（复用现有 `tool.ts` 的两个私有方法，抽成共享函数）。
2. `cli.ts` 注册改为**一次性注册 `SkillMetaTool`**，删除 per-skill `SkillTool`/`BundledSkillTool` 循环注册。元工具持有 `SkillManager` + bundled skill registry 引用做分发。
3. skill 摘要 listing 保留（`generateSkillListingAttachment`），此时它是模型发现 skill 的**唯一**入口，不再与工具 description 重复。
4. `MAX_SKILLS=50` 硬顶可放宽或移除（膨胀问题消失后，上限只需防御异常大目录，可提到如 500 并加日志）。
5. UI 侧 `src/ui/ToolStatus.tsx:51` / `ui-utils.ts:47,79` 的 `skill__` 前缀识别改为识别单一 `Skill` 工具 + 从 `args.skill` 取子 skill 名做展示。

**路线 B（保守，最小改动）——让 `skill__*` 真正 defer**：
1. 给 `SkillTool` / `BundledSkillTool` 增加 `shouldDefer = true`（除非 skill 显式 `alwaysLoad`）。
2. 这样首轮上下文只有 skill 摘要 listing，模型经 tool_search 按名激活 `skill__<name>` 才进上下文——"两层发现"真正生效。
3. 缺点：仍是 N 个工具（只是延迟），tool_search 往返有延迟；未根除信息模型（listing 与被激活工具的 description 仍会各出现一次）。

**推荐 A**：一次性消除膨胀 + 重复 + 让 listing 成为单一真相源，架构与 CC 完全对齐。改动面 `cli.ts`（注册）、`config/system-prompt.ts`（注入不变）、`tool/registry.ts`（无需 skill 特判）、`ui/*`（展示）四处，收敛清晰。

**验收标准**：
- 工具列表中只有 1 个 `Skill`（或 `skill`）工具，不随 skill 数量增长。
- 模型能按 `{skill:"code-review", args:"..."}` 正确分发到对应 skill 执行。
- `disableModelInvocation:true` 的 skill 经元工具调用被拒（返回明确错误），但仍在用户 `/` 列表。
- skill 摘要 listing 仍注入 system prompt，且不与任何工具 description 重复。
- `bun test` 覆盖：分发正确性、disableModelInvocation 拦截、未知 skill 名报错、activate/delegate 两模式；`make rebuild` + `sc-dev` 手工验证工具数不膨胀。

## 2. 死模块接线（写了却从未在生产调用）

> 用 `grep -rln "skill/<模块>"` 确认：以下模块除自己的测试文件外，`src/` 里零引用。字段 `loader.ts` 都解析了，但无消费者。

### P0-2　接线 skill 生命周期 hooks（`hooks.ts` 死代码激活）

**现状（缺口）**：`src/skill/hooks.ts` 的 `registerSkillHooks` / `unregisterSkillHooks` **只有 `tests/skill/hooks.test.ts` 调用**。`loader.ts:145-148` 解析了 frontmatter 的 `hooks` 字段存进 `SkillDefinition.hooks`，但 skill 被调用时**并不注册它声明的 hooks**——§18.10「Skill 通过 Hook 自动激活」在 sid-code 完全不生效。

**CC 做法**（`utils/hooks/registerSkillHooks.ts:20-64`）：skill 被调用时把其 frontmatter hooks 注册为 **session 作用域 hook**（`addSessionHook`），遍历 `HOOK_EVENTS`；支持 `once:true` 一次性 hook（执行后 `removeSessionHook` 自动移除）；`skillRoot` 作为 `CLAUDE_PLUGIN_ROOT` env 传入。

**实施方案**：
1. 在 skill **调用入口**接线 hooks 注册。因为 skill 有两条调用路径，需两处都接：
   - 模型路径：`SkillTool.execute`（路线 A 后是 `SkillMetaTool.execute`）在执行 skill 前，若 `skill.hooks` 非空且 `hookSystem` 可用，调 `registerSkillHooks(hookSystem, skill.name, skill.hooks, skill.skillRoot)`。
   - 用户路径：`SkillCommand.execute`（`src/command/skill-command.ts`）同理。
2. **hookSystem 注入**：`SkillTool`/`SkillMetaTool` 需持有 `hookSystem` 引用。注意 [[subagent-hook-wiring-order-rootcause]] 的教训——工具在 `cli.ts` 注册早于 `HookSystem` 创建，直接构造时传会拿到 `undefined`。**必须走 setter 回填**（仿 `app.ts` 的 `wireToolHookSystem` / `setPermissionChecker` 套路），在 HookSystem 就绪后回填进 skill 工具。
3. **生命周期与卸载**：skill hooks 是 session 作用域。inline skill 注入后长期存活，hooks 应持续到会话结束；delegate skill 在子代理内执行，hooks 作用域需限定在该子代理生命周期（子代理有独立 hookSystem 时注册到子代理的，否则注册到主的并在 delegate 返回后 `unregisterSkillHooks`）。**决策点**：delegate skill 的 hooks 默认注册到子代理 hookSystem（隔离更干净），文档需明确这一语义。
4. `once:true` 语义：复用 `hookSystem.registerSessionHook` 已支持的 `once` 选项（`hooks.ts:80-82` 已传 `once`），确认 HookSystem 侧执行后真的移除。
5. **安全**：MCP 来源 skill（`loadedFrom="mcp"`）**禁止注册 hooks**（远程来源不可信，能执行任意 shell）。在 `registerSkillHooks` 入口加 `loadedFrom` 判断，MCP 直接跳过并告警。

**验收标准**：
- 带 `hooks: { PostToolUse: [{matcher:"write", hooks:[{command:"..."}]}] }` 的 skill 被调用后，对应 hook 真的在后续工具调用时触发。
- `once:true` hook 执行一次后自动移除。
- MCP skill 的 hooks 被拒绝注册 + 告警。
- delegate skill 返回后其 hooks 不泄漏到主会话（按上述作用域决策）。
- `bun test` 覆盖注册/触发/once/MCP 拒绝/卸载；`sc-dev` 手工验证。

### P0-3　接线 skill 权限判定（`permission.ts` 死代码激活）

**现状（缺口）**：`src/skill/permission.ts` 的 `checkSkillPermission` / `skillHasOnlySafeProperties` **只有 `tests/skill/permission-mcp.test.ts` 调用**。实际 skill 调用**不走这套 allow/deny/ask + 安全属性白名单 + MCP 隔离**判定。§18.6 的安全模型形同虚设。

**CC 做法**：skill 调用有 permission 校验（`SkillTool.ts` 的 `validateInput` + permission 层），带敏感属性（hooks/allowedTools 等）的 skill 需审批，MCP 来源更保守。

**实施方案**：
1. 在 skill **执行前**接入 `checkSkillPermission`：
   - `SkillMetaTool.execute` / `SkillCommand.execute` 在真正 spawn 子代理 / 注入 prompt 前，调 `checkSkillPermission(skill, rules)` 得到 `allow|deny|ask`。
   - `deny` → 直接返回拒绝错误。
   - `ask` → 走现有 PermissionChecker 的 ask 通道（弹审批 UI）；用户拒绝则中止。
   - `allow` → 放行。
2. **规则来源**：`SkillPermissionRules`（`deny`/`allow` 列表）从配置读取。需在 config schema 加 `skillPermissions?: { allow?: string[]; deny?: string[] }`，或复用现有 `permissions` 结构加 `Skill(<name>)` 规则形态（对齐 CC 的 `permissions.allow/deny` 里可写 skill 规则）。**推荐后者**——统一权限入口，避免 skill 单开一套配置。
3. **安全默认对齐**：`permission.ts:20-40` 的 `SAFE_SKILL_PROPERTIES` 白名单已实现"未来新增属性默认需审批"的安全默认——这点比 CC 更严谨，保留。但需确认白名单覆盖当前所有安全字段（新增字段时同步更新白名单，否则误判为需审批）。
4. **与 hooks 注册的顺序**：先权限判定（deny/ask），通过后再注册 hooks + 执行。避免被 deny 的 skill 已经注册了 hooks。

**验收标准**：
- `permissions.deny` 含某 skill → 调用被拒。
- 带 hooks/allowedTools 的 skill 默认触发 ask（除非 allow 命中）。
- MCP skill 带敏感属性 → 一律 ask（不享受白名单自动放行）。
- 仅安全属性的 skill → 自动 allow。
- `bun test` 覆盖 deny/allow/ask/MCP 隔离/安全默认；`sc-dev` 手工验证审批弹窗。

### P0-4　补 plugin skills 加载（`loadPluginSkills.ts` 缺失）

**现状（缺口）**：`src/plugin/manifest.ts:109` 把插件的 `skills/` 目录解析进了 `skillsPaths`，`command/plugin.ts:121` 也显示"Skill(N 目录)"，但**没有任何 loader 从 `skillsPaths` 加载 skill**。插件系统有 `loadPluginCommands.ts` / `loadPluginAgents.ts` / `loadPluginHooks.ts` / `loadPluginMcp.ts`，**唯独缺 `loadPluginSkills.ts`**。`SkillManager.discover` 不接收插件目录，`unified-registry` 的 `loadSkillCommands` 也只扫 user/project。

**结论**：§18.10 插件系统的实打实缺口——**插件带的 skills 加载不进来**。

**CC 做法**：插件 skills 走 skill 加载链，命名空间 `plugin-name:skill-name` 隔离。

**实施方案**：
1. 新建 `src/plugin/loadPluginSkills.ts`，仿 `loadPluginCommands.ts`：
   - 遍历已加载插件的 `skillsPaths`，对每个目录扫 `<skill-name>/SKILL.md`（复用 `SkillLoader.buildSkillDefinition` 逻辑）。
   - skill 名加插件命名空间前缀 `pluginName:skillName`（对齐 CC + 现有 command 命名空间规则）。
   - `source` 标为插件来源，`loadedFrom` 需新增枚举值或复用 `"skills"`（建议 `SkillLoadedFrom` 加 `"plugin"`）。
2. **接入主 skill 系统**：
   - `SkillManager.discover` 增加可选入参 `pluginSkillDirs: string[]`，在 builtin/user/project 之后加载插件 skills（优先级：插件 skill 不覆盖同名内置/用户 skill，但命名空间前缀天然避免冲突）。
   - `unified-registry` 的 `loadSkillCommands` 同步纳入插件 skills（用户 `/plugin:skill` 路径）。
   - 元工具（P0-1 后）分发时能按 `pluginName:skillName` 解析。
3. **命名空间隔离**：确认插件 skill 名带前缀后，`sanitizeName`（`loader.ts:183`）不会把 `:` 替换掉——当前 `sanitizeName` 会把 `:` 替成 `-`（`/[:\\/<>*?"|]/g`）！**这会破坏命名空间**。需给插件 skill 走单独的名称规则（允许 `pluginName:skillName` 形态），或在拼前缀后跳过 sanitize。
4. **热重载/刷新**：`src/plugin/refresh.ts` 的 `reloadPlugins` 需同步刷新插件 skills。

**验收标准**：
- 装一个带 `skills/` 目录的插件，其 skill 出现在模型 listing + 用户 `/plugin:skill` 列表，可调用。
- 命名空间前缀不被 sanitize 破坏。
- 卸载插件后其 skills 消失。
- 插件 skill 与同名用户 skill 靠命名空间共存不冲突。
- `bun test` 覆盖加载/命名空间/卸载；`sc-dev` 手工验证。

## 3. 字段/机制缺口

### P1-1　delegate 消费 `effort` + `agent`（agentType）

**现状（缺口）**：`loader.ts:170-172` 解析了 `effort`、`agent`、`shell` 进 `SkillDefinition`，但：
- `SkillTool.executeDelegate`（`tool.ts:200-208`）调 `subAgent.executeCustom` 时**只传 `type`，没传 `effort`**；`agent`（agentType）完全没用。
- `SkillCommand.executeFork`（`skill-command.ts:88-95`）同样没传 `effort`/`agent`。
- 而 `sub-agent.ts:107` 的 `executeCustom` **明明支持 `effort`**，`agentType`（`sub-agent.ts:165`）也支持。

**结论**：skill 写了 `effort: high` / `agent: xxx` 不起作用。

**CC 做法**（`SkillTool.ts:209-212`）：fork 时把 `effort`/`agent` 合并进 forked agent definition。

**实施方案**：
1. `executeDelegate` / `executeFork` 调 `executeCustom` 时透传：
   ```ts
   await subAgent.executeCustom({
     ...,
     effort: this.skill.effort,          // 新增透传
     agentType: this.skill.agent,        // 新增：以 skill.agent 覆盖 agent 类型
     type: this.skill.agent ?? `skill:${this.skill.name}`,  // agent 优先，否则沿用 skill: 前缀
   });
   ```

### P1-2　接线条件激活 skill（`conditional.ts` + `paths`）

**实施方案**：

5. **glob 匹配**：`conditional.ts` 用 `Bun.Glob` + 正则回退，已实现。确认与 CC `ignore` 库的 gitignore 语义足够接近（`**`/`*`/`?`），差异记入文档。

**验收标准**：
- 带 `paths: ["src/**/*.ts"]` 的 skill 启动时不在初始 listing。

### P2-1　补企业 managed skills 层

## 5. 语义与成本细节

### P3-1　`argument-hint` 语义修正

**现状（缺口）**：`tool.ts:24-28` 的 `buildSkillSchema` 把 `skill.argumentHint` 塞进了模型工具 `input` 参数的 `.describe()`。但 `argument-hint` 语义是给**用户 slash 补全**看的提示（CC 定位一致，`frontmatterParser.ts:19`），不是模型入参说明。

**实施方案**：
- 路线 A（元工具）后，元工具的 `args` 参数 description 用通用说明，不塞 argumentHint。
- `argument-hint` 只用于用户 `/` 补全提示（`SkillCommand` / UnifiedCommand 的 `argumentHint` 字段，已正确使用于 `command-adapter.ts:28`）。
- 影响小，随 P0-1 一并处理。

### P3-2　listing 增量注入（按 agentId 跟踪 `sentSkillNames`）

**现状（缺口）**：`generateSkillListingAttachment` 每次构建 system prompt 都注入**全量** skill 摘要。CC 是增量注入——按 agentId 用 `sentSkillNames` 跟踪已发送，只注入新增 skill（`attachments.ts:2698-2726`）。

**实施方案**：
1. 维护 per-session（或 per-agentId）的 `sentSkillNames: Set<string>`。
2. 每轮构建 listing 时只包含未发送过的 skill（首轮全量，后续只增量）。条件激活（P1-2）/ 动态发现（P2-2）新激活的 skill 走这个增量通道注入。
3. **配合 prompt cache**：注意 [[prompt-cache-advanced-opt-review]] 的教训——system prompt 变动会击穿 cache。增量注入应放在**非 cache 前缀区**（如动态 reminder 区），避免每次新增 skill 就让整个 system prompt cache 失效。这是比"每轮全量"更优、且 cache 友好的做法。

**验收标准**：
- 首轮注入全部可用 skill 摘要。
- 后续轮次只注入新激活的 skill，不重复已发送的。
- 增量注入不击穿 system prompt 的 cache 前缀。
- `bun test` 覆盖首轮全量 + 增量 + 去重。
