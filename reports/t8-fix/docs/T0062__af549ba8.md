## 0. 这篇文档讲什么

这是对 sid-code **CLI 命令与参数层**的一次系统性对照审计的**执行方案**。我们把 CC 研究文档 §5 的每一项启动命令、每一个 CLI 参数，逐条对到 sid-code 源码，找出所有偏差、缺口、遗漏，按严重程度排序，给出可落地的实施步骤。

**核心结论先行**：sid-code 的 CLI 参数**基础面已对齐**（会话/无头/模型/权限/system-prompt/输出格式主干都在），但**缺口集中且数量可观**——共 **4 个 P0 + 10 个 P1 + 6 个 P2 + 4 项架构性缺失**。绝大多数 P0/P1 缺口的**底层能力/配置字段已经存在**，只是**缺少 CLI 入口接线**（典型如 `--effort`、`--fallback-model`、`--session-id`、`--add-dir`），属于低风险、高价值的补齐。

每一条论断都带 `file:line` 证据。

## 2. P0 —— 会话与模型行为，刚需且低风险

### P0-1　`--session-id <uuid>`

**缺口**
`config.sessionId` 字段完备（`config.ts:162`），`loadConfig` 收尾会自动生成（`config.ts:1113-1115`），但**没有任何 CLI flag 允许用户/SDK 显式指定会话 UUID**。CC 用它做 SDK 幂等、外部编排复现、多进程协调（`main.tsx:1003`）。

**CC 语义**（`main.tsx:1279-1282`）
- `--session-id <uuid>` 必须是合法 UUID。
- **组合约束**：`--session-id` 只能单独用于全新会话；若与 `--continue`/`--resume` 同用，**必须**同时带 `--fork-session`（否则报错退出）。即"指定 ID 恢复"本质是"分叉到新 ID"。

**实施步骤**
1. `cli.ts:131` `parseArgs.options` 加 `"session-id": { type: "string" }`。
2. `cliConfig`（`cli.ts:224`）映射 `sessionId: values["session-id"]`（若提供）。
3. **UUID 校验**：在映射处校验格式（`/^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i`），非法则 `console.error` + `process.exit(1)`，文案对齐 CC。
4. **组合约束**：若同时存在 `--session-id` 且（`--continue` 或 `--resume`）且**无** `--fork-session` → 报错退出（依赖 P0-2 落地）。
5. `config.ts:1113` 的自动生成分支保持不变（用户未指定时兜底）；用户指定时跳过生成。
6. `help.ts` 会话配置段补一行。

**验证**：`sid-code --session-id "非法" -p "x"` 报错；`sid-code --session-id <合法uuid> -p "x"` 后 `--list-sessions` 能看到该 id；`sid-code --session-id <id> -c` 无 `--fork-session` 时报错。

### P0-2　`--fork-session`

**缺口**
完全缺失。CC 用于"恢复会话时不复用原 ID，而是分叉出新 ID"（`main.tsx:1001`），配合 `--session-id` 或 `--resume`/`--continue` 使用。CC 的会话恢复逻辑对此有专门分支（`sessionRestore.ts:435,453`：默认复用原 ID，`--fork-session` 保留启动时的新 ID 并剥离 `srcUUID`）。

**实施步骤**
1. `cli.ts` `parseArgs` 加 `"fork-session": { type: "boolean" }`。
2. `config.ts` 新增字段 `forkSession?: boolean`（默认 undefined/false）。
3. `cliConfig` 映射 `forkSession: values["fork-session"]`。
4. **恢复逻辑接线**（关键）：定位我们的会话恢复入口（`session/` 目录 + `cli.ts:1387` 附近 resume 分支）。当前恢复默认复用被恢复会话的 id；改为：
   - 无 `--fork-session`：维持现状（复用原 id，续接同一会话）。
   - 有 `--fork-session`：生成新 id（或用 `--session-id` 指定的），把被恢复会话的消息历史**拷贝**到新会话，`parentUuid` 指向源会话，源会话保持不动。
5. `help.ts` 补一行，标注"与 `--resume`/`--continue` 组合使用"。

**验证**：`sid-code -r <id> --fork-session -p "x"`，恢复后 `--list-sessions` 出现**新** id，原 id 仍在且历史未被追加。

**风险提示**：这一项涉及会话存储层，需读懂 `session/` 的持久化格式。建议**先落 P0-1 的 flag 声明+校验**，fork 的存储改造作为紧随其后的独立小步，避免一次改动跨越 parse 层与存储层。

### P0-3　`--effort <level>`

**缺口**
文档 §5.2 明确列出 `--effort xhigh`（low/medium/high/xhigh/max）。我们有 `/effort` 斜杠命令、`effortLevel` 配置字段（`config.ts:142`）、`SID_CODE_EFFORT_LEVEL` 环境变量、`src/llm/effort.ts` 完整消费链路——**唯独没有启动 flag**。这是最"该有却没有"的一项。

**注意档位差异**：我们 `config.ts:142` 声明的是 `"low" | "medium" | "high" | "max"`（四档），CC 文档是 `low/medium/high/xhigh/max`（五档，多一个 `xhigh`）。

**实施步骤**
1. `cli.ts` `parseArgs` 加 `effort: { type: "string" }`。
2. `cliConfig` 映射 `effortLevel: values.effort`（注意字段名映射：flag 是 `effort`，config 字段是 `effortLevel`）。
3. **档位校验 + 对齐五档**：
   - 决策点：是否引入 `xhigh`。建议**引入**（对齐 CC，且 `xhigh` 在 max 之下是合理的中间档），把 `config.ts:142` 的联合类型扩为 `"low" | "medium" | "high" | "xhigh" | "max"`。
   - 需同步排查 `src/llm/effort.ts`、`model-params-catalog.ts`、`model-capability-filter.ts` 中对 effort 档位的映射表，确保 `xhigh` 有对应的 thinking budget / 参数。若 `xhigh` 映射工作量大，**可先只接 flag 支持现有四档，`xhigh` 作为紧随的增量**（避免阻塞主线接线）。
4. 校验非法档位 → 报错退出。
5. **优先级**：CLI flag > env(`SID_CODE_EFFORT_LEVEL`) > settings.json(`effortLevel`)。确认 `loadConfig` 的合并顺序符合此优先级（CLI 覆盖 env 覆盖文件）。
6. `help.ts` 模型配置段补一行。

**验证**：`sid-code --effort max -p "x" --verbose` 观察实际发出的 thinking budget/参数与 max 档一致；`--effort 乱填` 报错。

### P0-4　`--fallback-model <model>`

**缺口**
`config.fallbackModel` 字段在（`config.ts:109`），`ModelFallback.setFallbackTarget` 运行时能力在（记忆 `model-command-persistence-and-subswitch.md` 有记录），但**只能配 settings.json**，无 CLI flag。CC 用于"默认模型过载时自动降级"（`main.tsx:1000`，标注 only works with `--print`）。

**实施步骤**
1. `cli.ts` `parseArgs` 加 `"fallback-model": { type: "string" }`。
2. `cliConfig` 映射 `fallbackModel: values["fallback-model"]`（覆盖 settings.json 值）。
3. 确认 `ModelFallback` 在启动时读取 `config.fallbackModel` 初始化降级目标（若目前只从 settings.json 读，需补一条从 config 读的路径）。

5. `help.ts` 模型配置段补一行。

**验证**：`sid-code --fallback-model deepseek-v4-pro -p "x"`，构造主模型过载场景（或单测 mock 429/overloaded），断言自动切到 fallback。

## 3. P1 —— 高价值功能缺口

### P1-1　`--add-dir <dirs...>`

**缺口**
`/add-dir` 斜杠命令在（`command/permissions.ts:144-196`），`config.allowedDirectories` 字段+`path-validator` 运行时入口都在（`path-validator.ts:387` 注释明说"给 /add-dir 用"），但**无启动 flag**。CC 用于启动即给工具授权额外工作目录（`main.tsx:1002`，多值 `<directories...>`）。

**实施步骤**
1. `cli.ts` `parseArgs` 加 `"add-dir": { type: "string", multiple: true }`（多值，对齐 CC 的 `<directories...>`）。
2. `cliConfig` 映射：把 `values["add-dir"]` 数组**并入** `config.allowedDirectories`（注意是追加而非覆盖——用户可能同时在 settings.json 配了目录）。
3. **路径归一化**：对每个目录做 `resolve()` + 存在性校验（不存在给 warning 但不阻塞，对齐 `/add-dir` 斜杠命令的宽容行为）。
4. 确认 `PathValidator` 构造时（`checker.ts:254`）读取到合并后的 `allowedDirectories`。
5. `help.ts` 权限配置段补一行。

**验证**：`sid-code --add-dir ../lib --add-dir ../shared -p "read ../lib/x.ts"`，断言工具能访问这两个目录，未加的目录仍被拦。

### P1-2　`--no-session-persistence`

**缺口**
完全缺失。CC 用于 `-p` 模式下不落盘会话（`main.tsx:991`），场景：CI/临时查询不想污染会话历史。CC 有 print-only 约束（`main.tsx:1855-1857`：非 print 模式用会报错）。

**实施步骤**
1. `cli.ts` `parseArgs` 加 `"session-persistence": { type: "boolean" }`（配合 `allowNegative: true`，`--no-session-persistence` 会解析为 `false`）。**注意**：我们已开 `allowNegative`（`cli.ts:198`），所以声明正向 key 即可自动支持 `--no-` 前缀。
2. `config.ts` 新增字段 `sessionPersistence?: boolean`（默认 true）。
3. `cliConfig` 映射 `sessionPersistence: values["session-persistence"]`。
4. **print-only 校验**：若 `--no-session-persistence` 且非 `--print` → 报错退出（对齐 CC `main.tsx:1857`）。
5. **落盘门控接线**：定位会话写盘点（`session/` 存储 + `cli.ts:1248-1264` registerSession/写会话文件处），当 `sessionPersistence === false` 时跳过所有落盘（registerSession、消息持久化、SessionEnd 写文件）。
6. `help.ts` 会话配置段补一行，标注 print-only。

**验证**：`sid-code -p --no-session-persistence "x"`，跑完后 `--list-sessions` 无新增；`sid-code --no-session-persistence`（无 -p）报错。

### P1-3　`--allow-dangerously-skip-permissions`

**缺口**
我们有 `--dangerously-skip-permissions`（直接跳过所有权限），但缺 CC 的 `--allow-dangerously-skip-permissions`——它是"**启用**该跳过选项作为可能性，但默认不开"（`main.tsx`，与 `--permission-mode` 组合）。两者语义不同：前者立即生效，后者只是"解锁"让用户在会话内可切到 bypass 模式。

**CC 语义**：`--allow-dangerously-skip-permissions` 让 bypassPermissions 模式**可被启用**但不默认启用；配合 `--permission-mode` 使用。（对应记忆里提到的 `disableBypassPermissionsMode` 的反向开关。）

**实施步骤**
1. `cli.ts` `parseArgs` 加 `"allow-dangerously-skip-permissions": { type: "boolean" }`。
2. `config.ts` 新增字段 `allowDangerouslySkipPermissions?: boolean`。
3. `cliConfig` 映射。
4. **权限层接线**：定位权限模式切换逻辑（`permission/checker.ts` + 权限模式状态）。当前若用户想进 bypass 模式，路径是什么？需确认：
   - 有此 flag → 允许运行时（交互式 `/permissions` 或模式切换）切到 bypass 模式。
   - 无此 flag → bypass 模式不可达（除非直接 `--dangerously-skip-permissions` 一步到位）。
5. `help.ts` 权限段补一行，讲清与 `--dangerously-skip-permissions` 的区别。

**验证**：确认两个 flag 语义可区分——`--allow-...` 只解锁不生效，`--dangerously-...` 直接生效。

**注意**：本项与权限系统深度耦合，且记忆 `permission-hitl-dead-code-and-gaps.md` 指出权限动态层大面积未接线。建议**与权限系统 §7 的缺口修复合并规划**，此处只登记 CLI 层缺口。

### P1-4　`--append-system-prompt-file <path>`

**缺口**

## 5. 架构性缺失（需独立评估，部分依赖不具备的能力）

### A-1　`auth` 子命令（login/logout/status）
CC `claude auth login --email ... --sso` / `logout` / `status`（文档 §5.1）。依赖 **Anthropic 账户体系 + OAuth**（CC `main.tsx` 有完整 OAuth 流程）。sid-code 走 API key + 公司网关，**无账户登录概念**。
**结论**：不直接对齐。若要"超越"，可做一个 `sid-code auth status` 打印当前 provider/key 来源/网关连通性检测（诊断价值），但 login/logout 无对应语义。**标记为不适用，除非引入账户体系**。

### A-2　`agents` 子命令（列出所有配置的子代理）
CC `claude agents`（文档 §5.1，`main.tsx:4282` 有实现，支持 `--setting-sources`）。
**结论**：**可做且低成本**。我们有 `BUILTIN_AGENTS` + `subAgentModels`，加一个 bootstrap 快速路径 `if (args[0] === "agents")`，枚举内置 + 自定义子代理（名称/描述/模型）打印即可。建议纳入本轮实施。

### A-3　`mcp` CLI 子命令
CC `claude mcp`（文档 §5.1，管理 MCP 服务器）。我们有 `command/mcp-enhanced.ts`（list/add/remove/enable/disable/test）**但仅作 TUI 内斜杠命令**，无 `sid-code mcp ...` 命令行入口。
**结论**：**可做且低成本**。加 bootstrap 快速路径 `if (args[0] === "mcp")`，复用 `mcp-enhanced.ts` 的逻辑（它已经是子命令式 list/add/remove），做一层 CLI 参数适配即可。建议纳入本轮实施。

### A-4　`--chrome` / `--no-chrome` / `--remote` / `--ide` / `--init` / `--init-only` / `--maintenance`
- `--chrome`/`--no-chrome`：Claude in Chrome 集成，依赖浏览器扩展 + CC 专有协议。**不具备**。
- `--remote`：创建 claude.ai 远程会话，依赖 claude.ai 后端。**不具备**（我们有 `--bridge` 是自建远程控制，语义相近但非对齐）。
- `--ide`：自动连接 IDE。我们有 `SID_CODE_AUTO_CONNECT_IDE` env + `src/ide/integration.ts`，**可补一个 `--ide` flag 作为 env 的 CLI 等价物**（低成本，建议做）。
- `--init` / `--init-only` / `--maintenance`：运行 Setup hooks 的不同触发器（startup/init/maintenance）。依赖我们的 hook 系统是否有 "Setup" 事件 + trigger 概念。**需评估 hook 系统**（记忆里 hook 系统对标 §8 是另一条线），建议与 hook 对齐一起做。

**A-4 小结**：只有 `--ide` 是低成本可立即补的（env 已有）；其余依赖专有能力或 hook 系统深改，标记为独立评估。

1. **parseArgs 声明**：新增 flag 一律加到 `cli.ts:131` 的 `options`。boolean 类需要 `--no-` 前缀支持的，依赖已开的 `allowNegative: true`（`cli.ts:198`），只声明正向 key。多值用 `multiple: true`。

5. **help.ts 同步**：每个新 flag 必须在 `src/help.ts` 对应分组补一行，保持帮助文本与实现一致（当前 help.ts 已缺失一批 flag 的说明，本轮一并补齐）。
6. **settings 交互安全**：涉及读写 settings 的（`--settings`/`--setting-sources`），**只读合并、不回写磁盘**，规避记忆记录的 lossy round-trip（`settings-write-lossy-roundtrip.md`）和 cache null clobber（`settings-source-cache-null-clobber.md`）两个已知坑。
7. **测试**：每个 flag 至少一条单测——覆盖"正常生效"+"非法值报错"+"组合约束"三类。放到 `cli.ts` 参数解析的测试文件。
8. **构建验证**：每批次完成后跑 `bun test` 全量 + `make rebuild`，用 **`sc-dev`**（开发版，非 `sc`）实测 flag 行为。
