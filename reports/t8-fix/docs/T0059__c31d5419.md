## 0. 给下一轮修复者的快速上手（必读）

### 0.1 这是什么

对 sid-code 做了一轮"harness-LLM 可见性缺口"系统排查（12 项必查清单）。**确认 6 个缺口**，其余 6 项已闭环。本文逐个给出修复方案。

**缺口的本质**（同母方法论）：模型只能通过三条通道感知 harness——① system prompt ② 工具定义 ③ 注入消息流的内容。harness 有某能力/状态 X，但这三条通道里没有任何一条告诉模型 X 的存在或当前值 → 模型永远不会用它 / 永远不知道它 → 功能"工程完成、运行时死亡"。样板就是已修复的 ToolSearch（延迟工具靠每轮注入 `<available-deferred-tools>` 闭环）。

### 0.2 核心注入点（改这里）

绝大多数修复都落在**同一个地方**——主循环 `src/query/loop.ts` 的每轮 reminder 注入段：

- **`src/query/loop.ts:270-340`**：`reminderParts: string[]` 的收集 + `injectReminders` 注入。这是"每轮都注入、随消息流走、不受 system prompt 5 分钟缓存影响"的正确通道。
- **`src/query/reminder-inject.ts:26-62`**：`injectReminders()` 纯函数，把 reminder 前置到最后一条 user 消息（无 text block 的纯 tool_result 轮会追加 text block）。
- **对照**：deferred-tools 块（loop.ts:331-340）是已闭环样板，**新注入照它的写法**。

**关键区分**（贯穿全文）：
- ✅ **每轮 reminder 通道**（loop.ts reminderParts）= 实时、抗缓存、抗 compact。
- ❌ **system prompt 通道**（`src/config/system-prompt.ts` + `attachments.ts`）= 只在 init / CLAUDE.md 变更时构建，且有 5 分钟缓存（system-prompt.ts:89 `CACHE_TTL`），**主循环每轮不重建**。运行时会变的状态放这里 = 时机缺失 bug。

## 缺口 A — 模型对"快到 token 上限/即将 compact"完全无感知【🔴 死功能｜P0】

### 根因定位

- **harness 侧能力**：`src/query/loop.ts:142-218` 每轮计算上下文使用率：
  - `currentTokens = ctxMgr.estimateTokens(toolCount)`（loop.ts:144）
  - `usagePercent`、`remaining = 100 - usagePercent`（loop.ts:146-147）
  - `remaining <= 6` 时 `yield { kind: "context_warning", remaining }`（loop.ts:216-218）
- **断裂边**：`context_warning` 是 `QueryLoopYield` 事件，**只被上层 UI / 日志消费**。反向验证：在 loop.ts 内 `grep "context_warning|usagePercent|remaining"` 与 `addMessage|reminderParts|inject` 的交集 = **0 命中**。这个数字从未进入发给模型的 `finalMessages` 或任何 system reminder。
- **后果**：模型不知道自己快到上限，不会主动"收尾 / 把关键结论落盘到 todo 或文件 / 精简输出"。compact 永远是 harness 背着模型突然执行，模型在 compact 后只看到 `[压缩边界]`（事后），事前毫无准备——长任务里关键中间结论可能在模型还没落盘时就被压缩丢弃。

### claude-code 对照

`src/utils/attachments.ts:825-860` 的 `getAttachments` 管线里有一批每轮 delta attachment（`date_change`、`ultrathink_effort`、`deferred_tools_delta` 等），上下文压力类信号通过同一 attachment 通道随消息流告知模型，而非埋在 UI 事件里。

### 修复方案

在 `src/query/loop.ts` 的 reminder 收集段（loop.ts:270-318 之间，与 todo 回注同级）追加一个上下文压力 reminder：

```ts
// 缺口 A 修复：上下文压力告知（每轮，超过阈值才注入）
// usagePercent 已在 loop.ts:146 算出
const CONTEXT_PRESSURE_THRESHOLD = 80; // 使用率 ≥80% 开始提醒
if (usagePercent >= CONTEXT_PRESSURE_THRESHOLD) {
  reminderParts.push(buildContextPressureReminder(usagePercent, remaining));
}
```

新建纯函数（建议放 `src/query/context-pressure.ts`，与 todo-reminder.ts 同构，便于单测）：

```ts
export function buildContextPressureReminder(usagePercent: number, remainingPercent: number): string {
  return `<system-reminder>
上下文使用率已达 ${usagePercent.toFixed(0)}%（剩余约 ${remainingPercent.toFixed(0)}%）。即将触发自动压缩，压缩后较早的对话细节可能丢失。
请尽快：① 把尚未落盘的关键结论/决定写入文件或用 todo_write 记录；② 收敛当前输出，避免展开冗长内容；③ 如任务接近完成，优先完成收尾。
（请勿向用户复述本提醒）
</system-reminder>`;
}
```

**注入点**：必须走 `reminderParts`（每轮、随消息流），**不要**放进 system prompt（会被缓存冻结）。

**阈值建议**：与 `src/context/auto-compact.ts` 的 `TOKEN_THRESHOLDS` 对齐——在 `autoCompact` 真正触发的阈值**之前**几个百分点开始提醒，给模型"落盘窗口"。可考虑分级：≥80% 温和提醒，≥90%（接近 `TOKEN_THRESHOLDS.autoCompact`）强提醒"马上要压缩了"。

### 验收标准

- 构造一个高使用率的 ctxMgr（mock estimateTokens 返回接近上限），跑一轮，断言 `finalMessages` 最后一条 user 消息含 `上下文使用率`。
- 使用率低于阈值时不注入（避免每轮刷屏浪费 token）。
- `bun test` + `make build` 通过。

## 缺口 B — 会话恢复后模型不知道"这是续接的会话"【🔴 死功能(条件性)｜P0】

### 根因定位

- **harness 侧能力**：`src/session/store.ts:280-287` 的 `SessionStore.buildResumeMessage(summary)` 已写好提示文案：
  > "本次会话是从之前的对话中恢复的，之前的对话因上下文窗口限制而中断。以下是之前对话的摘要：… 请从上次中断的地方继续，无需再次询问。"
- **断裂边**：`src/app.ts:930-980` 的 `restoreSession` 有**三条恢复路径**，只有一条注入了恢复提示：
  - 路径 1（app.ts:946-949）：`messages.length <= 20` → 直接 `ctxMgr.setMessages(sessionData.messages)`，**不注入任何恢复提示**。
  - 路径 2（app.ts:956-973）：`>20 且有摘要` → 调 `buildResumeMessage` 注入 ✅（唯一闭环的路径）。
  - 路径 3（app.ts:974-978）：`>20 但无摘要` → `safeSliceTail(15)` + `setMessages`，**不注入任何恢复提示**。
- **后果**：最常见的"短会话续接"（≤20 条）和"无摘要长会话"两种情况下，模型看到一堆历史消息却不知道发生过中断，不知道"无需再次询问、从断点继续"。可能重新和用户打招呼、重问已问过的问题、或重复已完成的工作。
- **附带**：`~/.sid-code/progress/<sessionId>.md`（work-log 落盘，见 `src/query/work-log.ts`）在所有恢复路径里都**未被读取回注**——这本是抗压缩、跨会话的外部进度记忆，恢复时白白浪费。

### claude-code 对照

`src/utils/crossProjectResume.ts` + `src/utils/listSessionsImpl.ts` 有独立的 resume 上下文重建机制，恢复时统一注入续接上下文。

### 修复方案

**统一三条路径**，把"续接提示"提到 `restoreSession` 入口，无论走哪条路径都注入一条轻量续接标记。

方案（改 `src/app.ts:930-980`）：

1. 在方法开头计算一次 `isResume = true`（本来就是恢复语境）。
2. 路径 1（≤20 条）：`setMessages` 之后，追加一条简短续接提示（不需要摘要，因为历史完整）：
   ```ts
   this.ctxMgr.addMessage({
     role: "user",
     content: [{ type: "text", text: SessionStore.buildResumeMarker() }],
   });
   ```
3. 路径 3（无摘要）：同路径 1，`setMessages(recentMessages)` 后追加续接提示，并说明"早期消息已因恢复截断"。
4. 路径 2 保持现状（已有 `buildResumeMessage`）。

新增一个轻量 marker（store.ts，与 `buildResumeMessage` 并列）：

```ts
/** 续接标记（无摘要时用，历史消息本身已在上下文里） */
static buildResumeMarker(progressNote?: string): string {
  return `<system-reminder>
本次会话是从之前的对话恢复的续接会话（上方消息为历史上下文）。请直接从上次中断处继续，无需重新打招呼或重复询问已确认的信息。${progressNote ? `\n之前的进度记录：\n${progressNote}` : ""}
</system-reminder>`;
}
```

5. **（增强，可选）** 读取 progress 落盘补进度：
   ```ts
   // 从 ~/.sid-code/progress/<id>.md 读最近进度快照，作为 progressNote 传入
   const progress = readProgressSnapshot(sessionData.id); // 见 work-log.ts
   ```
   注意 progress 文件用的是被恢复会话的 id（`sessionData.id`），不是本进程新 id。

### 注意事项（已知坑，别踩）

- **协议配对**：路径 1 用 `setMessages` 整体替换；若在其后用 `addMessage` 追加 user 消息，要确保历史末尾不是"未应答的 tool_use"（否则插入 user 消息破坏 tool_use/tool_result 配对 → OpenAI 400）。安全做法：用 `safeSliceTail`（已 import，app.ts:935）保证切片边界干净，或在追加 marker 前检查末尾。路径 2 的现有实现（app.ts:960-972）已处理这个顺序问题，可参照。
- marker 应作为**独立 user 消息**插在历史**之后**，让它出现在注意力最强的末尾位置。

### 验收标准

- 三条路径各构造一个 SessionData，断言恢复后 ctxMgr 历史里都能找到续接提示文案。
- 恢复后历史满足 tool_use/tool_result 配对（跑 `checkMessageHistoryIntegrity` 应无 orphan）。
- `bun test` + `make build` 通过。

## 缺口 C — permission mode 只进被缓存的 system prompt，运行时切换不刷新【🟠 时机缺失｜P1】

### 根因定位

- **harness 侧能力**：`src/config/attachments.ts:218-226` 的 `generatePermissionModeAttachment(mode)` 生成详细 mode 行为指南（`PERMISSION_MODE_DESCRIPTIONS`，attachments.ts:58-94，含 plan 模式"绝对不能编辑"、readonly、acceptEdits、dontAsk 等硬约束）。经 `buildSystemPrompt`（system-prompt.ts:200-202）注入。
- **permission mode 运行时可变**：
  - `src/app.ts:1167` `this.config.permissionMode = "plan"`（enter_plan_mode）
  - `src/app.ts:878-879` CLAUDE.md 规则覆盖
  - `/` 命令切换（`src/command/builtins.ts`）
- **断裂边**：
  - ① system prompt 有 5 分钟缓存（system-prompt.ts:89 `CACHE_TTL`），且仅在 init（init-helpers.ts:271）/ CLAUDE.md 变更（app.ts:704）时重建。`buildSystemPrompt` 在主循环里**从不每轮调用**。
  - ② 反向验证：`grep permissionMode src/query/loop.ts` = **0 命中**。主循环每轮都不注入 mode。
- **后果**：用户中途切 mode（尤其 acceptEdits / dontAsk / readonly），模型上下文里的 mode 指南仍是**会话启动时的旧值**。
- **半个补丁**：plan mode 另有 `getPlanModeReminder` 每轮注入（loop.ts:274-277 + app.ts:327-331），所以"切入 plan mode"这一种情况被兜住了。但**其它 mode 之间的切换无任何每轮通道**。

### claude-code 对照

`src/utils/attachments.ts:605` 的 `command_permissions`、:382 的 `hook_permission_decision` 走每轮 attachment delta 通道，不靠静态 system prompt 承载权限状态。

### 修复方案

把 permission mode 从"只在 system prompt"改为"每轮 reminder 通道也注入"（或仅在 mode 变化时打 delta，省 token）。

方案 1（简单，每轮注入，推荐先做）：在 loop.ts 的 reminderParts 段追加：

```ts
// 缺口 C 修复：permission mode 每轮可见（覆盖 plan 之外的所有 mode 切换）
// 通过 deps 暴露当前 mode（engine 透传 config.permissionMode）
if (deps.getCurrentPermissionMode) {
  const mode = deps.getCurrentPermissionMode();
  if (mode && mode !== "default") {
    // 已有 getPlanModeReminder 覆盖 plan，避免重复
    if (mode !== "plan") {
      reminderParts.push(buildPermissionModeReminder(mode));
    }
  }
}
```

- 需要在 `src/query/engine.ts`（参照 getTodoState 的接法，engine.ts:66-68/205-206）和 app.ts deps 工厂（app.ts:327-342 同段）新增 `getCurrentPermissionMode: () => this.config.permissionMode`。
- `buildPermissionModeReminder` 可直接复用 `PERMISSION_MODE_DESCRIPTIONS`（把 attachments.ts:58-94 的 map 导出复用），包成 `<system-reminder>`。

方案 2（省 token，delta）：用 `LoopState` 记 `lastSeenPermissionMode`，只在与上轮不同时注入一次"权限模式已切换为 X"。`LoopState` 见 `src/query/types.ts`，参照 `lastSeenTodoWriteVersion`（loop.ts:287）的写法。

**建议**：方案 1 + 方案 2 结合——非 default mode 时低频重述（防遗忘），mode 变化的那一轮强注入（防时机缺失）。

### 验收标准

- 启动后切到 acceptEdits，跑一轮，断言 finalMessages 含该 mode 的指南文案。
- default mode 不注入。
- 切回 default → 再切 readonly，断言变化轮注入了新 mode。
- `bun test` + `make build` 通过。

## 缺口 D — deny 规则/禁用工具，模型动手前不可知，只能撞墙【🟡 半盲｜P2】

### 根因定位

- **harness 侧能力**：`src/permission/checker.ts` 能在执行前判定拒绝：
  - :329 deny 规则命中
  - :344 工具已禁用
  - :374 路径验证拒绝
- **断裂边**：deny / disabled 清单从未进任何模型通道。模型只有在调用后吃到 `权限拒绝: <reason>`（`src/query/tool-executor.ts:163-167`）或 `用户拒绝执行工具`（:152-156）才知道。
- **后果**：模型对"哪些路径/命令被 deny"无前瞻，会反复尝试被禁的操作，浪费轮次。注意：error 文案本身**合格**（带 reason，item 10 已闭环），问题是**事后**而非**事前**。

### claude-code 对照

claude-code 用 `getAlwaysAllowRules` 类机制 + `command_permissions` attachment（attachments.ts:605）把权限规则前置告知模型。

### 修复方案

把 deny 规则摘要作为**低优先级**信息注入。两个选择：

- 选择 A（system prompt 附件，静态规则适用）：deny 规则通常在配置里、会话内基本不变，可在 `buildSystemPrompt` 加一个 `denyRules` 附件（attachments.ts 加 `generateDenyRulesAttachment`，priority 取较低如 GIT_STATUS 级）。因为规则静态，缓存冻结无害。
- 选择 B（每轮 reminder，若规则运行时可变）：同缺口 C 走 reminderParts。

**建议选 A**：deny 规则是配置态、会话内稳定，放 system prompt 最省 token 且无时机问题。

实现：从 `PermissionChecker` 暴露一个 `describeDenyRules(): string`（列出 deny 的命令模式 / 路径前缀 / 禁用工具名），注入为：

```
<permission-constraints>
以下操作已被配置禁止，请勿尝试（尝试也会被拒绝）：
- 禁用工具：<tool names>
- deny 路径：<path patterns>
- deny 命令：<command patterns>
</permission-constraints>
```

### 验收标准

- 配置若干 deny 规则，断言 system prompt（或 reminder）含约束摘要。
- 无 deny 规则时不注入空块。
- `bun test` + `make build` 通过。

## 缺口 E — Skill 发现：列表附件是死代码，defer 后 whenToUse 丢失【🟡 半盲｜P2】

### 根因定位

- **harness 侧能力**：
  - `SkillTool` 把每个 skill 包装成 `skill__<name>` 工具，`description()` 含 `whenToUse`（`src/skill/tool.ts:45-57`），在 `src/cli.ts:678` 注册进 registry。
  - `generateSkillListingAttachment`（`src/config/attachments.ts:334-346`）+ `PRIORITY.SKILL_LISTING=8`（attachments.ts:31-32）本意做"两层索引发现"（只放摘要省 token）。
- **断裂边**：
  - ① **死代码**：`grep generateSkillListingAttachment` 在 attachments.ts 定义处之外**零调用**。`buildSystemPrompt`（system-prompt.ts:196-273）的附件收集里**没有 skillListing 分支**——skill 摘要列表从未进系统提示词。
  - ② **defer 后丢描述**：skill 当前只靠 `skill__*` 工具的 description 暴露。但若该工具被 defer（registry.ts:202-211，MCP 工具及 `shouldDefer` 工具默认延迟），每轮 deferred reminder **只喂工具名**（loop.ts:335 `deferredNames.join("\n")`），`whenToUse` / description 全丢——模型只看到 `skill__xxx` 一个名字，无从判断何时该用、也就不会去 tool_search 调出。
- **后果**：skill 体系（CLAUDE.md §0.1 的变现层）对模型半可见。若 skill 工具恰好可见则尚可（靠 description 里的 whenToUse），一旦被 defer 就近乎死功能。

### claude-code 对照

claude-code 的 skill / agent 列表走 `agent_listing_delta`（attachments.ts:692/851）等专门 delta attachment，带描述注入消息流，不依赖工具是否被 defer。

### 修复方案

**接通死代码 + 保证 skill 摘要常驻可见**：

1. 在 `buildSystemPrompt`（system-prompt.ts:196-273 附件收集段）加入 skillListing 分支：
   ```ts
   // 缺口 E：接通 skill 摘要列表（此前 generateSkillListingAttachment 是死代码）
   if (ctx.skillEntries && ctx.skillEntries.length > 0) {
     const att = generateSkillListingAttachment(ctx.skillEntries, contextWindowTokens);
     if (att) attachments.push(att);
   }
   ```
   - `SystemPromptContext`（system-prompt.ts:28-80）加 `skillEntries?: SkillListingEntry[]` 字段。
   - 调用方（init-helpers.ts:271 + app.ts:704）从 skill registry 收集 entries 传入。`SkillListingEntry` 见 `src/skill/budget.ts:29`，`generateSkillListing` 见 budget.ts:112。
2. **（关键，别遗漏）** skill 工具**不应被 defer**——或者，被 defer 的 skill 至少要在 deferred reminder 里带一句话描述。两个选择：
   - 选择 A：给 SkillTool 设 `alwaysLoad = true`（registry.ts:203 `isToolDeferred` 首先看 alwaysLoad），保证 skill 工具的 whenToUse 始终在工具定义里可见。但这会增加首轮工具列表 token。
   - 选择 B（推荐）：skill 走"摘要列表常驻 system prompt（步骤 1）+ 工具本体可 defer"的两层结构——这正是 `SKILL_LISTING` 附件设计的初衷。摘要让模型知道"有这些 skill、何时用"，真正调用时再 tool_search 调出 `skill__*` 工具。这样既省 token 又不丢发现性。

**建议选 B**：步骤 1 接通摘要列表后，defer 本身就不再是问题（发现性由摘要承载，token 由 defer 节省），符合原设计意图。

### 验收标准

- 注册若干 skill，断言 system prompt 含 skill 摘要列表（名 + whenToUse 截断）。
- 无 skill 时不注入空块。
- skill 工具被 defer 时，模型仍能从摘要列表得知该 skill 存在。
- `bun test` + `make build` 通过。

## 缺口 F — sub-agent 类型名可见但能力边界不可见【🟡 半盲｜P2】

### 根因定位

- **harness 侧能力**：
  - `sub_agent` 工具的 `description()`（`src/agent/tool.ts:104-111`）和 schema enum（tool.ts:27）列出了类型名（`types.join("、")`）。
  - `src/agent/agent-definition.ts:48-112` 为每种类型定义了 `description` + `tools`：
    - explore：`快速搜索和分析代码库，只返回关键发现`，tools=`read/grep/glob/ls/read_many/task_list`（**只读**）
    - general：`执行指定的子任务并返回结果`，tools=`read/write/edit/bash/grep/glob/ls/read_many/web_fetch/web_search/task_list`（**可写**）
    - summary、plan、verify 各有 description + tools
- **断裂边**：暴露给模型的只有**类型名列表**。每种 agent 的 `description`（如"对抗式验证" vs "快速搜索"）和**工具集边界**（explore 不能写文件、general 能）**从未进入工具定义或消息流**。
- **后果**：模型派活时只能凭类型名猜能力，可能把"需要写文件"的活派给只读的 explore，子代理撞墙后才反馈失败，浪费一整个子代理回合。

### claude-code 对照

`src/utils/attachments.ts:1490` 的 `getAgentListingDeltaAttachment` 把可用 agent 及其描述以 delta attachment 注入消息流，模型派活前可见各 agent 的能力边界。

### 修复方案

**最省事**：扩展 `sub_agent` 工具的 `description()`（agent/tool.ts:104-111），把每种类型的一句话能力 + 关键工具集写进去：

```ts
description(): string {
  const defs = getBuiltInAgentDefinitions(); // 需在 agent-definition.ts 暴露完整定义而非仅 names
  const typeLines = defs.map(d =>
    `- ${d.type}：${d.description}（可用工具：${(d.tools ?? ["全部"]).join("/")}）`
  ).join("\n");
  return `启动一个子代理执行独立子任务，子代理有独立上下文。
可用类型：
${typeLines}
子代理完成后只返回最终结果。run_in_background=true 后台执行；isolation=worktree 在独立 Git Worktree 执行。`;
}
```

- 需要 `agent-definition.ts` 暴露 `getBuiltInAgentDefinitions()`（返回带 description/tools 的完整对象），现仅有 `getBuiltInAgentTypes()`（只返回 names，tool.ts:11 import）。
- 注意工具 description 进入工具定义通道，受 prompt 缓存影响小（工具定义会话内稳定），这里合适。

**可选增强**：若 agent 类型运行时可变（自定义 agent），改走每轮 reminder delta（对标 claude-code），但内置 5 种类型静态，**优先改 description 即可**。

### 验收标准

- 断言 `SubAgentTool.description()` 含每种类型的能力描述 + 工具集。
- 新增 `getBuiltInAgentDefinitions()` 有单测覆盖返回结构。
- `bun test` + `make build` 通过。

# 第五部分：修复顺序与通用注意事项

### 建议顺序

1. **缺口 A**（上下文压力）— 纯新增 reminder，风险最低，收益最高（防长任务丢结论）。
2. **缺口 B**（会话恢复）— 改 restoreSession 三路径，注意 tool_use/tool_result 配对（已知坑见 §B）。
3. **缺口 C**（permission mode）— 加 deps + 每轮/delta 注入。
4. **缺口 F**（sub-agent description）— 改 description，最局部。
5. **缺口 E**（skill 列表）— 接死代码 + 确认 defer 策略。
6. **缺口 D**（deny 规则）— system prompt 附件，最可选。

### 通用注意事项（每个都适用）

- **注入通道选择铁律**：运行时会变的状态 → **每轮 reminderParts**（loop.ts）；会话内稳定的配置 → **system prompt 附件**（但记得它有 5min 缓存，且只在 init/CLAUDE.md 变更重建）。选错 = 制造新的时机缺失 bug。
- **省 token**：reminder 要么节流（如 todo 的 8 轮间隔）、要么只在阈值/变化时注入，不要每轮无脑刷屏。摘要类信息只喂名字 + 一句话，别喂完整 schema（对标 deferred-tools 只喂名）。
- **协议配对**：任何往历史插 user 消息的改动，都要保证不破坏 tool_use/tool_result 配对（用 `safeSliceTail` / `checkMessageHistoryIntegrity` 自检），否则 OpenAI 400。loop.ts 发送前有 `backfillOrphanToolResults` 兜底（loop.ts:227-252），但别依赖它。
- **纯函数 + 单测**：每个 `buildXxxReminder` 都做成纯函数（入状态、出字符串），照 todo-reminder.ts / reminder-inject.ts 的测法补单测——这是这类缺口唯一能被测试覆盖的部分（注入逻辑可测，"模型是否真感知"测不了）。
- **不向用户复述**：所有 `<system-reminder>` 文案都要带"请勿向用户提及/复述本提醒"，对齐现有 todo-reminder.ts:63 风格。
- **收尾**：`bun test`（全量）+ `make build`，不可跳过（CLAUDE.md §0）。

### 备注：item 3a（todo 裸窗口）为何不单列修复

todo 写完后第 1~7 轮（节流 `TURNS_BETWEEN_REMINDERS=8`，todo-reminder.ts:23）模型靠刚写入的工作记忆追踪，理论上有"裸窗口"。但：① 刚 todo_write 完模型记忆最新鲜；② 写入那轮已刷新基线（loop.ts:293-295）；③ 缩短间隔会增 token。属可接受的工程权衡，**不作为缺口修复**，仅记录。若未来发现弱模型在此窗口遗漏，可把 `TURNS_BETWEEN_REMINDERS` 调小或改自适应。
