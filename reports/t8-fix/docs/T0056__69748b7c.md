# 受控缓存实测结果（T3 / P1-1）

> 实测日期：2026-08-08
> 工具：`bun scripts/cache-bench.ts`（逐轮固定前缀 + 尾部追加增量）
> 渠道隔离：全程 `SID_CODE_USAGE_LEDGER` / `SID_CODE_CACHE_BREAKS` 指向临时目录
> 污染核对：本批 bench/探针跑前后账本行数**同值**（当时为 350 / 86），未污染。
> ⚠️ 判据是"**跑脚本前后行数不变**"，不是"行数恒为 350/86" ——
> 2026-08-09 已因 T4/P1-3 的真实无头会话涨到 357/91（真实请求本就该入账本）。
> 复核请重新取基线再比，别拿这里的绝对值当基线。

## 0. 一句话结论

**三个协议族在可信渠道上的稳态命中率都在 95% 以上**（Chat 96.3% / Anthropic 98.7%），
唯一低于此的是 Responses 族的 55.5%，但那不是实现问题 —— 是服务端**按 128 token 粒度
渐进扩展缓存前缀**，轮数越多越接近上限（实测 r6 已达 94.0%）。

## 1. 逐轮曲线

### 1.1 glm-5.2 @ uniapi（Chat Completions 线）

| 轮次 | 完整输入 | 命中 | 写入 | 命中率 |
| --- | --- | --- | --- | --- |
| r1 | 2366 | 0 | 0 | 0.0% |
| r2 | 2384 | 2304 | 0 | 96.6% |
| r3 | 2402 | 2304 | 0 | 95.9% |
| r4 | 2420 | 2304 | 0 | 95.2% |
| r5 | 2438 | 2304 | 0 | 94.5% |
| r6 | 2456 | 2432 | 0 | 99.0% |

**稳态（排除 r1）96.3%，全轮 80.5%。** 花费 $0.2318。

形态完全正确：r1 冷启动 0 命中，r2 起立刻满命中。
r2→r5 命中值恒为 2304 而分母每轮 +18（尾部追加），所以百分比缓慢下滑；
r6 跳到 2432 —— 服务端把缓存前缀往后扩了一段（见 §2 的 128 粒度）。

### 1.2 gpt-5.6-luna @ uniapi（Responses 线 —— P0-1 修复的验证）

| 轮次 | 完整输入 | 命中 | 命中率 |
| --- | --- | --- | --- |
| r1 | 2882 | 0 | 0.0% |
| r2 | 2905 | 0 | 0.0% |
| r3 | 2928 | 1792 | 61.2% |
| r4 | 2951 | 1792 | 60.7% |
| r5 | 2974 | 1792 | 60.3% |
| r6 | 2997 | 2816 | 94.0% |

**稳态（排除 r1）55.5%，全轮 46.4%。** 花费 $0.2668。

**这一条是 P0-1 的端到端验证**：修复前该路径的命中恒读成 0（`input_tokens_details.cached_tokens`
从未被读取），账本记 2.2%。现在能读到真实非零命中了。

但**不要把 55.5% 当成 Responses 族的上限**：
- r2 仍 0 —— 服务端缓存写入有延迟，与 deepseek 官方直连的特征一致（§1.4 曾观察到）
- 命中值 1792 / 2816 都是 **128 的整数倍**，且 r6 一次跳了 1024
- 说明服务端是**渐进扩展**缓存前缀，而非一次缓存全部。轮数越多越接近上限。

### 1.3 claude-sonnet-5-gateway @ uniapi（Anthropic 线 —— 回答 §1.4 / T1）

| 轮次 | 完整输入 | 命中 | 写入 | 命中率 |
| --- | --- | --- | --- | --- |
| r1 | 4184 | 4163 | 0 | 99.5% |
| r2 | 4207 | 4163 | 0 | 99.0% |
| r3 | 4230 | 4163 | 0 | 98.4% |

**稳态（排除 r1）98.7%，全轮 99.0%。** 花费 $0.1902。

⚠️ **r1 就 99.5% 不是渠道造数**：这是同一前缀的**第二次**运行，
上一次运行已把它写进服务端缓存（探针的判据 A 用每次全新的 nonce 前缀，
恰好排除这种情况 —— 两个工具的前缀策略相反是刻意设计）。

## 2. T1 的答案：uniapi 的 anthropic 通道**能**命中

方案 §1.4 列的三种结局里，命中的是第一种：**anthropic 族有可信基线，博客表格改用 uniapi 数据。**

判据链（两个工具交叉验证，单独任一个都会得出错误结论）：

| 观测 | 结论 |
| --- | --- |
| 探针判据 A：全新前缀 r1 `read=0 create=2584` | 冷启动正确报 0 命中 + 全量写入 |
| 探针 repeat×3：稳定 `read=2584 create=0` | 命中稳定、不抖动 → 判定 **✓ 可信** |
| 探针判据 B：无断点 `read=0 create=0` | 不打 `cache_control` 就不缓存，符合 Anthropic 协议 |
| bench 第二次运行：r1 起 98%+ | 缓存跨运行持久，且 sid-code 的断点位置有效 |

**一个方法论教训（值得进博客）**：第一次跑 bench 时该通道 6 轮 `hit` 全为 0，
差一步就写成"网关不透传 cache_control"。但探针用**完全相同的请求**却稳定命中 ——
两个结论矛盾，说明不是渠道问题而是**我的仪器**问题：
bench 只记了 `hit` 没记 `write`，而 `hit=0` 有两种相反成因：

1. 什么都没缓存（断点没生效 / 前缀太短）
2. 每轮都在**重新写入**（缓存键把变化的尾部也算进去了 → 永远写、永远读不到）

**这两种成因的修法相反，而只看命中列无法区分。** 已给 bench 补 `write` 列 +
自动提示（`cache-bench.ts` 的"命中恒 0 但每轮都在写入"分支），并加了对应单测锚死。

## 3. 与账本 66.9% 的差距

| 口径 | 数值 | 说明 |
| --- | --- | --- |
| 受控稳态（Anthropic） | 98.7% | 理想形态：前缀固定、只在尾部追加 |
| 受控稳态（Chat） | 96.3% | 同上 |
| 受控稳态（Responses） | 55.5% → 94.0%（r6） | 服务端渐进扩展，轮数越多越高 |
| 受控全轮（含冷启动） | 46.4%–99.0% | 轮数越少，r1 的拖累越大 |
| **账本聚合** | **66.9%** | 混了模型/渠道/会话长短/compact 次数 |

**差距不在协议实现。** 受控形态下三族都能到 95%+，说明断点布局与协议映射都是对的。
账本低是因为真实会话里前缀被反复打断 —— 这正是 P1-2 的 `prefix_break` 埋点要量的东西。

> ⚠️ **2026-08-09 补充：上面这句"前缀被反复打断"是对的，但它的 message 级读数不可直接当优化目标。**
> T4 已拿到分布（`prefix-break-分布-20260808.md`）：断裂 100% 落在 `message` 段，
> `msg[0]` 占总浪费 81.6%。但按此实现的修法（把 reminder 挪成独立尾部消息）
> **真实命中率反而降了 0.2~11.2pp、已回滚** ——
> 因为服务端按 **token 前缀**匹配，挪 message 结构在 wire 上塌缩成同一串字节，
> 共同前缀长度分毫未变（实测前后都是 15 字符），而探针按 message 切段，
> 下标 +1 就让 `msg[0]` 归零，造成"修好了"的假象。
>
> **所以"账本 66.9% 里有多少是可回收的前缀浪费"目前仍未定量。**
> 需要先给探针加 token/字符级共同前缀度量才能回答。详见那份文档的 §2.5。

⚠️ **口径提醒**：受控全轮口径受轮数强烈影响（6 轮时 r1 占 1/6），
所以**不要拿受控全轮数字与账本直接比**。可比的是稳态口径与"账本里长会话的后半段"。

## 4. 成本

三次实测合计约 **$0.69**（glm $0.2318 + luna $0.2668 + sonnet $0.1902），
另加探针 $0.1893。每次运行硬上限 $0.50，均未触顶。

## 5. 复现方式

```bash
bun scripts/cache-bench.ts --model glm-5.2 --rounds 6
bun scripts/cache-bench.ts --model gpt-5.6-luna --rounds 6
bun scripts/cache-bench.ts --model claude-sonnet-5-gateway --rounds 3
bun scripts/cache-trust-probe.ts --model claude-sonnet-5-gateway --rounds 3
```

⚠️ 同一前缀重跑会命中上一次运行写入的缓存，导致 r1 就高命中。
要测真实冷启动，改 `staticPrefix()` 里的文本或等缓存过期。
