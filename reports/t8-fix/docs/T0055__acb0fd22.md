## 1. 一句话结论

任务在**第 16 轮**就已 `end_turn` 完成并输出了完整审计报告，但因 **Goal 评估器全程故障**（6 次调用 0 成功），系统把"评估器坏了"静默降级为"目标未满足"，逼着模型从第 16 轮**空转到第 31 轮**反复重跑已完成的核查；最后**第 32 轮主模型请求 hang 死**，因 abort 无法穿透多层 `for await` 阻塞，白等 600 秒才被最外层配对看门狗记录收尾。

用户观察到的三个现象——「任务执行到一半中断在收尾处」「goal 过程不清晰」「评估器暂时不可用」——是**同一条故障链**的不同切面。

## 3. 分级问题清单

### 🔴 P0-1｜Goal 评估器全程不可用 + 静默降级方向错误 → 死循环空转

**根因 A（配置/选型）**
评估器模型选定链（`src/query/loop.ts:1680-1684`）：`config.goal.evaluatorModel > subAgentModels.verify > subAgentModels.default > 主模型`。本次 `verify=deepseek-v4-pro`，超时写死 8 秒（`src/goal/config.ts:33`）。

warn.log 6 次失败 `durationMs` 全是 **8003~8005ms**——每次精确跑满 8 秒被 abort，一次没成功。deepseek-v4-pro 这条路要么连不通、要么 8 秒对它的首字节+推理太短。

**根因 B（降级方向错误）**
`src/query/goal-gate.ts:147-153` catch 分支：评估失败 → `satisfied:false, reason:"评估器暂时不可用，继续工作"`。在"报告已完成"场景下 = **评估器坏了 → 永远判未满足 → 永远催继续**。方向反了：评估器故障 = "无法判定" ≠ "未满足"，默认应放行。

**根因 C（无熔断）**
连续失败无熔断。模型自己都识破了（截图 1201-1203），goal-gate 仍不放行。

**影响**：token ↑475.6k、40 分钟、$2.53，约一半是纯空转。

#### 确定方案 P0-1

**改动 1：复用现成 BlockedDetector 做评估器熔断**
- 位置：`src/query/goal-gate.ts:147-153`（catch 分支）
- 现状：评估失败时 `evalResult.blockerKey` 为 undefined，绕过了 goal-gate.ts:197 的 `blockedDetector.record()`。
- 改法：catch 分支里设 `evalResult = { satisfied: false, blockerKey: "__evaluator_unavailable__", reason: "..." }`，后续走正常的 blockedDetector 路径。连续 `blockedThreshold`（默认 3）次相同 blockerKey → 触发 blocked 硬停止 → 放行 end_turn。**不需要新写计数逻辑，复用现成机制**。
- 同时把 blocked 硬停止的行为从"判定不可能达成"改为"放行 end_turn + TUI 告警'评估器连续不可用，自动放行'"。

**改动 2：超时从 8s 改为 25s**
- 位置：`src/goal/config.ts:33` `evaluatorTimeout: 8000` → `evaluatorTimeout: 25000`
- 依据：deepseek-v4-pro 首字节 5-15s 属正常，8s 必超；25s 够完成 512 token 生成。

**改动 3：评估器模型选定链去掉 `subAgentModels.verify`**
- 位置：`src/query/loop.ts:1682-1684`
- 现状：`config.goal.evaluatorModel || config.subAgentModels?.verify || config.subAgentModels?.default || config.model`
- 改为：`config.goal.evaluatorModel || config.subAgentModels?.default || config.model`（删掉 verify 一层）
- 理由：verify 语义是"对抗验证子代理"（需强模型），goal 评估是"快速判完成"（需快模型）。两者解耦。

**改动 4：catch 降级语义反转**
- 位置：`src/query/goal-gate.ts:149` `satisfied: false` → 由改动 1 的 blockedDetector 统一处理，不再直接返回 `satisfied:false`。
- 不需要单独改——改动 1 做完后，catch 分支走 blockedDetector 路径自然解决。

**验证方式**：单测注入一个必超时的 mock provider（delay 30s），跑 3 轮 goalGate，断言第 3 轮返回 `shouldContinue:false`（blocked 放行）。

### 🔴 P0-2｜主 LLM 请求 hang 死 → abort 无法穿透多层 `for await` 阻塞（v2 根因坐实）

> ⚠️ **推翻 v1 猜测**：`"timeout"` **已注册**在 `ABORT_REASONS`（`src/llm/errors.ts:121`），`isAbortError` 也能识别 `"Request aborted"`（errors.ts:324-329）。v1 写的"疑似 timeout 未注册"是**错的**。真根因在信号传播的结构，不在识别。

**真根因：abort 只能中断最底层 fetch，无法叫醒阻塞在 `for await` 上的中间层。**

逐层读码坐实的链路：
1. session abort（`app.ts:2847` `abort("timeout")`）→ 触发 openai.ts 的 abortPromise reject。
2. openai.ts 最外层 catch（`src/llm/openai.ts:841-849`）把 abort 错误转成 **`yield { type:"error" }` 而非 throw**。warn.log 证明这一步执行了（打了"请求异常 model=glm-5.2"）。
3. **但这个 yield 要被消费，上游三层 `for await` 必须先醒**：
   - `fallback.ts:438` `for await (const event of stream)` — `signal?.aborted` 检查在 **loop 体内**（439 行），只有下一个 event 到达才执行。
   - `stream-processor.ts:106` `for await` — 同样，超时标志检查在 **110 行 loop 体内**。
   - `loop.ts:945` `await Promise.race([processStream, turnTimeout, watchdog])`。
4. 当 SSE 半开（TCP 连接在、服务端不再发 event），`reader.read()` 永不 settle → 三层 `for await` 全部**永久阻塞在等下一个 event**，`signal?.aborted` 检查永远执行不到。abort 中断了 fetch，但中间层的 `await` 没有 race abort，醒不过来。
5. loop.ts 两道兜底防线（turnTimeout `setTimeout:855` + watchdog `setInterval:900`）本应 300s~600s 触发，但代码注释自承"**实测 setTimeout 回调延迟 193s → 流 hang 死 35min**"、"实测 22 分钟无反应"——Bun 事件循环被半开 TCP IO 占满时定时器延迟 fire。turn 32 的 events.jsonl **零 WatchdogKill/TimeoutFired 事件**，坐实两道防线在真实 hang 下双双失效。
6. 最终只有跨模块的 collector 配对看门狗（`collector.ts` `PAIRING_TIMEOUT_MS=600000`，独立 setTimeout）在 600s 后记录 `ModelCallUnpaired` 收尾。

与记忆 [ESC 中断崩溃] / [Harness-Retry P0 信号未转发] 同源——**abort 送达底层 ≠ 主循环收到收尾**。

#### 确定方案 P0-2（彻底修复，非缩短窗口）

**核心改动：给 `fallback.ts` 和 `stream-processor.ts` 两层的 `for await` 补上 abortPromise race**

`openai.ts:1291-1343` 已有现成、可直接复制的模板：
```ts
let signalAbortHandler: (() => void) | null = null;
const abortPromise = (signal && !signal.aborted) ? new Promise<never>((_, reject) => {
  signalAbortHandler = () => reject(new Error("Request aborted"));
  signal.addEventListener("abort", signalAbortHandler, { once: true });
}) : null;
// 消费循环内：
const racers = [iterator.next()];
if (abortPromise) racers.push(abortPromise);
const result = await Promise.race(racers);   // abort 触发 → 立即 reject，不等 event
```

**改动 1：`src/llm/fallback.ts:438` 的 `for await (const event of stream)`**
- 改为手动迭代 + race：`const it = stream[Symbol.asyncIterator](); while(true) { const { value, done } = await Promise.race([it.next(), abortPromise]); ... }`
- fallback.ts:863 已有 `signal.addEventListener("abort", onAbort)` 基础设施，构造 abortPromise 无新依赖。

**改动 2：`src/query/stream-processor.ts:106` 的 `for await`**
- 同改动 1 模式。stream-processor 已有 `getAbortController`（line 28），从中取 signal 构造 abortPromise。

**改动 3：`src/query/loop.ts:945` 的 `Promise.race`**
- 已经是 race（processStream vs turnTimeout vs watchdog），无需改结构。改动 1、2 生效后，processStream 会因 abort 立即 reject，race 立即 settle。

**改动 4：collector 配对看门狗超时 600s → 120s**
- 位置：`src/trace/collector.ts` `PAIRING_TIMEOUT_MS`
- 作为改动 1-3 都失效时的最后兜底，600s 太长，改 120s。

**为什么不靠加 failsafe / 缩短 setTimeout**：loop.ts 的 turnTimeout（setTimeout:855）和 watchdog（setInterval:900）代码注释自承"实测 setTimeout 延迟 193s / hang 35min"——Bun 事件循环被半开 TCP IO 占满时定时器不可靠。**只有改动 1、2 的 race 模式不依赖定时器、不依赖底层 reader 响应，是唯一真解**。改动 4 只是兜底。

**验证方式**：单测起一个"返回 headers 后永不发 body"的 mock HTTP server，发请求 → 500ms 后 abort → 断言 `executeWithFallback` 在 1s 内以 abort 错误 reject（而非 hang）。三层各写一个。

### 🟠 P0-3｜评估器上下文窗口太小，看不到完整报告（v2 新增，goal 体系深坑）

`extractEvalContext`（`src/goal/evaluator.ts:120-124`）：只取**最近 3 轮（`messages.slice(-6)`）**，每个 text block **截断 800 字符**，总上限 **4000 字符**（`maxChars=4000`）。

本次审计报告正文约 **6.7k 字符**（截图「已思考 56s · 6.7k 字符」）。这意味着：**即使评估器不超时、正常返回，它也只能看到报告的头 4000 字符 + 截断片段，大概率判不出"已完成"**。这是比"8 秒超时"更深的设计缺陷——对"输出长报告"类任务，评估器的判据输入天然不足。

#### 确定方案 P0-3

**改动 1：`extractEvalContext` 保证最后一条 assistant 消息完整**
- 位置：`src/goal/evaluator.ts:120-138`
- 现状三道截断联合：`messages.slice(-6)` + `block.text.slice(0, 800)` + `truncateToLimit(joined, 4000)`。
- 改法：单独取最后一条 role=assistant 的消息**不截断**（或放宽到 8000 字符）拼在最前，其余最近消息维持 800 截断；总上限 `maxChars` 从 4000 提到 12000。
- 理由：评估器判"是否完成"最需要的就是模型最后的完整产出，这一条必须完整。

**改动 2：`maxChars` 默认值改可配**
- 位置：`src/goal/evaluator.ts:120` `maxChars: number = 4000` → `12000`，并从 `GoalConfig` 读（新增 `evalContextMaxChars` 字段，默认 12000）。

**验证方式**：构造一条 8000 字符的 assistant 报告消息，调 `extractEvalContext`，断言返回内容包含报告结尾文本（而非被截在 4000 处）。

### 🟡 P1-1｜"汇总告知"型任务缺完成兜底

fast-path（`src/goal/evaluator.ts:42` `tryFastPathEval`）只认 `test_result`+"0 fail" 和 `build_result`+"success" 两类客观信号。对「审计并汇总告诉我」这种无客观完成信号的任务，评估器 LLM 是唯一判据——它一挂（P0-1）或看不全（P0-3）就彻底没兜底。

#### 确定方案 P1-1

**改动：`tryFastPathEval` 增加"报告型任务已交付"快速路径**
- 位置：`src/goal/evaluator.ts:42`（`tryFastPathEval` 函数）
- 新增判据：目标 objective 含 `/告诉我|汇总|报告|说明|检查.*结果/` 类词 **且** 最后一轮 `stop_reason === "end_turn"` **且** 最后一条 assistant text 长度 > 500 字符 → 返回 `{ satisfied: true, reason: "报告型任务已产出实质文本并 end_turn" }`。
- 效果：这类任务不再依赖评估器 LLM，fast-path 直接放行，与 P0-1/P0-3 形成三重保险。

**验证方式**：构造 objective="检查并汇总告诉我" + 一条 end_turn 的长文本 assistant 消息，调 `tryFastPathEval` 断言返回 `satisfied:true`。

### 🟡 P1-2｜TUI 对 goal 循环过程不透明（对应"过程不清晰"）

- 评估器故障只进 trace 的 `evalReason`，TUI **无醒目告警**。
- 模型反复输出大段重复报告，用户看不到"这是 goal gate 判未满足 → 续命第 N 轮"的状态标识。
- 底部状态行 `🎯 32/50 ~64%` 只有轮次进度，没暴露评估器健康度。

#### 确定方案 P1-2

**改动：goal-gate 评估失败时通过 systemMessages 推 warning 到 TUI**
- 位置：`src/query/goal-gate.ts:147-153`（catch 分支），已有 `systemMessages` 数组（goal-gate.ts:160 附近已在用 `systemMessages.push`）。
- 改法：catch 分支 `systemMessages.push({ level: "warning", text: "⚠️ Goal 评估器连续失败 N/3 次，第 N 次将自动放行。可 /goal clear 手动结束。" })`，N 从 blockedDetector 的计数取。
- 效果：用户在 TUI 直接看到评估器健康度，不再"莫名其妙反复重跑"。

**验证方式**：单测断言评估失败时 `goalGateOutput.systemMessages` 含 level=warning 且文本含"评估器"。

### 🟡 P1-3｜轨迹可观测性缺陷（v2 新增）

排查过程中发现 events.jsonl 自身的记录质量问题，影响事故复盘：
- **AfterModel 事件字段大面积为 null**：`content_types`/`ttft_ms`/`elapsed_ms` 在 31 条 AfterModel 里全为 null（值其实记在了 AfterModelRaw / RetryTelemetry 里）。字段冗余且未填充，复盘时易误判。
- **SubagentStop 的 data 为 null**：两次子代理（explore、verify）结束事件没记录耗时/结果/token，子代理开销无法从轨迹核算。
- **tokensUsed 恒为 0**：GoalGateDecision 的 `tokensUsed:0` 全程为 0，无法从轨迹看出 goal 评估消耗。

#### 确定方案 P1-3

**改动 1：AfterModel 事件删除冗余 null 字段**
- 位置：`src/trace/collector.ts` 的 `handleAfterModel` 方法（emit AfterModel 事件处）。
- 改法：AfterModel 事件只保留 `index`/`stop_reason`/`usage`，删除 `content_types`/`ttft_ms`/`elapsed_ms`（这些已在 AfterModelRaw 里有值，重复且不填充 = 误导）。或：从 AfterModelRaw 的 data 里复制过来填充。选后者（填充），保持一个事件就能看全。

**改动 2：SubagentStop 补全 data**
- 位置：emit `SubagentStop` 事件的调用点（搜索 `SubagentStop`）。
- 改法：data 补 `{ agent_id, elapsed_ms, output_tokens, status: "completed"|"error"|"aborted" }`。

**改动 3：GoalGateDecision 的 tokensUsed 计入评估器调用开销**
- 位置：`src/query/goal-gate.ts` emit GoalGateDecision 处。
- 现状：`tokensUsed:0` 因为评估失败时没 token 消耗。评估成功时的 token 也未记录。
- 改法：`evaluateGoal` 返回时带 `tokensUsed`（从 provider stream 累计），catch 时写 0 不变（确实没消耗）。成功路径填真实值。

**验证方式**：跑一次带 goal 的完整 loop 单测，断言 events.jsonl 中 AfterModel 有 `elapsed_ms!=null`、SubagentStop 有 `elapsed_ms`、GoalGateDecision（成功路径）有 `tokensUsed>0`。

### 🟡 P1-4｜评估器复用 `subAgentModels.verify` 是错误的模型选型（v2 新增）

**已坐实**：评估器 provider 在 `loop.ts:1688-1699` 构造，用的是 **同一个 `config.baseURL` 和 `config.openaiKey`**（`new OpenAIProvider(config.openaiKey, evaluatorModel, config.baseURL)`）——评估器和主模型走同一网关，只是模型名不同（deepseek-v4-pro）。因此故障不是"跨厂商网关问题"，而是**模型选型问题**：把"对抗验证子代理用的强模型 verify"错误地复用给了"只需出 512 token JSON 的快速评估"。强模型慢 + 8s 超时 = 必然失败。

#### 确定方案 P1-4
