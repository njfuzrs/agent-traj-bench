>    那起事故的形态。收窄后语义自洽：cwd=项目根时全仓变更都算，cwd=`website` 时

### 9. 权限模式 / 上下文压力提醒的"变化检测"状态挂在按消息重建的 `LoopState` 上

**结论**：`permission-reminder` 与 `context-pressure` 依赖
`state.lastSeenPermissionMode` / `state.lastSeenContextPressureLevel` 判断"是否刚变化"，

**模式归类**：P4 去重键粒度错误（状态生命周期是"每条消息"，语义需要"整个会话"）、
P8 注释与实现相反。

**证据**：
- `src/query/loop.ts:245`：`const state: LoopState = createInitialLoopState(...)` 位于
  `queryLoop()` 函数体内，每次调用都新建。
- `src/query/engine.ts:353`：`queryLoop({...})` 在 `submitMessage()`
  （定义于 `src/query/engine.ts:171`）内被调用——即每条用户消息调用一次。
- `src/query/loop.ts:730-733` 的注释自认了这个架构事实：
  > "queryLoop 由 engine.submitMessage 每条用户消息调用一次、state 每次新建、
  > turnCount 首轮自增为 1"
- 而 `src/query/permission-reminder.ts` 顶部设计注释描述的是跨消息持续语义
  （"mode 变化的那一轮强注入；非 default mode 持续时每 N 轮低频重述一次"），
  与 state 的实际生命周期矛盾。
- 独立佐证（我在主任务侧扫全部 36 个会话轨迹）：权限模式提醒确实出现重复，
  单会话内最多 2 次，文本为"权限模式已切换为「dangerously-skip-permissions」"与
  "当前权限模式为「dangerously-skip-permissions」"——即"刚切换"与"持续重述"两种措辞

**复现条件**：非 default 权限模式（如 `--dangerously-skip-permissions`、`acceptEdits`）
下发多条用户消息。default 模式不受影响。

**对模型的实际影响**：每条新消息开头都收到一次"权限模式已切换"的措辞，而实际上并没有
刚切换。措辞与事实不符，且挤占 cache 友好的静态前缀之后的位置，重复注入长文本。

**修复方向**：把跨消息语义的状态从 `LoopState` 上移到会话级容器（`SessionState` 或
engine 实例字段）。判定"是否刚变化"的状态，其生命周期必须与"变化"的语义范围一致。

两条仍值得修（合并为一次收敛即可），但不应占用"最先处理"的位置。**这也是本次补验最有

## 方法论说明

**为什么这批缺陷长期未被发现**——几乎全部依赖"叠加条件"才显形：

| 缺陷 | 显形所需的额外条件 | 最简场景下的表现 |
|---|---|---|
| 第 1 条 | 存在带 `paths:` 的规则文件 | 无该文件时完全正常 |
| 第 2 条 | 自定义 agent + 声明 tools + 走 spawn | 内置 agent 或进程内路径均正常 |
| 第 3 条 | 路径含非 ASCII 且骨架相同 | 纯 ASCII 路径永不复现 |
| 第 4 条 | frontmatter 闭合符笔误 | 写对了就完全正常 |
| 第 5 条 | 长会话触发清理分支（>6 个大输出） | 短会话走早退分支，`_meta` 完好 |
| 第 6 条 | 走 OpenAI 兼容 provider | Anthropic 路径保真 |
| 第 7 条 | 5 分钟 TTL 内切换语言 | 超时后自愈，表现为"偶发" |
| 第 7b 条 | 工具集**等数量**替换 | 数量变了则键变、自动失效 |
| 第 7c 条 | 改 skill 描述但**不改名字** | 改名字就生效，故显得"时好时坏" |
| 第 8 条 | 角色合并把内部消息与 `tool_result` 并入同一条 | 单块消息不暴露 |
| 第 9 条 | 非 default 权限模式 + 多条消息 | default 模式正常 |
| 第 11 条 | 先 JIT 注入再触发 rebuild | 顺序颠倒不复现 |
| 第 12 条 | 配置了返回 `additionalContext` 的 hook | 无此类 hook 时不涉及 |
| 第 21 条 | 会话含 `thinking` 块 + 消费方未经 usage 校准 | 校准后的压缩路径表现正常 |
| 第 22 条 | 连了 IDE 且有选区/`@提及` | 未连 IDE 时 `collectIDEContext` 返回 `{}`，无异常 |

**唯一的例外是第 20 条（`@` 提及零权限校验）——它不需要任何叠加条件，输入一个 `@路径`
即必现。** 这反而值得单独反思：它长期未被发现不是因为难触发，而是因为**没人从"注入面"
这个角度看过 `@` 展开**——它在实现上被当作"输入语法糖"，从未与"读文件要过权限"这条
不变量对账。**触发门槛低 ≠ 容易被发现；分类错位造成的盲区，比条件叠加更隐蔽。**

这解释了审计任务文档里那条教训——原缺陷的单元测试用单文件 fixture，因此一直是绿的。
**构造 fixture 时必须先想清楚"什么条件下 bug 才显形"，再据此设计场景**；用最简场景测出
"没问题"是本类缺陷的主要漏检来源。

**第二轮补验（2026-07-29）新增的一条方法论教训——指纹词选得太窄会造成假阴性**：
原文档用 4 个关键字（`reminderParts` / `system-reminder` / `additionalContext` /
`systemPrompt`）扫 `src/ide/` 等目录后判定"不构成注入面"。复核确认这 4 个词在该目录
**确实零命中**，但 `src/ide/` 恰恰是真注入面（第 22 条）——它的注入走**结构化 attachment
对象**（`{ ideSelection, ideMention }` 展开进 `buildSystemPrompt` 入参），全程不出现任何
上述字面量。
**对策：排除一个注入面时，不能只查"注入动作的关键字"（正向），必须补一次反向查
——列出 `buildSystemPrompt` / `reminderParts` / attachment 生成器的全部入参与消费方，
逐个回溯来源。** 正向 grep 只能证明"这里没写那几个词"，证明不了"这里没注入"。
这与上面 fixture 那条是同一类错误的两种表现：一个是**场景造得太简单**，
一个是**指纹选得太窄**——共性是"用一个不完备的检验通过了，就当作结论"。

**反复出现的三个结构性模式**（建议作为 review checklist）：

1. **手写字段列表 vs 类型演进**（第 5 条，第 7/7b/7c 三条，第 16 条隐患）
   `return {a, b, c}` 或手写缓存键维度列表，必然跟不上类型新增字段。本次审计里这个模式
   命中 5 次，是出现频率最高的一类。
   对策：默认透传（`{...msg}`）、缓存键从对象自动派生。

2. **同一逻辑两处并列实现，其中一处忘记传参/漏处理**（第 2 条，第 8 条三处同构，
   第 11 条，第 13 条的重复实现）
   对策：收敛为单一函数，而非给漏的那处补参数——补参数只修当次。

3. **静默丢弃 / 静默降级**（第 6 条，第 4 条的降级，第 12 条的无标注拼接）
   未识别的分支既不报错也不告警；解析失败时 fallback 到更宽松的语义。
   对策：加 default 分支 `log.warn`，参照 `src/llm/openai.ts:522-531` 的写法让丢弃可观测；
   约束缺失应 fail-closed 而非 fail-open。

4. **写好却从未接线的防线**（第 1 条的 `activeFiles`，第 14 条整个模块，
   第 13 / 15 条的死导出）
   本次审计里"机制静默死亡"命中 4 次，与审计任务文档中原事故的第 2 条根因同型。
   危险之处在于它比"没实现"更糟：代码在、注释在、测试可能也在，让人误以为风险已覆盖。
   对策：新增防线时必须同时提交一个能证明它真的跑到的用例（不是单测函数本身通过，
   而是走真实调用链）；定期用"导出符号零引用"扫描找出死防线。

**证据强度分级**（本文档采用）：

- 最强：真实轨迹（`raw.jsonl` 的 `request.system` / `messages`）——证明模型**实际**看到了什么。
  重建方式：首行 `request.messages` 为基线，后续行的 `request.new_messages` 增量累积
  （**注意**：只有首行带完整 `messages`，直接逐行读 `messages` 会严重漏计——本次审计
  初次扫描就踩了这个坑，修正后请求快照数从 36 升到 166）。
  **轨迹能证什么、不能证什么（2026-07-29 补）**：它记录的是 **provider 序列化之前的内部
  请求**，不是 wire body。所以它能证"某内容出现/未出现在内部请求里"（如第 3 条的
  frontmatter 指纹、第 21 条的 thinking 块留存），**但不能用来反推真实 token 口径**——
  实测两个记录入参几乎相同的样本（`system` 均 21348 字符、`tools` 均 30340 字符）真实
  usage 为 24590 vs 47122，差 1.9 倍。第 21 条据此**拒绝给出"低估 N 倍"的数字**，
  只保留代码级可证的漏算清单。**把"最强证据"用在它证不了的问题上，会得出精确但错误的
  结论——这比没有数据更危险。**
- 次强：`bun -e` 实跑真实函数（非 mock）+ fixture 复现。
- 最弱：仅读代码推断——本文档中此类结论均已标注"未完全验证"。
