# Builtin Skill 附属文件不释放 + delegate 模式读不到 references — 排查与修复方案

> 状态:Bug 1（附属文件不释放）代码已改、未提交;Bug 2（delegate 读不到 references）待决策。
> 记录日期:2026-06-19
> 涉及文件:`scripts/embed-builtin-skills.ts`、`src/skill/ensure-builtin.ts`、`src/skill/tool.ts`、`src/agent/sub-agent.ts`、`src/skill/builtin/*/SKILL.md`

---

## 0. 一句话结论

这次排查从「想给 code-review skill 新建一个 reference 文件放对抗验证纪律」起步,挖出**两个独立问题**:

- **Bug 1【已修】** 编译期嵌入脚本只嵌入 `SKILL.md`、只对它计哈希,`references/` `scripts/` `validations/` `evals/` `learnings.md` 等附属文件**从不进二进制、运行时从不释放到磁盘**。影响 6 个 skill 共 94 个附属文件。已修复并验证(101/101 文件正确落盘)。

- **Bug 2【待决策,本文档重点】** 即使 Bug 1 修好、references 落盘了,**delegate 模式的子 agent 依然读不到这些 references**——因为 delegate 模式压根没把 skill 目录路径告诉子 agent,且子 agent 工作目录是项目目录而非 skill 目录。

**直接结论**:「对抗验证纪律」应**写进 SKILL.md 正文**,不要新建 reference 文件。因为 sid-code 内置的 5 个核心 skill(code-review 等)全是 `mode: delegate`,对它们而言 reference 文件这条路在 Bug 2 修复前根本走不通;而 SKILL.md 正文无论哪种模式都必定加载、零可见性风险。

## 1. 这次讨论的来龙去脉(背景)

起点是一个想法:把「对抗验证纪律」(让 code-review skill 在审查时遵守的一段自查规则)单独放到一个 reference 文件里,让 SKILL.md 引用它。

排查中先确认了第一层事实(用户原始判断):

> 嵌入脚本只嵌入 SKILL.md(不含 references/),且只对 SKILL.md 内容计哈希。这意味着 references/ 文件运行时不会被释放到磁盘,所以 delegate 模式的 skill agent 实际读不到新增的 reference 文件。

这个判断**当时完全正确**——这就是 Bug 1。于是先修了 Bug 1。

但修完 Bug 1 后继续深挖 delegate 模式的真实执行链路,发现**即使 references 落盘了,delegate 子 agent 仍读不到**。这是比 Bug 1 更深一层的 Bug 2。本文档把两层都讲清楚,并给出决策建议。

## 2. Bug 1【已修】附属文件不进二进制、不释放

### 2.1 问题描述

builtin skill 的资产分两类:

- `SKILL.md` —— skill 的主提示词(frontmatter + 正文)
- 附属文件 —— `references/*.md`(模板/规则)、`scripts/*.ts`(确定性脚本)、`validations/*.json`(输出契约)、`evals/*.yaml`(评测用例)、`learnings.md`(经验回写)

`bun build --compile` 只把**被 import 的 TS/JS 模块**打进二进制,纯数据文件(SKILL.md、references 等)不会自动嵌入。为此项目用 `scripts/embed-builtin-skills.ts` 在编译前把数据文件原文生成到一个被 import 的 TS 模块 `builtin-embedded.generated.ts`,运行时由 `ensure-builtin.ts` 释放到 `~/.sid-code/builtin-skills/<name>/`。

**Bug**:嵌入脚本只读每个 skill 目录下的 `SKILL.md`(旧 `embed-builtin-skills.ts:38`),哈希也只覆盖 `SKILL.md`(旧 `:50-56`);`ensure-builtin.ts` 释放时也只写 `SKILL.md`(旧 `:70`)。所有附属文件**从不进二进制、运行时磁盘上根本不存在**。

### 2.2 影响面

```
bug-fix          附属文件 0 个  （仅 SKILL.md,不受影响）
ci-self-heal     附属文件 23 个  ← 全丢
code-governance  附属文件 16 个  ← 全丢
code-review      附属文件 23 个  ← 全丢
incident-rca     附属文件 15 个  ← 全丢
security-audit   附属文件 16 个  ← 全丢
skill-creator    附属文件 1 个   ← 全丢
```

合计 94 个附属文件运行时不存在。SKILL.md 正文里大量 `references/output-template.md`、`scripts/parse-diff.ts`、`validations/output-schema.json` 等引用全部指向不存在的文件。

### 2.3 修复方案(已实施)

**改动 1:`scripts/embed-builtin-skills.ts`** —— 从「只读 SKILL.md」改为「递归扫描整个 skill 目录」:
- 生成 `files: [{relPath, content, encoding}]` 清单(含 SKILL.md)
- 哈希覆盖所有文件的 `relPath` + `encoding` + `content`,任一文件变即触发重新释放
- 文本文件(按扩展名识别)存 utf-8 原文(diff 友好);二进制存 base64
- 保留 `rawContent` 字段(= SKILL.md 原文),向后兼容 `src/skill/bundled/review.ts:30-38` 等直接读 `rawContent` 的调用方

**改动 2:`src/skill/ensure-builtin.ts`** —— 释放循环从「只写 SKILL.md」改为「遍历 `skill.files` 按相对路径还原目录结构」(`ensure-builtin.ts:68-90`):
- 按 `relPath`(POSIX 分隔)逐段 join,`mkdir -p` 重建子目录
- base64 文件解码后写盘
- 旧嵌入数据无 `files` 字段时,兜底只释放 SKILL.md(`:77-78`)

### 2.4 验证结果(已通过)

- 嵌入脚本:7 个 skill、101 个文件,hash=`f3dc67cd9f148946`
- 真实调用 `ensureBuiltinSkillsReleased()`:101/101 文件按目录结构正确落盘,关键附属文件(references/scripts/validations/evals)抽查全过
- `SkillManager.discover()` 完整流程:code-review 的 `baseDir` = `~/.sid-code/builtin-skills/code-review`,从该目录能读到 `references/output-template.md`(1625 字节)
- `bun test`:3862 测试全过,0 失败
- `make build`:构建成功,嵌入数据确认含全部 101 文件

## 3. Bug 2【待决策】delegate 模式读不到 references(本文档重点)

修完 Bug 1 后,references 确实落盘了。但这只是**必要条件**,不是充分条件。delegate 模式还缺一环,导致子 agent 实际读不到。

### 3.1 先看两种执行模式的差异

`src/skill/tool.ts` 里 skill 有两种执行模式:

**activate 模式(`tool.ts:98-121`)** —— 注入当前对话:
```ts
const skillDir = dirname(this.skill.filePath);          // ← 拿到 skill 真实目录
const folderStructure = await scanSkillResources(skillDir); // ← 扫描并列出有哪些 references
// 输出里带 <available_resources>…列出 references…</available_resources>
```
模型因此知道「这个 skill 目录下有哪些 references 文件、它们在哪」,可以用 Read 读真实路径。

**delegate 模式(`tool.ts:126-166`)** —— 起一个独立子 agent:
```ts
const userPrompt = this.skill.prompt + (userInput ? `\n\n用户输入:\n${userInput}` : "");
//                 ↑ 只有 SKILL.md 正文进了子 agent,没有任何目录信息
const result = await subAgent.executeCustom({
  systemPrompt: `你是一个专门执行 "${this.skill.name}" 任务的代理。${this.skill.description}`,
  userPrompt,
  allowedTools: this.skill.allowedTools || [],
  // ← 没有 skillDir、没有 baseDir、没有 references 列表
});
```

### 3.2 三个硬事实(决定结论)

| 事实 | 代码位置 | 含义 |
|------|---------|------|
| SKILL.md 正文 100% 注入子 agent | `tool.ts:134` | 写在正文里的内容,子 agent 一定看得到 |
| delegate 模式**完全没把 skill 目录路径传给子 agent** | `tool.ts:126-166`(已逐行确认无 skillDir/baseDir) | 子 agent 不知道 references 在哪个目录 |
| 子 agent 工作目录 = **项目目录**,不是 skill 目录 | `sub-agent.ts:362` `:398` `workdir: process.cwd()` | SKILL.md 写「读 references/xxx.md」,子 agent 用相对路径会去**项目目录**找,不是 skill 目录 |

把三条连起来:**对 delegate 模式的 skill,新建 reference 文件这条路依然走不通**——不是文件不落盘(已修),而是子 agent 不知道去哪个目录读它,且默认相对路径会指向错误的项目目录。

### 3.3 谁是 delegate、谁是 activate(关键:核心 skill 全是 delegate)

```
mode: delegate  ← references 这条路走不通
  ci-self-heal
  code-review        ← 用户想加「对抗验证纪律」的就是它
  code-governance
  incident-rca
  security-audit

mode: activate  ← Bug 1 修复后 references 可正常用
  bug-fix
  skill-creator
```

**5 个对外交付的核心质量 skill 全是 delegate**。这正是为什么对它们来说「reference 文件」当前不是可选项。

### 3.4 那 Bug 1 修了还有意义吗?有

Bug 1 修复对 **activate 模式**完全生效:activate 用真实 `filePath` 定位目录、`scanSkillResources` 列出 references、模型读真实路径。所以修复让 activate 模式(bug-fix / skill-creator)能正常依赖 references。这是真实修复,不是白做。同时它也是 Bug 2 后续修复的**前置条件**——references 得先落盘,delegate 才谈得上读它。

## 4. 决策:对抗验证纪律放哪

### 4.1 推荐方案 —— 写进 SKILL.md 正文 ✅

**理由**:无论 delegate 还是 activate,SKILL.md 正文都必定注入子 agent,零可见性风险。code-review 是 delegate,reference 文件对它无效,正文是唯一可靠路径。

**落地步骤**(待用户给出纪律内容后执行):
1. 把「对抗验证纪律」原文接入 `src/skill/builtin/code-review/SKILL.md` 正文的合适章节(如「工作流程」或「红线」段)
2. 跑 `bun run scripts/embed-builtin-skills.ts` 重新嵌入(哈希会变,触发重新释放)
3. `bun test` + `make build` 验证

**需要用户提供**:
- 「对抗验证纪律」的具体内容(原文或要点)
- 放进哪个 skill(默认 code-review;若多个 skill 都要,逐个加)

### 4.2 备选方案 —— 新建 reference 文件 ❌(当前不推荐)

仅在 **同时做 §5 的 Bug 2 修复** 后才对 delegate skill 可行。在那之前,对 code-review 这种 delegate skill 等于写一个永远读不到的死文件——正是本次排查最初要避免的「可见性缺口」。

## 5. 可选深层改动 —— 让 delegate 模式也能读 references

如果希望 delegate skill 将来也能用 reference 文件(纪律/模板/规则拆分到独立文件,SKILL.md 正文保持精简),需要补 Bug 2。这是**独立可选项**,与 §4 的纪律落地不冲突。

### 5.1 改动思路(三选一,按侵入度排序)

**思路 A(最小,推荐)** —— 在 `executeDelegate` 里像 activate 一样注入资源清单:
- 在 `tool.ts:134` 构造 userPrompt 时,先 `scanSkillResources(dirname(this.skill.filePath))`,把 references 列表 + skill **绝对目录路径**拼进 prompt
- 同时在 prompt 里明确告知子 agent:「references 在绝对路径 `<skillDir>/references/`,读它们时用绝对路径,不要用相对路径」
- 优点:不改 sub-agent,只改 prompt 构造;子 agent 用绝对路径读,绕开 `process.cwd()` 指向项目目录的问题

**思路 B** —— 把 skill 目录作为子 agent 的 workingDir 传入:
- 给 `executeCustom` 增加 `workingDir` 参数,delegate 时传 skill 的 baseDir
- 风险:子 agent 的工具(grep/glob/bash)工作目录会从项目目录变成 skill 目录,可能影响 code-review「读项目代码」的本职(它要读的是被审查的项目文件,不是 skill 自己的文件)。需谨慎,可能要区分「读 skill 资源用 skillDir、读项目代码用 projectDir」

**思路 C** —— references 内容在嵌入期内联进 SKILL.md:
- 嵌入脚本把 references 内容直接拼进 rawContent
- 等于回到「全写正文」,失去拆分文件的意义,不推荐

### 5.2 建议

若决定做,优先**思路 A**:改动局部、不动 sub-agent 工作目录语义、用绝对路径最稳。需单独立项,本次先不做。
