# Token 与费用统计 —— 客观性/统计性审计与修复方案

> **文档性质**：审计 + 修复方案（仅设计，未改代码）。
> **审计基准**：git `master`（commit `5964e06`，已含 processStream 缓存修复）。
> **方法**：6 维度多 agent 并行深审（79 个 agent）+ 对抗式双票验证 + 人工逐条复核。workflow 确认 15 项（7×P1 / 8×P2），人工另坐实 1 项 P0 + 4 处同源缺陷。
> **日期**：2026-06-12 · **作者**：zhourusheng + Claude 协作
> **背景动机**：一次"只回复 OK"的会话费用恒为全价、缓存 99% 命中却一分没省，暴露出 token/费用链路的系统性失真。token 与费用是 Agent 的生命线，必须精准、可控、可靠。

---

## 0. 总体结论（一句话）

token/费用链路存在 **1 个资金级失控(P0)**、**3 类统计失真(P1)**、**1 类估算偏差(P1→可级联至资金)** 和若干展示口径不一致(P2)。根因高度集中在三个系统性主题：**(A) 同一逻辑存在多套并行实现导致修复不同步**、**(B) "末次值(stock)"与"累加值(flow)"两种口径在同一公式里混用**、**(C) 关键假设(汇率/定价/上下文窗口/分词系数)硬编码且无校准回路**。

---

## 1. 数据流全景（六层 + 两条生产路径）

```
                        ┌─ 主交互/无头(-p) 路径 ─────────────────────────────────┐
API响应 ─► Provider解析 ─► query/stream-processor ─► query/loop ─► updateUsage ─► SessionState(真相源)
  │         (openai/anthropic/ollama)                                                  │
  │                                                                                    ├─► calculateCost ─► totalCostUSD
  └─ 子代理 路径 ─► agent/stream-processor ─► agentic-loop ─► [✗ 从不 updateUsage]      │
                                                                                       ▼
                                                        trace/collector(metadata.json) / telemetry(usage-ledger) / Footer
```

**关键架构事实**：
- `processStream` 有 **3 套独立实现**：`query/stream-processor.ts`（主交互/`-p`）、`entrypoints/headless.ts`（SDK/eval）、`agent/stream-processor.ts`（子代理）。
- 计费真相源是 `SessionState`，但只有**主交互路径**会调 `updateUsage`。子代理路径（`agentic-loop` → `agent/stream-processor`）**完全独立、且不回写主会话**。
- `cost` 单源（SessionState 计算，collector/builder 只透传），但 `token` 有"末次 vs 累加"两套口径在不同层混用。

## 2. 核心问题清单（按严重度排序）

### 🔴 P0-1：子代理（Task/自定义 Agent）的 token 与费用完全脱漏，主会话费用系统性低估

| 项 | 内容 |
|----|------|
| **位置** | `agent/tool.ts:173-180`、`agent/custom.ts:131-134`、`agent/agentic-loop.ts:140-141` |
| **现象** | Task 工具 `subAgent.execute()` 返回的 `result.usage` 仅被拼进文本 summary 给 LLM 看，**从未调用 `sessionState.updateUsage()`**。`git grep updateUsage` 在全部子代理文件中**零命中**。 |
| **根因** | 子代理走独立的 `runAgentLoop`，其 `totalUsage` 在子代理结束后被丢弃；调用方（Task 工具）只取 `output`/`success`。 |
| **代价** | **资金失控方向 = 系统性低估**。任何使用 sub-agent / Task / 自定义 Agent 的会话，子代理烧的 token 与钱**全部不计入**总费用。对一个主打"代码审计 / security-audit / fan-out 探索"的产品，子代理往往是 token 消耗大头 —— 真实成本可能被低估数倍。`costLimit` 预算守卫对子代理消耗完全失效。 |
| **修复方向** | 子代理结束后把 `loopResult.totalUsage` 回写主会话：① Task 工具拿到 `result.usage` 后调 `parentSessionState.updateUsage(model, result.usage, duration, provider)`；② 或在 `SubAgentResult` 增加结构化 usage 并由统一归集点累加。注意区分 model（子代理可能用不同 subAgentModel），按 model 分别计费。③ 后台异步子代理（`runAsync`）路径同样要归集。 |

---

### 🔴 P0/P1-2：四套 processStream/usage 累加中，缓存字段与 inputTokens 丢弃不同步

| 项 | 内容 |
|----|------|
| **位置** | `agent/stream-processor.ts:83-86`（未修）、`agent/agentic-loop.ts:140-141`（未修）；对比已修的 `query/stream-processor.ts`、`entrypoints/headless.ts` |
| **现象** | 同一个"message_delta 累加 usage"逻辑有 4 处拷贝。本次已修主交互 2 处，但**子代理的 2 处仍丢弃 `cacheReadInputTokens`/`cacheCreationInputTokens`**，`agent/stream-processor.ts:85` 甚至连 `inputTokens` 都没累加（只加 outputTokens）。 |
| **根因** | **系统性主题 A**：多套并行实现导致一次修复无法覆盖全部路径。 |
| **代价** | 子代理即便将来接入计费（P0-1 修复后），仍会因丢缓存字段而**按全价计费 + input 计 0**，命中省钱再次失真。 |
| **修复方向** | **治本**：抽取单一 `accumulateUsage(target, eventUsage)` 工具函数，4 处全部改调它，消灭拷贝。**治标**：先把 `agent/stream-processor.ts` 和 `agentic-loop.ts` 补齐 cacheRead/cacheCreation/inputTokens 累加（与已修两处对齐）。 |

---

### 🟠 P1-3：`getNormalizedCacheUsage` 混用末次(stock)输入与累加(flow)命中 → 命中率/省钱失真

| 项 | 内容 |
|----|------|
| **位置** | `session/state.ts:138-141`（写入）+ `230-255`（消费） |
| **现象** | `updateUsage` 里 `stats.inputTokens = usage.inputTokens`（**取末次**，因含全部历史避免 N²），而 `stats.cacheReadInputTokens += ...`（**累加**）。`getNormalizedCacheUsage` 把这两个口径不一致的值一起喂给 `normalizeCacheUsage`。 |
| **根因** | **系统性主题 B**：stock 与 flow 混用。对 OpenAI/DeepSeek 口径 `uncached = max(0, input − hit)`：多轮后累加命中（可达 80k+）远超末次输入（~18k），`uncached` 被钳到 0。 |
| **代价** | **统计失真**：Footer 命中率列、会话摘要、SessionEnd 账本的"命中率/省了多少钱"全部算错（命中率虚高、uncached 虚低）。注意：**真实计费不受影响**（`calculateCost` 用的是每次调用的原始 usage，不是这个汇总），仅展示/统计失真。 |
| **修复方向** | 汇总命中率时，输入项也要用"累加口径"：要么把每次调用的 `promptTotal` 也累加进 stats（新增 `cumulativePromptTokens` flow 字段），要么在 `getNormalizedCacheUsage` 用 `cumulativePromptTokens` 而非末次 `inputTokens`。统一 stock/flow 语义。 |

---

### 🟠 P1-4：未知模型 `getPricing` 返回 null → `calculateCost` 静默返回 0，预算守卫失效

| 项 | 内容 |
|----|------|
| **位置** | `session/state.ts:179-181`（`if (!pricing) return 0`）+ `266-279`（定价表仅 10 个模型） |
| **现象** | 定价表 `MODEL_PRICING` 只含 10 个硬编码模型。任何不在表中的模型（新模型、本地 Qwen、用户自配端点）→ `getPricing` 返回 null → `calculateCost` 返回 **0**。 |
| **代价** | **资金失控方向 = 静默归零**。换个模型名费用立刻变 0，`costLimit` 守卫被绕过，用户以为"免费"实际在烧钱。这正是最初"费用恒为 0"类问题的温床。 |
| **修复方向** | ① 未知模型不静默归零：记一条 `WARN` 日志 + 用保守兜底价（或标记 `cost=null/unknown` 让上层显式展示"未知定价"而非 0）；② 定价表外置为可配置（配合主题 C）；③ 让 `availableModels` 配置项携带 price 字段，运行时优先读配置价。 |

---

### 🟠 P1-5：`getPricing` 反向前缀匹配会把短/截断模型名错配到最贵的表项

| 项 | 内容 |
|----|------|
| **位置** | `session/state.ts:272-276`（`model.startsWith(key) \|\| key.startsWith(model)`） |
| **现象** | 模糊匹配是**双向**的。`key.startsWith(model)` 这个方向危险：模型名 `"deepseek-v4"` 会匹配到表中先定义的 `"deepseek-v4-pro"`；`"gpt-4o"` 的截断 `"gpt-4"` 可能命中 `gpt-4o`。匹配取**遍历到的第一个**，依赖对象键顺序。 |
| **代价** | **资金失控方向 = 错配定价**。若实际是 flash 却配到 pro，单价贵 3 倍；反之低估。非确定性（依赖键顺序）使问题更隐蔽。 |
| **修复方向** | 去掉 `key.startsWith(model)` 反向匹配，只保留精确匹配 + 明确的 `model.startsWith(key)` 正向匹配，并对正向匹配取**最长前缀**而非首个命中。或改用显式 alias 表。 |

---

### 🟠 P1-6：上下文估算系数偏低且参与 compact 决策 → 压缩触发过晚，有溢出/截断风险

| 项 | 内容 |
|----|------|
| **位置** | `context/token.ts:9`（ASCII 系数 0.20 ≈ 5 字符/token）+ `manager.ts:100`（compactThreshold 0.7）+ `252-253`（按估算判定压缩等级） |
| **现象** | 字符级启发式对代码/JSON 这类高密度文本偏低估（真实更接近 3-4 字符/token）。该估算**不只用于展示**，还驱动 compact 决策（soft/hard/emergency）。 |
| **代价** | **可级联至资金/可靠性**：估算偏低 → 实际已接近窗口却以为还有余量 → compact 触发过晚 → 真实 prompt 超窗 → API 报错或被迫紧急压缩丢上下文。比纯展示问题严重。 |
| **修复方向** | ① 提高代码/JSON 场景的系数（或按内容类型分档）；② **关键**：compact 决策应优先用"上一次 API 返回的真实 `inputTokens`"作为锚点，而非纯字符估算（见 P1-7 校准回路）；③ 给 compactThreshold 留更大安全裕度。 |

---

### 🟠 P1-7：估算器与 API 真实 usage 之间无校准回路，偏差永不收敛

| 项 | 内容 |
|----|------|
| **位置** | `context/manager.ts:526-552`（estimateTokens 纯启发式，无反馈） |
| **现象** | 每次 API 调用都会拿到**真实** `inputTokens`，但系统从不用它回校估算器。估算与真实各算各的。 |
| **代价** | 偏差长期存在且不收敛，所有依赖估算的判断（百分比、compact、截断）持续带偏。 |
| **修复方向** | 建立轻量校准：记录"上次真实 inputTokens / 当时估算值"的比值作为动态校正因子，下次估算 ×factor。这是把多个估算问题（P1-6 / EST 系列）一次性收敛的治本手段。 |

## 4. 系统性主题与治本方向

审计发现的问题不是孤立 bug，而是三个系统性主题的反复出现：

### 主题 A：同一逻辑多套并行实现 → 修复不同步
- **表现**：4 套 usage 累加、3 套 processStream、3 套 token 估算器。
- **治本**：抽取单一权威实现——`accumulateUsage()`（usage 累加）、统一 `TokenEstimator`（估算）。所有路径强制走唯一入口。这能一次性消灭 P0-2、EST-1、EST-5。

### 主题 B：stock(末次) 与 flow(累加) 口径混用
- **表现**：P1-3（命中率失真）、DISP-1（token/cost 不可比）、ACC 系列。
- **治本**：在 `ModelUsageStats` 明确区分两类字段——`lastPromptTokens`(stock，给上下文百分比) vs `cumulativePromptTokens`/`cumulativeOutputTokens`(flow，给计费/命中率)。所有消费点显式声明用哪类。

### 主题 C：关键假设硬编码且无校准
- **表现**：汇率 1元≈$0.14、定价表 10 模型、上下文窗口、分词系数,均散落硬编码;估算无反馈回路。
- **治本**：① 定价 + 汇率外置为配置（`availableModels` 携带 price/currency），运行时读配置；② 建立估算→真实 usage 的校准回路（P1-7）；③ 未知模型显式标记而非静默归零（P1-4）。

## 5. 建议修复顺序（按 ROI）

| 阶段 | 修复项 | 理由 |
|------|--------|------|
| **第一批（资金安全，必做）** | P0-1 子代理 usage 归集；P1-4 未知模型不归零；P1-5 定价错配 | 直接影响真实费用与预算守卫，是"失控"的核心 |

| **第四批（展示一致）** | DISP 系列、PARSE-2、PARSE-4 | 用户可见一致性，量级小 |
