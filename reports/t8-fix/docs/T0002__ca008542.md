# 遥测落盘恒为空：190MB 纯换行字节，span/metric 一条未落 —— P0

> **发现方式**：做三方可观测性横向对比（`docs/summary/Observability/可观测性横向对比总表.md`）时，
> 为填 D3/D4 格子去核验落盘产物，撞见的。**不在任何人的计划里。**
> **North Star**：**底座·可度量**（span/metric 采了但出不去，等于没采）+ **深度融合企业级**（客户拿不到 span）。

## 一句话

`~/.sid-code/telemetry/` 下 **10 个文件共 190MB，全部是纯 `\n` 字节，非换行字节为 0**。
`TelemetryHookProbe` 的 5 类 span、`TokenMeter` 的 3 个 metric **全部正确构造、正确入队，
但导出恒为空数组** —— 落盘写下的每一行都只是一个裸换行符。

**批次 B 刚刚打通的 OTLP exporter 因此也是哑的**：它有 `if (spans.length === 0) return`
（`src/telemetry/exporters/otlp.ts:206,211`），收到空数组安静返回，什么都不发。

## 证据（全部可复跑）

```bash
ls -la ~/.sid-code/telemetry/
# traces.jsonl 20971268 / metrics.jsonl 20939197 / 另有 traces.1-4 与 metrics.1-5 轮转文件
du -ch ~/.sid-code/telemetry/traces*.jsonl ~/.sid-code/telemetry/metrics*.jsonl | tail -1
# → 190M total

for f in ~/.sid-code/telemetry/traces*.jsonl ~/.sid-code/telemetry/metrics*.jsonl; do
  echo "$(basename $f): 非换行字节 = $(tr -d '\n' < "$f" | wc -c)"
done
# → 全部 10 个文件均为 0

head -c 64 ~/.sid-code/telemetry/traces.jsonl | xxd
# 00000000: 0a0a 0a0a 0a0a 0a0a 0a0a 0a0a 0a0a 0a0a  ................
```

## 根因：显式 undefined 覆盖默认值，四个后果叠加

```
~/.sid-code/app.json 里有 {"telemetry":{"enabled":true,"exporters":[{"type":"jsonl"}]}}
        ↓
src/config/config.ts:996-999   转换时无条件写出三个键：
        batchSize: v.batch_size || v.batchSize          → 两者都没配 ⇒ undefined
        flushIntervalMs: v.flush_interval_ms || v.flushIntervalMs → undefined
        maxQueueSize: v.max_queue_size || v.maxQueueSize          → undefined
        ↓  注意：是**显式存在的 undefined 键**，不是键缺失
src/telemetry/bus.ts:128       this.config = { ...DEFAULT_CONFIG, ...config }
        → 展开时显式 undefined **覆盖掉** DEFAULT_CONFIG 的 512 / 5000 / 2048
```

四个后果，每个都独立成灾：

| # | 位置 | 表达式 | 后果 |
|---|---|---|---|
| ① | `bus.ts:229,241` | `splice(0, undefined)` | **恒返回空数组**，队列永不排空 |
| ② | `bus.ts:217,196` | `q.length >= undefined` | 恒 `false`，**满批刷新失效** |
| ③ | `bus.ts:145` | `setInterval(fn, undefined)` | 间隔被当 0ms，**实测 1 秒 tick 879 次**（正常 0.2 次，放大 ~4400x） |
| ④ | `exporters/jsonl.ts:45,52` | `[].map(...).join("\n") + "\n"` | 空数组 → **只写一个裸 `"\n"`** |
| ⑤ | `bus.ts:212-215` | `q.length >= undefined` 驱逐判断 | 队列**无界增长**（实测入队 5000 条一条不驱逐，期望驱逐到 ~2048） |

③ × ④ 的组合就是 190MB 的来源：每秒约 879 次写入，每次写 1 字节。

## 复现探针（本次实测输出）

```bash
# 探针 1：JsonlExporter 收到空数组
#   traces: 2 字节, 内容="\n\n"   metrics: 1 字节, 内容="\n"
# 探针 2：配置合并
#   merged.batchSize = undefined  (期望 512)
#   splice(0, undefined) 取出: 0 个；队列剩余: 3
# 探针 3：定时器
#   setInterval(fn, undefined) 在 1 秒内触发 879 次 → 放大约 4395x
# 探针 4：队列驱逐
#   入队 5000 条后队列长度 = 5000（期望 ~2048）→ 驱逐失效
```

## 为什么单测全绿也发现不了

这是本仓库第三次遇到同构的失效形态（前两次：`analytics` 1113 行 1 埋点、
单测污染真实遥测数据），值得记清楚**为什么门禁没拦住**：

1. **`tests/telemetry/otlp-exporter.test.ts`（26 例）与 `otlp-wiring.test.ts`（12 例）
   直接构造 exporter 并传入非空数组**，绕过了 `TelemetryBus` 的配置合并。
   组件验收全绿 + 链路断裂，可以同时成立。
2. **批次 B 的「本地 collector 收到完整 span 树」验收也是这样做的** —— 它验的是
   exporter 的编码正确性（OTLP/JSON 的 hex traceId、BigInt 纳秒等三个坑都对），
   **不是「生产配置路径下 span 能否出去」**。
3. **落盘失败静默**：`bus.ts:232` 的 `.catch()` 只 `debug` 级日志；而这里根本没报错——
   写入是「成功」的，写的是 `\n`。
4. **轮转掩盖增长**：50MB 才轮转，190MB 静静堆在那里没有任何告警。

> **一句话教训：验收 exporter ≠ 验收链路。**
> 「组件测试传非空数组」这个动作本身，正好绕过了唯一会出错的那一环。

## 修复要求

**主修（2 行量级）**——切断 undefined 覆盖默认值这条路：

- `src/config/config.ts:996-999`：三个键**只在有值时才写入**（或统一剔除 undefined 键）
- `src/telemetry/bus.ts:128`：合并后对三个数值字段用 `??` 兜底，**双保险**
  （只改 config.ts 治不了别的调用方直接 `new TelemetryBus({batchSize: undefined})`）

**顺带加固**：

- `exporters/jsonl.ts:43,50`：`if (spans.length === 0) return`（与 `otlp.ts` 对齐）
  —— 即使上游再出空批次，也不该写裸换行
- 清理 190MB 垃圾文件（**先确认非换行字节为 0 再删**，见上方命令）

**验收判据**（可机械检查，避免又变成「看起来做了」）：

1. 跑一个真实会话后 `jq -r '.name' ~/.sid-code/telemetry/traces.jsonl | sort | uniq -c`
   能看到 `invoke_agent` / `chat` / `execute_tool`
2. `jq -r '.name' ~/.sid-code/telemetry/metrics.jsonl | sort -u` 能看到
   `gen_ai.client.token.usage` 与 `sidcode.cost.usd`
3. **新增门禁测试**：构造 `new TelemetryBus({ enabled: true, exporters: [...],
   batchSize: undefined, flushIntervalMs: undefined, maxQueueSize: undefined })`，
   断言 `flush()` 后 exporter **收到非空数组**。
   —— 这条直接钉住本 bug 的形态：**显式 undefined 必须不能击穿默认值**
4. 断言 `setInterval` 的实际间隔不为 0（或断言合并后的 `flushIntervalMs` 是数字）

> 第 3 条是关键。本 bug 的成因是「配置合并的边界情况没有任何测试覆盖」，
> 修复必须同时装上防复发门禁，否则下一次有人加配置字段时会重演。
