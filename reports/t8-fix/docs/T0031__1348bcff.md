## 0. 必须先讲清楚的一件事：本地 claude-code 是什么

**这份 claude-code 不是官方开源仓库，而是 2026-03-31 通过 npm 发行包 source map 泄露的源码快照**（其 `README.md` 原文："本仓库镜像了一份公开暴露的 Claude Code 源码快照，该快照于 2026 年 3 月 31 日通过 npm 发行包中的 source map 泄露而被公开访问"；package name = `sid-claude-code`）。

这个事实**直接决定多个结论的解读方式**，上一版完全没意识到：

1. **代码可读、可分析**：source map 还原后是带真实变量名、注释、甚至 `AnalyticsMetadata_I_VERIFIED_THIS_IS_NOT_CODE_OR_FILEPATHS` 这种内部标记的源码（`query.ts:23`），不是混淆产物。所以"读真实代码做对标"是成立的——这正是本版做的事。
2. **测试一定为 0，且这毫无信息量**：npm 发行包**从不打包测试**。`src/__tests__` = 0 是"发行产物剥离了测试"的必然结果，**不能解读为"claude-code 不写测试 / 不健壮"**。上一版把"claude 0 测试 vs sid 44463 行测试"当成 sid 反超的核心论据，这是**拿发行产物比开发仓库的范畴错误**。
3. **是 3-31 的时间切片**：比当前官方版本旧约 2.5 个月，部分能力可能已演进。对标结论应理解为"对 3-31 快照"。

> 一句话：claude-code 快照**适合读架构、读能力实现**，**完全不适合**用它的"测试数""是否含某辅助文件"反推工程健壮性。

## 1. 一句话结论（先看这个）

**上一版的总基调"sid 用 1/4 代码实现内核骨架、并在多处反超"方向没错，但它给出的几乎每一个量化论据都站不住，导致差距图景被严重扭曲。** 实读代码后的真实结论是三句话：

1. **claude-code 的领先是"深度领先"而非"广度堆砌"**，且集中在 5 个可验证的硬骨头：**上下文压缩（数量级领先）、持久 Shell 会话、Bash 安全（tree-sitter + 30+ 注入校验）、MCP OAuth 接入、路径/命令安全分类器**。这些不是"横向功能"，是内核健壮性，是档位 B（对外可交付）的真实底线。
2. **sid-code 的反超是真实的，但只在 3 个点**：**多供应商异构 Provider 抽象、运行时循环检测、流式思考块/协议兜底工程**。这三点都源于"跑 DeepSeek/OpenAI 等非 Anthropic 模型"的现实压力——claude 在自家协议下不需要，sid 被逼出了真本事。
3. **sid 最该补的不是"功能"，是"自己战略叙事里答应了却没接住的东西"**：Git/PR 命令闭环（commit/review/pr_comments）完全缺失，而 sid 主打的恰恰是"PR-to-Prod 质量闸门"——**命令层与战略正面冲突**，这是第一优先级。

**"代码越多越健壮"在这里依然是伪命题**，但理由和上一版说的不同：不是因为"claude 没测试 sid 有测试"（那是范畴错误），而是因为 **claude 的体量近一半在 UI 渲染层和单工具的巨型实现里**（BashTool.tsx 一个文件 160KB），内核深度差距远小于 4.8× 的行数差。

## 3. 内核深度逐项对标（本版核心，全部实读代码）

> 这一章是上一版最缺的：上一版靠目录行数推断，本版逐个读了控制流。每项给"真实实现 + file:line + 裁决"。

### 3.1 Agent 主循环 —— 上一版结论"sid 反超"是**统计口径错误**

**真相**：claude 的主循环根本不是上一版说的 655 行。

- claude 活的主循环是 `src/query.ts` 的 `queryLoop`（241-1728，单个 `while(true)` 就近 1500 行），对外由薄包装 `query()`（219-239）暴露；`QueryEngine.ts`（1295 行）是 UI/会话驱动层。加上 `Tool.ts`（792）、`services/tools/StreamingToolExecutor.ts`（530）+ `toolOrchestration.ts`（188）、`services/compact/`（≈2600）、`query/stopHooks.ts`（473），**claude 主循环相关代码实测 5000+ 行**。
- 上一版的"655"只数了 `src/query/` 子目录（config/deps/stopHooks/tokenBudget/transitions ≈ 655），**完全漏掉了真正承载主循环的 query.ts 1729 行**——主循环不在那个目录里。
- sid 侧：活的主循环是 `query/loop.ts` 的 `queryLoop`（96-968，被 `query/engine.ts:193` 消费、`app.ts:284` 启动）。

**裁决：上一版"sid query(4443)+agent(4564) 反超 claude query(655)"——错误（严重误导）。** 这是拿 sid 全量比 claude 的 1/8 残片。真实情况是两边主循环都是 5000–9000 行量级、架构同构（显式 while 循环 + 不可变 state 传递），**深度相当，各有侧重**。

**两边的真实设计差异（这才是有价值的对比）**：

| 维度 | claude | sid |
|---|---|---|
| 循环出口判定 | **刻意不信任 `stop_reason`**（注释 query.ts:554），用"流式期间是否出现 tool_use block"（`needsFollowUp` 标志 558/834/1062）驱动——不依赖供应商正确设字段，更鲁棒 | **信任 `stop_reason`** 分支（loop.ts:719/811/948），但**叠了两层兜底**：F1 空参数 tool_use 退化检测（601-709，DeepSeek 大上下文特性）、F2 end_turn fall-through（712-718）。这是跑国产模型的真实工程债 |
| 设计取向 | 与自家 API 协议精密配合 | 抹平多供应商协议不规范 |

**sid 主循环的真实技术债**：`agent/loop.ts` 的 `AgentLoopRunner`（115，837 行）是**生产死代码**——全仓无任何 `new AgentLoopRunner`，仅 4+ 个测试文件实例化它。sid 实际并存**三套循环**：`queryLoop`（活，主）、`agentic-loop.ts` 的 `runAgentLoop`（活，子 agent）、`AgentLoopRunner`（死）。**应清理收敛**（与 MEMORY 记录一致）。

### 3.2 上下文压缩 —— claude **数量级领先**（这是真硬骨头）

- **claude**：多层独立系统约 2600+ 行（compact.ts 1705 + prompt.ts 374 + microCompact.ts 530）。autoCompact 阈值 = effectiveWindow − 13k buffer（autoCompact.ts:62），调 `compactConversation` 做**结构化 8 段摘要**，摘要 prompt 是**专门的 374 行 prompt 工程**（prompt.ts）。并存 microCompact / snipCompact / contextCollapse / sessionMemoryCompact / reactiveCompact 5+ 套，主循环按 snip→microcompact→contextCollapse→autocompact 顺序编排（query.ts:401-468）。熔断阈值 `MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES=3`，**注释直接写 BQ 数据驱动**（autoCompact.ts:68：1279 个会话曾连续失败 50+ 次、浪费 25 万 API 调用/天）。
- **sid**：`runCompactPipeline`（query/compact/index.ts:45-104）四级渐进 ①toolResultBudget ②snipCompact ③microcompact ④autoCompact，架构骨架对标到位。但 autoCompact 摘要 prompt 是**内联几行**（auto-compact.ts:93-101），远不及 claude 的 374 行打磨。有熔断（circuit-breaker.ts 阈值 3 + 5min recovery）。

**裁决**：sid **架构对标到位**（管道分级 / 熔断 / Session Memory 优先路径都有），但**深度差一个量级**——claude 是"数据驱动调参 + 专业摘要 prompt 工程 + 5 套子系统"，sid 是"~600 行四级管道 + 内联 prompt"。**这是 sid 该补的第一类深度差距。**

> 顺带纠正上一版另一处错误对比：上一版称"sid context(2144) 超过 claude context(1004)"。实读发现 **claude `src/context/`（1004 行）全是 React UI Context**（mailbox.tsx / modalContext.tsx / notifications.tsx），与"上下文工程"无关；claude 真正的上下文构建在 `src/context.ts`（189 行）+ 散落于 query.ts/QueryEngine.ts。**目录名撞车导致的伪对比**。但结论歪打正着：sid `context/`（2144 行）确实是扎实的纯压缩工程（manager.ts 四级压缩 / micro-compact / tool-output-masking / 落盘 + prompt cache 前缀稳定），**这块 sid 做得硬**。

### 3.3 工具系统 —— 上一版"弱 8×"被行数夸大，真实约 **2×**，但有接口债

- **真实工具数：claude 52（`tools/` 子目录）≈ 实际可用 48，sid 30（cli.ts 实际注册）。约 1.6–2×**，不是行数的 8×（50847 vs 6432）。行数差距主因是 **claude 单工具巨型化**（BashTool.tsx 160KB、ToolSearchTool 14KB）且含大量 UI 与边缘工具。
- **接口成熟度 claude 强**：claude `Tool.ts:362-497` 用 **zod/v4 强类型 schema**（运行时校验 + `z.infer` 类型推导）、`description()` **入参感知**（按上下文动态生成）、含 `searchHint`/`shouldDefer`/`alwaysLoad`（ToolSearch 协议）/`backfillObservableInput`/`outputSchema` 等高级钩子。sid `tool/types.ts` 用**手写 JSON Schema 无运行时校验**，description 无参，且**接口分裂**——`types.ts` 定义了新泛型 `Tool` 但 `registry.ts:8` 仍 `import LegacyTool as Tool`，**实际工具全跑 LegacyTool**（bash.ts:6），新接口基本没接上。

**sid 缺的高价值工具**（实读确认）：

**裁决**：**差在接口现代化（zod 校验 + 新接口落地）与模型协作类工具，不在工具数量。**

### 3.4 权限引擎 —— 上一版"弱 7×"口径错，纯逻辑约 **3.2×**，但能力代差更严重

- 上一版的 21000 = `utils/permissions`(9409, 纯逻辑) + `components/permissions`(12159, **全是 .tsx 纯 UI**)。**纯权限逻辑应只比 9409 vs sid 2950 ≈ 3.2×**。
- **但能力代差比行数代差严重**，sid 真实缺：
  1. **LLM 命令风险分类器**：claude 有 `yoloClassifier.ts`（独立 LLM 风险分类）+ `bashClassifier.ts`；**sid 只有 `checker.ts:41-76` 的 25 条硬编码正则**，极易被编码/混淆/unicode 绕过。
  2. **规则按来源分层**：claude `ToolPermissionContext`（Tool.ts:123-138）按 source 分桶（user/project/policy 优先级）+ strippedDangerousRules + bypass 可用性；sid `rules.ts:147` 简单数组 merge，**不分来源**。
  3. **路径安全**（最大单点差距）：claude `filesystem.ts`（62254 字节）+ `pathValidation.ts`（16249 字节）；**sid `path-validator.ts` 仅 222 行**。
  4. shadowed 规则诊断：claude 8050 行 vs sid 91 行。

**裁决**：行数 3.2×，但**能力代差（LLM 风险分类 / 来源分层 / 路径安全）远大于 3.2×**，是档位 B 安全底线的真实缺口。

### 3.5 Bash 工具 —— 上一版"弱 20×"**成立且不虚**，最致命是无持久 Shell

- 行数：claude bash 总盘 ~24500 行（utils/bash 12093 + tools/BashTool 12411，含 bashSecurity.ts 102KB、bashParser.ts 130KB、ast.ts 112KB）vs sid ~1190 行（tool/bash.ts 408 + tool/bash/ 564 + shell-parser 215）。**真实约 20×**。
- **三个致命能力差距**（实读确认）：
  1. **持久 Shell 会话**：claude `ShellSnapshot.ts`（582 行）快照用户 aliases/functions/options 注入持久 shell，**跨命令保留 cwd/env**；**sid `bash.ts:211` 每次 `spawn` 全新进程**——`cd`、`source venv/bin/activate`、`export` 在后续命令全部失效。**这是最影响实用性的代差。**
  2. **注入防护**：claude `bashSecurity.ts` 有 **30+ 个 validate 函数**（IFS 注入 / /proc/environ / 混淆 flag / brace 扩展 / unicode 空白 / CR 注入 / heredoc 替换…）+ tree-sitter AST 解析（treeSitterAnalysis.ts）；**sid 用 25 条正则 + 手写状态机**（shell-parser.ts），无 heredoc/unicode/混淆防护。
  3. sed 当编辑器解析：claude `sedEditParser.ts` + `sedValidation.ts`（21KB）；sid 49 行仅检测 `-i`。
- sid 的一个**真实亮点**：超时自动后台化（bash.ts:224-320，超时不杀进程转 PID），设计上优于直接 kill。

**裁决**：Bash 是 sid 最实打实的深度缺口，**持久 Shell 会话应优先补**（直接影响日常可用性）。

### 3.6 MCP —— 上一版自相矛盾，真相是"传输广度 sid 略胜，企业接入面几乎为零"

- **sid 的硬缺口**：
  1. **OAuth 全链路完全缺失**：claude `services/mcp/auth.ts`（2465 行，PKCE / 动态注册 / discoverOAuthServerInfo / token 刷新）；sid `grep -i oauth` 仅命中注释，只能用 `manager.ts:291` 静态 Bearer token。**这是接入 claude.ai / Linear / Sentry 等远程 MCP 的硬门槛。**
  2. Elicitation：claude 10166 行（含校验）vs sid 1431 行（薄）。
  3. 官方 registry 发现 + claude.ai connector + channel 级权限：sid 全无。

**裁决**：协议骨架 sid 够用，**企业级接入面（OAuth）是该补的硬缺口**。

### 3.7 LLM Provider —— 上一版"sid 3 家反超 claude 单家"**方向对、表述错**

- **claude 不是单家**：`utils/model/providers.ts:4` 定义 `firstParty | bedrock | vertex | foundry` **4 个渠道**（环境变量切换），`bedrock.ts` 真实调 `@aws-sdk/client-bedrock`。**但这 4 家都只跑 Anthropic 模型**（`.filter(includes('anthropic'))`）——是"同一 Claude 模型的多云接入"，**不是异构多厂商**。
- **sid 才是真异构多厂商**：`registry.ts:187` createProvider 三 case（anthropic 400 行 / **openai 821 行真实协议翻译** / ollama 36 行薄）+ `provider.ts:9` ProviderCapabilities 抽象（streaming/tools/thinking/vision/promptCaching/parallelToolCalls）+ 非流式降级路径。配套 fallback.ts(844 行)/protocol-sentinel.ts/quota.ts。**sid 缺 bedrock/vertex**。
- **API 层深度 claude 碾压**：claude `services/api/` 13187 行（claude.ts 3419 + withRetry 822 + usage/overageCreditGrant/ultrareviewQuota/rate-limit-options/promptCacheBreakDetection——**计费/额度授信/超额/限流一整套商业化基础设施**）；sid 5595 行够用但无商业计费（合理，sid 非托管服务）。

**裁决**：准确表述是——**sid 在"异构多厂商模型抽象"上确实领先（claude 锁 Anthropic）；claude 在"单模型多云接入 + 商业 API 治理"上远超 sid**。两种不同的"多"。sid 的多 Provider 是符合"国内 Build"战略的真实差异化。

### 3.8 容错（重试/熔断/循环检测）—— sid 在循环检测上**真实完胜**

| 机制 | claude | sid |
|---|---|---|
| 模型 fallback | FallbackTriggeredError 切模型（query.ts:894） | ModelFallback 引擎 844 行（x-should-retry / persistent retry / 退避），**更厚** |
| 流超时 | 交给 SDK | **自管心跳 60s + 整体 300s**（stream-processor.ts:57-87）+ 超时重试 2 次 |
| **循环检测** | **几乎没有**——仅 token budget 的 diminishingReturns + 系统 prompt 文字劝导（"don't retry identical action blindly"），**无运行时重复工具检测器** | **完备**——LoopDetector(485 行)含 ToolCallLoopDetector / **ToolShapeLoopDetector**(对参数变体不敏感) / ContentLoopDetector / **LLM 认知循环检测**(LOOP_DETECTION_PROMPT) + 自动恢复 |

### 3.9 Skill / 子 Agent / Memory —— 各有胜负

## 7. 核心洞察总结

1. **行数差 4.8×，但内核深度差只有 2–3×。** claude 的体量近一半在 UI 渲染层（106754 行）和单工具巨型化（BashTool.tsx 160KB）里，加上商业化 API 基础设施（计费/额度/超额）和横向功能（Computer Use/远程/Vim）。这些对"通用编程基座"内核不是必需。

2. **claude 的真实领先是"深度"，集中在 5 处可验证硬骨头**：上下文压缩（数量级）、持久 Shell、Bash 安全、MCP OAuth、路径/命令安全分类器。这些是档位 B 的底线，是该补的。

3. **sid 的反超是真实的，集中在 3 处，且都源于"跑非 Anthropic 模型"**：异构多 Provider 抽象、运行时循环检测、流式思考块/协议兜底。claude 在自家协议下不需要，sid 被现实逼出了真本事——**这是要继续深化的差异化**。

4. **sid 最该补的是"战略叙事的窟窿"**：主打 PR-to-Prod 质量闸门，却没有 Git/PR 命令闭环。claude 的实现形态（prompt 模板 + 工具白名单）照搬成本极低，应列第一优先级。

5. **上一版的总方向没错，但论据几乎全错**——claude 主循环不是 655 行、权限不是弱 7×、工具不是弱 8×、claude 不是单 Provider、context 拿错目录对比、MCP 自相矛盾、"0 测试"是范畴错误。**教训：对标不能数目录行数 + 猜功能，必须读控制流。** 本版每条结论都带 file:line，可复核。

6. **"代码越多越健壮"在这里是伪命题**——但理由是 claude 的体量大量花在 UI 与商业化上、且测试数据因发行包剥离而失真，**不是因为 sid 测试多就更健壮**。sid 应继续走"显式工程化 + 跑通多模型"的差异化路线，把精力投在上面那 5 处深度缺口和 1 处战略窟窿上，而非盲目堆代码量或追横向功能。
