## 0. TL;DR

这次 400 的真相（已逐条 file:line 坐实，纠正了两个早期错判）：

| 早期判断 | 坐实结果 | 纠正 |
|---|---|---|
| 「eval 不用 deepseek，结构性免疫此 bug」 | `sid-code-live.ts:428` eval 默认 provider = **deepseek-v4-pro** | ❌ 错判：eval 就是 ds 跑 |
| 「ADR-039 可能没执行」 | `tool-executor.ts:177-249` 兜底逻辑**完整落地** | ❌ 错判：ADR-039 已执行 |
| 「executeTools 有缺口」 | executeTools 单函数不变量**滴水不漏** | 部分对：缺口不在这里 |

**真实根因**：协议不变量只在**生产端的一个函数**（executeTools）被守住，但「消息历史完整性」这个**全局不变量**缺一个**统一的、发送前的强制关卡**。孤儿 tool_use 可从 executeTools 之外的路径（中断、followup 时序、plan-mode 转换）进入消息历史，而 `openai.ts:convertMessages` 发送前**零校验**（全库搜证：无任何 validate 包裹），原样转发即 400。

**四道防线的盲区**：

1. **协议防线**：守在生产端单点（executeTools），消费端（convertMessages 发送前）盲。← 本次直接根因
2. **测试防线**：3253 个 test 集中在**函数级**，无「中断/多轮累积」的会话级不变量测试。
3. **可观测防线**：崩溃只落 `metadata.json`，**不落 messages**（`uploader.ts:468`）→ 无法验尸。
4. **UI 防线**：`src/ui` 仅 2 个测试（还是本次新加的），几乎裸奔。

**方案主线**：先补**最便宜、最高杠杆**的两道——「发送前协议关卡 + 崩溃落 messages」，让「已知 bug 复发」和「无法验尸」当场显形；再系统性补测试矩阵与 UI 测试。

## 1. 根因的精确结构（file:line 实证）

### 1.1 生产端守住了（ADR-039 兑现）

`src/query/tool-executor.ts:218-249`：组装层强制「N 个 tool_use → N 个 tool_result」，缺失 idx 用 `yieldMissingToolResults` 补 error 占位 + `log.error` 告警。**该函数对任意输入，出口不变量成立**。`tests/agent/tool-result-invariant.test.ts` 4 条覆盖：基线/并发抛错/pre-hook 异常/abort 上抛。

### 1.2 但全局不变量没有统一关卡

孤儿 tool_use 可从 executeTools **之外**进入 `ctxMgr` 消息历史：

- **中断路径**（本次 metadata = `user_interrupt`）：`loop.ts:587-607` 的 try/catch 补齐后 `:606 throw err` 上抛；补齐依据 `collectToolResultIdsFromBlocks(ctxMgr.getMessages())`。若 assistant 消息（`:500` addMessage）与 executeTools 之间被中断切开，或补齐与上抛之间状态错位，历史可残留孤儿。
- **followup 时序**（`loop.ts:609-616`）：ADR-019 注释自己点出——followup 的 user 消息必须排在 tool_result **之后**，否则违反协议。这是一条「靠注释提醒、无机制强制」的脆弱约束。
- **plan-mode 转换**（`tool-executor.ts:255-260`）：转换注入 followup，时序同样脆弱。

### 1.3 消费端是盲的（本次直接根因）

`src/llm/openai.ts:68 convertMessages` 逐条转换消息：assistant.tool_use → 顶层 tool_calls，user.tool_result → 独立 role:"tool"。**全库搜证**（`grep convertMessages src/`）：它只在 `:150`（stream）/`:255`（non-stream）被直接调用，**无任何发送前校验包裹**。输入历史有孤儿 → 原样转发 → API 400。

ADR-039 **否决了**在 convertMessages 兜底（方案 B，理由「治标不治本，脏数据已进历史」）——决策正确，但留下代价：**这里连一个"发现孤儿就报警 + 落盘脏历史"的哨兵都没有**。本方案不违反 ADR-039（不在此修数据），而是加**只读校验 + 告警关卡**。

### 1.4 可观测端无法验尸

`src/trace/uploader.ts:444 persistMetadataSnapshot` → `:468 writeFileSync(metadata.json)`。**全库无 messages 落盘逻辑**。崩溃 session `914346ad/` 只有 `metadata.json` + `.uploaded`，**messages 从未被写本地**。CLAUDE.md 评测纪律不变量第 1 条「transcript 必落盘」在真实交互路径**未被遵守**。

## 3. 执行顺序（按杠杆排，不是按防线排）

**第一波（P0，本次根因 + 验尸能力，1-2 人天）**——做完这波，「已知 bug 复发」和「无法验尸」立即显形：

1. **D3-1 + D3-2**（崩溃落 messages + 协议违例专项落盘）：先补验尸能力，**这样后续任何复发都有现场**。最便宜、最高杠杆，先做。
2. **D1-1**（发送前孤儿校验关卡）：本次 400 的直接修复，覆盖所有孤儿路径。
3. **D1-2 + D2-2**（中断路径测试 + 长多轮 case）：复现本次 bug 的两个角度，做完它当场变红→修绿。
4. **D2-1**（provider 契约测试）：锁死 ≥3 家 provider 不再漏。

**第二波（P1，系统性补盲，本 sprint）**：D1-3/D1-4（时序不变量+共享断言）、D2-3/D2-4（中断 case+盲区扫描）、D3-3/D3-4（归因摘要+live 纪律）、D4-1/D4-2/D4-3（UI 测试铺开）。

**第三波（P2，长期）**：D4-4（UI CI 统计）+ 路线图其余 UI 项。

## 4. 为什么这样分（设计理由）

- **先补可观测再补修复**：D3 在 D1 之前做。理由——修复可能不完整（这次 ADR-039 就是「修了仍漏」），但只要有验尸能力，下次复发能立刻定位，不再「只剩 metadata」。可观测性是「修复的修复」。
- **关卡 > 单点兜底**：D1-1 在消费端出口设**统一关卡**，对齐 ADR-039 的同一哲学（「不变量在出口强制，不靠每个入口自觉」）——ADR-039 在 executeTools 出口做了，本方案在 provider 发送出口再做一道，双保险。
- **不违反 ADR-039**：D1-1 是**只读校验 + 告警 + 落盘**，不在 convertMessages 修数据（ADR-039 方案 B 否决的是「修数据」）。脏数据仍由生产端（executeTools/loop）负责不产生，消费端只负责「发现并报警」。
- **测试从函数级升到会话级**：3253 个 test 不少，但本次证明「函数对≠会话对」。D1-2/D2-2 专测「多轮累积 + 中断」这类跨函数、跨轮次的不变量。

## 5. 待确认 / 风险

- **[待定·D1-1 strict 边界]**：strict 模式（抛错）只在 eval/test 开，生产开会不会因误报中断用户？需先用 D3-2 的落盘数据观察误报率，再决定生产是否升级为 strict。
- **[待验证·D1-2 中断时序]**：本方案推断「中断切开 assistant 与 executeTools」是孤儿来源之一，但**未在崩溃现场坐实**（因为没落盘——正是 D3-1 要补的）。D1-2 测试写出来若无法复现，需结合 D3-1 落盘的真实现场重新定位。**诚实标注：1.2 节的中断路径是基于代码结构的强推断，非现场实证。**
- **[审批]** D1-1/D1-2/D1-3/D1-4 触 `core_code`，走 §0.3 L3 人审 diff；D1-1 还需补一条 ADR（记录「消费端加只读关卡」决策 + rejected alternatives + 引用 ADR-039 为什么不够）。
- **[范围]** 本方案聚焦「协议/测试/可观测/UI」四道防线，不含性能、安全等其他维度——那些需另开 audit。
