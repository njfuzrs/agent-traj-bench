## 一、问题现象

用户反馈：sid-code 每轮都往 user turn 注入一大堆内容——`<available-deferred-tools>`(100+ 个 MCP 工具名) + `<current-date>` + `# 权限模式: 跳过权限（危险）` + Skills 列表 + **CLAUDE.md 全文（超长）** + `<git-status>`。用户质问："不应该是一次注入就 OK 了吗？为什么不断重复注入？"

在排查过程中，sid-code 对**当前这个排查会话本身**反复复现了同一现象（见第六节"活体复现记录"），注入量逐轮递增，第 4 轮达到 100+ 个 MCP 工具名。

## 二、核心结论（先给结论，后给证据）

**不是所有"每轮都出现"都是 bug。要区分两类：**

| 类别 | 内容 | "每轮出现"是否是 bug | 原因 |
|------|------|---------------------|------|
| **A. system prompt 附件** | CLAUDE.md / current-date / git-status / Skills 列表 / 权限模式附件 | **不是 bug** | 它们在 system role，LLM API 标准行为是每次请求都带完整 system prompt。这是"携带"不是"重复注入" |
| **B. user turn reminder** | deferred-tools / 权限模式 reminder / MCP instructions | **部分是 bug** | 它们经 `injectReminders` 注入 user message，每轮重新拼到 user turn。其中 deferred-tools 每轮都注无节流，权限模式有双通道重复 |

**真正的"重复注入"bug 有两个：**

1. **权限模式双通道重复注入**（确认 bug）：同一份权限模式文案 `# 权限模式: 跳过权限（危险）` 同时进 system role（附件）和 user role（reminder），同一轮出现两次。
2. **deferred-tools 每轮全量重注入**（设计取舍问题）：100+ 个工具名每轮都重新拼到 user message，无节流、无去重。

## 三、决定性证据链

### 证据 1 — CLAUDE.md / date / git-status / Skills 全在 system role（不是 bug）

`src/config/attachments.ts` 定义了所有附件的生成函数：

- `generateClaudeMdAttachment`（`:180-197`）→ 返回 `<system-reminder># claudeMd...` 包裹的附件
- `generateDateAttachment`（`:392-400`）→ 返回 `<current-date>` 附件
- `generateGitStatusAttachment`（`:234-323`）→ 返回 `<git-status>` 附件
- `generateSkillListingAttachment`（`:482-494`）→ 返回 Skill 摘要附件
- `generatePermissionModeAttachment`（`:329-337`）→ 返回权限模式文案附件

这些附件在 `src/config/system-prompt.ts:377-453` 被 `buildSystemPrompt` 收集到 `attachments` 数组，按 `PRIORITY` 优先级排序后拼进 system prompt 字符串。最终经 `loop.ts:1083` 的 `sendParams.system = ctxMgr.getSystemPrompt()` 单独传给 LLM API 的 `system` 参数——**不在 messages 数组里**。

→ "每轮都带 CLAUDE.md 全文"是 LLM API 标准行为（每次请求必发完整 system prompt），**不是 sid-code 重复注入 bug**。

### 证据 2 — 轨迹文件验证：CLAUDE.md 在 system role，不在 user role

`session.traj` 的 `history[0]`（system role，37805 字符）末尾含 CLAUDE.md 全文 + git-status；`history[1]`（user role，2697 字符）只有 deferred-tools + MCP instructions + commit prompt。

→ 证明 CLAUDE.md 只进 system role，没有第二条通道把它重复注入到 user message。

### 证据 3 — 权限模式有双通道重复注入（确认 bug）

**通道 1：system 附件通道**（`attachments.ts:329` + `system-prompt.ts:398`）：
```ts

  attachments.push(generatePermissionModeAttachment(ctx.permissionMode));
}
```
→ 权限模式文案 `# 权限模式: 跳过权限（危险）` 进 system role（system prompt 附件）。

**通道 2：user reminder 通道**（`permission-reminder.ts:53` + `loop.ts:723`）：
```ts
// loop.ts:715-723
if (!isBaseline && (changed || turnsSinceMode >= PERMISSION_MODE_REMINDER_INTERVAL)) {
  const modeReminder = buildPermissionModeReminder(mode, changed);
  // ...
  if (modeReminder && !isDuplicate) {
    reminderParts.push(modeReminder);  // ← 注入 user turn
```
→ 权限模式文案（同一份 `PERMISSION_MODE_DESCRIPTIONS`，`permission-reminder.ts:20` import）又进 user role（reminder 通道）。

**两条通道用同一份文案源**（`attachments.ts:126-171` 的 `PERMISSION_MODE_DESCRIPTIONS`），`permission-reminder.ts:20` 直接 import 它。

→ 同一份权限模式文案同时出现在 system role 和 user role，**同一轮出现两次**。本次活体复现直接验证：权限模式文案在同一轮的 user turn 开头（`<system-reminder>` 块内）和中段（current-date 后裸文本）各出现一次。

### 证据 4 — deferred-tools 每轮全量重注入（无节流）

`loop.ts:1065-1078`（commit `b9781b406`，2026-06-18）：
```ts
// 工具延迟加载：每轮注入 <available-deferred-tools> 提醒
// 单独处理（不进 reminderParts）：它每轮都注、非节流，且内容独立成块。

```

注释明说"每轮都注、非节流"。当接了 6 个 MCP server（chrome-devtools/context7/lark-mcp/master-mcp/playwright/tavily/vibe-coding），deferred 工具名达 **100+ 个**，每轮都把这 100+ 个工具名重新拼到 user message 前面。

→ 这不是"一次注入就 OK"，而是每轮都全量重注入，且无去重、无节流。

## 五、为什么之前没发现

### 5.1 负收益防线审计发现了 reminder 通道的"零新信息注入"，但没发现双通道

`permission-reminder.ts:29-44` 的注释记录了"负收益防线审计 发现 4（2026-07-30）"：

> `lastSeen === undefined` 是会话首轮的基线初始化，不是切换。旧判据把首轮算成 changed，导致每个以非 default mode 启动的会话首轮都强注入一条——实测 24 个会话全程 mode 从未变过，三个会话 turn#1 的注入逐字节完全相同，共 37 次零新信息注入。

→ 审计发现并修了"reminder 通道内部的零新信息重复注入"（首轮基线 + 去重），但**审计的范围只限 reminder 通道内部**，没有跨通道检查"reminder 通道注入的内容是否与 system 附件通道重复"。双通道重复注入不在审计视野内。

### 5.2 双通道的设计意图是互补，实际却重叠

`permission-reminder.ts:7-14` 的注释解释了引入 reminder 通道的初衷：

> 根因：generatePermissionModeAttachment 生成的 mode 行为指南经 buildSystemPrompt 注入，但 system prompt 有缓存（CACHE_TTL），且仅在 init / CLAUDE.md 变更时重建，主循环每轮不重建。用户中途切 mode 后，模型上下文里仍是会话启动时的旧值。

→ 设计意图：system 附件通道负责"首轮注入"，reminder 通道负责"运行时切换后刷新"。两者**本应互斥**（首轮走 system，切换走 reminder）。但实际实现没有让它们互斥——system 附件通道在每次 `buildSystemPrompt` 时都注入（包括切换后的重建），reminder 通道在切换时也注入，**切换那一轮两通道同时注入同一份文案**。

## 6.5 业界标杆对照（Claude Code 源码核查，2026-07-30）

> 核查对象：`/Users/zhourusheng/Code/person/claude-code/src`（1964 个 ts/tsx 文件）。
> 结论：**CC 的架构与本文档原方案（§7 方案 A/B）恰好相反。原方案的三条论证全部不成立，必须推翻。**

### 6.5.1 决定性发现 1 — CC 把 deferred-tools 从 system 前置**迁移到了 user 侧增量附件**

CC 有两条 deferred-tools 通道，由 `isDeferredToolsDeltaEnabled()`（`utils/toolSearch.ts:629`）门控，**新路径正是本文档 P1 想废弃的那条**：

```ts
// services/api/claude.ts:1327-1345（旧路径，正在被淘汰）
// When the delta attachment is enabled, deferred tools are announced
// via persisted deferred_tools_delta attachments instead of this
// ephemeral prepend (which busts cache whenever the pool changes).
if (useToolSearch && !isDeferredToolsDeltaEnabled()) {
  messagesForAPI = [
    createUserMessage({
      content: `<available-deferred-tools>\n${deferredToolList}\n</available-deferred-tools>`,
      isMeta: true,
    }),
    ...messagesForAPI,   // ← 前置到消息序列最前面
  ]
}
```

新路径 `getDeferredToolsDelta`（`toolSearch.ts:646-706`）的关键设计：

```ts
// 扫描历史里已有的 deferred_tools_delta 附件，重建"已播报过"的集合
for (const msg of messages) {
  if (msg.attachment.type !== 'deferred_tools_delta') continue
  for (const n of msg.attachment.addedNames) announced.add(n)
  for (const n of msg.attachment.removedNames) announced.delete(n)
}
const added = deferred.filter(t => !announced.has(t.name))   // ← 只发新增
if (added.length === 0 && removed.length === 0) return null   // ← 无变化不发
```

**三个可直接借鉴的设计点**：

1. **发增量，不发全量**。`addedNames` / `removedNames`，不是每次 100+ 个全量。
2. **去重状态从历史消息重建，而非内存变量**。这是它抗 compact / 抗 resume 的根本原因——内存 Set 会在 compact 后丢失导致重播，而"扫历史附件"天然与上下文同生命周期。
3. **落 user role，包 `<system-reminder>`**（`utils/messages.ts:4178-4192` → `wrapMessagesInSystemReminder`），且**追加在用户消息之后**（`processTextPrompt.ts:84` `messages: [userMessage, ...attachmentMessages]`）——即 CC 自己就是"用户指令在前、注入在后"，与上一份文档的"拼接顺序后置"修复方向一致。

### 6.5.2 决定性发现 2 — CC 明确记录了"把列表塞进 system/tool 描述"的代价

`utils/attachments.ts:1481-1487` 对 agent 列表做同类迁移时留下的注释，是对本文档 P1 方案 B 最直接的反驳：

> The agent list was embedded in AgentTool's description, causing **~10.2% of fleet cache_creation**: MCP async connect, /reload-plugins, or **permission-mode change** → description changes → full tool-schema cache bust. Moving the list here keeps the tool description static.

两点值得注意：
- 「MCP async connect → 列表变化 → cache 全量重算」正是我们 P1 方案 B 会踩的同一个坑，CC 用实测数据量化了代价：**10.2% 的 cache_creation**。
- 「**permission-mode change** → cache bust」直接命中我们 P0 方案 A 的核心动作（"mode 切换即重建 system prompt"）。CC 把它当作**要消除的问题**，而我们的原方案把它当作**要新增的机制**。

### 6.5.3 决定性发现 3 — CC 不给非 plan 的权限模式做"每轮文案注入"

我枚举了 CC 全部 59 种附件类型（`grep "type: '" utils/attachments.ts`），与权限模式相关的只有：

| 附件类型 | 触发条件 | 是否每轮 |
|---------|---------|---------|
| `plan_mode` / `plan_mode_reentry` / `plan_mode_exit` | 仅 `mode === 'plan'`（`attachments.ts:1191`） | **否**，`TURNS_BETWEEN_ATTACHMENTS` 节流 + full/sparse 分档（每 N 次才发全文，其余发精简版） |
| `auto_mode` / `auto_mode_exit` | 进入/退出 auto 模式 | 否，状态迁移时一次 |
| `command_permissions` / `hook_permission_decision` | — | `normalizeAttachmentForAPI` 里 **`return []`**（`messages.ts:4253-4261`，根本不发给模型） |

**`bypassPermissions` / `acceptEdits` 这些 mode 没有任何"行为指南文案"注入通道**——`grep -rn "bypassPermissions"` 命中的 20 个文件全是权限判定、UI 展示、设置迁移，没有一处往模型上下文写约束文案。

这推翻了原方案 A 的安全性论证。**权限的强制点在 PermissionChecker（代码强制），不在"模型看到文案后自觉遵守"。** 我们 §7 原文写的"8 轮盲区不可接受，模型可能在盲区内执行本该被约束的写操作"——如果这句话成立，那说明 PermissionChecker 本身有洞，靠往上下文塞文案去兜底是错误的补法（而且塞了也只是概率性生效）。CC 只对 **plan mode** 做每轮注入，因为 plan 是**行为模式**（"先规划再执行"无法用权限规则表达，只能靠模型自觉）；`deny-write` / `bypassPermissions` 是**权限模式**，由 checker 硬拦，不需要模型配合。

顺带印证：CC 连 plan mode 这种真需要模型自觉的场景，也不是"每轮全文注入"，而是节流 + full/sparse 分档（`attachments.ts:1224-1231`）。我们的 8 轮节流 + 逐字节去重，粒度上已经和 CC 同级甚至更严。

### 6.5.4 多 provider 立场差异（不能照抄 CC 的部分）

CC 只面向 Anthropic 协议（含 Bedrock/Vertex 网关），sid-code 要同时支持 OpenAI 族。这带来一个 CC 完全不需要考虑的约束：

**`openai.ts:277-291` 的 `prependSystemMessage` 会把 system prompt 动态区搬到 messages 末尾、以 `role: "user"` 落地。** 运行时实测（`buildSystemPrompt` + `splitSystemByDynamicBoundary`）：

```
静态区含 CLAUDE.md ? false        ← CLAUDE.md 在动态区
动态区含 权限模式 ?  true         ← 权限附件在动态区
动态区含 git-status ? true
动态区含 skill ?     true
动态区长度 991 / 静态区长度 4746
```

根因：`attachments.ts` 里只有 `generateOutputStyleAttachment`（`:368`）一处调了 `stableAttachment`，其余附件（含 `generatePermissionModeAttachment:331`、`generateClaudeMdAttachment:182`、`generateSkillListingAttachment:488`）都返回**裸对象、无 `cacheStability`**，而 `system-prompt.ts:509` 的分拣规则是「未标记按保守策略当 dynamic」。

**这个事实同时推翻两条原论证**：

1. **P0 方案 A 的"权限文案只在 system role 出现一次"达不到。** 在 OpenAI 族（deepseek 是本项目主力），system 附件那份仍以 user 消息落地。删掉 reminder 通道只是从"两次"变成"一次但仍在 user role"，宣称的架构收益不存在。
2. **P1 方案 B 的"不占 user turn 空间"完全归零。** `deferredToolNames` 加进 `SystemPromptContext` 后同样落动态区（新字段无 `cacheStability` 标记），被 `prependSystemMessage` 原样推回 user 消息末尾。**100+ 工具名从"user turn 前部"搬到"user turn 末部"，一个 token 都没省，还多绕一层间接。**

推论：**在多 provider 前提下，"放 system prompt 动态区"不是一个能省 user turn 的动作**——对 Anthropic 族它是独立 cache block，对 OpenAI 族它就是一条 user 消息。任何以"搬进 system 动态区就不占 user turn"为前提的方案，在本项目都不成立。

### 6.5.5 顺带修正 §三 的一处归因错误

原 §三核查结论（`:310`）写：

> 本次活体复现中这些内容出现在 user turn 注入流里，是 sid-code 排查场景的特殊展示机制（harness 把 system prompt 内容回显给排查中的 AI 看）

**这条归因是错的。** 我 grep 了 `回显` / `systemPromptEcho` 等，代码里不存在任何这样的机制。真实原因就是 6.5.4 的 `prependSystemMessage`：OpenAI 族把动态区（CLAUDE.md 全文 + date + git-status + skills 全在里面）以 user 消息推到序列末尾。

这不改变 §二 表格「A 类不是 bug」的结论（同一份内容每轮携带，而非同轮重复两次，仍是 LLM API 的正常代价），但**必须修正"它在 system role、不占 user turn"这个说法**——在主力 provider 上，CLAUDE.md 全文确实每轮以 user 消息重发。用户看到的"每轮一大堆注入"有相当一部分来自这条路径，不是排查场景的特殊展示。

**原"排除保留 reminder 通道"的理由（已失效）**：

reminder 通道有 **8 轮节流盲区**——`PERMISSION_MODE_REMINDER_INTERVAL = 8` 意味着长任务中途最多连续 8 轮看不到权限约束文案。对 `deny-write` / `dangerously-skip-permissions` 这类**安全约束**，8 轮盲区是不可接受的隐患：模型可能在盲区内执行本该被约束的写操作。相比之下 system 附件通道每轮都在（每次请求必带完整 system prompt），无盲区。

> **失效原因**：这段推理把"模型看到文案"当成了权限的执行机制。实际强制点在 `PermissionChecker`（代码硬拦），文案只是告知。如果"模型在盲区内执行了本该被约束的写操作"真会发生，那是 checker 有洞，往上下文塞文案只是概率性缓解，不是修复。CC 对 `bypassPermissions` / `acceptEdits` / `deny-write` 全无文案注入通道，只对 plan mode（**行为模式**，无法用权限规则表达）做节流注入。见 §6.5.3。

**原方案 A 完整版的效果（三条全部不成立）**：

1. ~~**权限文案只在 system role 出现一次**~~ → OpenAI 族仍落 user role（§6.5.4）。
2. ~~**每轮可见，无 8 轮节流盲区**~~ → 前提错误，权限不靠模型自觉（§6.5.3）。
3. ~~**切换当轮生效**~~ → 代价是每次切换击穿全量 system cache，CC 正在反向迁移（§6.5.2）。

**原"代价与取舍"（已失效）**：

- mode 切换当轮会击穿一次 prompt cache（重建 system prompt → 静态前缀变化）。但 mode 切换是**低频事件**（用户手动操作 / 工具触发，非每轮发生），击穿一次的代价远小于"8 轮安全约束盲区"的代价。这是"更安全 vs 更省 cache"的取舍，本次为更安全让路，符合北极星"更安全"方向的优先级。

> **失效原因**：这个取舍的两端都被高估了。左端"8 轮安全盲区"不是真隐患（见上）；右端"击穿一次"也低估了——`Shift+Tab` 循环切模式时用户往往连按数次，每次都是全量 system prefix 重算（本项目 system prompt 实测 37805 字符）。CC 的数据是这类"description/prefix 随状态变化"占了 10.2% 的 cache_creation。既然左端收益不存在，这个取舍不成立。

**关键技术前提（原文保留，前提本身成立但结论不成立）**：

- `generateCacheKey`（`system-prompt.ts:265`）已把 `permissionMode` 纳入缓存键，所以只要调用方在 mode 切换时传入新 mode 值调 `buildSystemPrompt`，就会 cache miss → 重建。前提成立。
- 当前缺的是**触发点**：`cyclePermissionMode`（`app.ts:3991`）、`activatePlanMode`（`app.ts:3800`，注释明说"不重建保 cache"）、`deactivatePlanMode`（`app.ts:3810`）、`tool-executor.ts:598` 的 contextModifier 改了 `config.permissionMode` 但都不调 `rebuildSystemPrompt`。这正是 `permission-reminder.ts` 当初引入的原始动机（缺口 C：5 分钟缓存冻结，mode 切换不刷新）——移除 reminder 通道的同时必须补上这个触发点，否则 mode 切换后 system prompt 里的权限文案仍是旧值，制造新的"已切换但模型上下文里是旧约束"隐患。

**缺口 1 — plan mode 有独立的 reminder 通道，不受废弃 `permission-reminder.ts` 影响（完整性）**

### ⚠️ 7.1.1 补充发现（2026-07-30 二次核查）：plan mode 是**同一 bug 的第三个实例**，原文档全程未识别

原文档"缺口 1"断言 *"plan mode 走独立通道 `getPlanModeReminder`，不受影响"* —— 这个断言**不完整**。运行时验证：

```
buildSystemPrompt({tools: [], permissionMode: "plan"})
  含『计划模式已激活』? true
  含『绝对不能』?     true
  含 exit_plan_mode ? true
```

`grep -rn "计划模式已激活" src/` 只有两处命中：`attachments.ts:153`（`PERMISSION_MODE_DESCRIPTIONS.plan`）和 `plan/prompt.ts:18`（`buildPlanModePrompt`，走 `enter_plan_mode` 的 tool_result）。**`system-prompt.ts` 里没有任何独立的 plan prompt 路径** —— plan 的约束文案进 system prompt 的**唯一通道，就是我们要删的那个附件**（`PERMISSION_MODE_DESCRIPTIONS` 的 `plan` 键）。

所以 plan mode 实际有**三条**通道，且是同一个双通道 bug 的第三个实例：

| # | 通道 | 内容 | 时机 |
|---|------|------|------|
| 1 | `PERMISSION_MODE_DESCRIPTIONS.plan` → system 附件 | 「计划模式已激活 / **绝对不能** / 允许-禁止操作清单」 | 每次 `buildSystemPrompt`（**要删的**） |
| 2 | `buildPlanModeReminder` → user reminder | 简短版，full/sparse 分档节流 | 每轮（`loop.ts:734-738`） |
| 3 | `buildPlanModePrompt` → `enter_plan_mode` 的 tool_result | 完整工作流（阶段 1-5 + 决策记录指引） | 仅进入 plan 那一次（`tool/enter-plan-mode.ts:99`） |

文案重叠实测（`buildPlanModeReminder` vs 附件）：

| 关键短语 | 附件（通道1） | reminder full | reminder sparse |
|---------|-------------|--------------|----------------|
| 计划模式已激活 | ✅ | ❌ | ❌ |
| 绝对不能 | ✅ | ❌ | ❌ |
| exit_plan_mode | ✅ | ✅ | ✅ |

**结论：通道 1 与通道 2 语义重叠但措辞不同**（附件是"绝对不能编辑 + 完整允许/禁止清单"，reminder 是"不要进行任何编辑 + 催促尽快提交"）。这既是重复注入（同一约束两处说），也是**措辞不一致**（两份文案独立演进，已经漂移）。

**这对 §7.1 的影响 —— 删附件是安全的，但必须补一步**：

- plan 的**代码强制**在 `PermissionChecker` + plan 状态机（`attachments.ts:153` 自己写着"由权限层代码级强制"），删文案不改变实际约束能力。
- 但 plan 与其它 mode **性质不同**（§6.5.3）：plan 是**行为模式**（"先规划再执行"无法用权限规则表达，必须靠模型自觉），CC 也正是**只**对 plan 做每轮注入。所以 plan 的文案不能简单删掉了事。
- **落地动作修正**：删附件时，需把通道 1 里 reminder 缺失的关键语义（「此约束覆盖你收到的所有其他指令」这句最强的越权防线，以及"允许 read/grep/glob、禁止 bash/写操作"的明确清单）**并入 `buildPlanModeReminder` 的 full 档**。full 档本就是低频（每 N 轮一次），承载这段成本可接受；sparse 档保持精简不变。
- 同时**消除措辞漂移**：并入后 plan 约束文案只剩一处事实源（`plan/prompt.ts`），`PERMISSION_MODE_DESCRIPTIONS.plan` 这个键可以一并删除（它在删附件后也变成无调用方 —— `permission-reminder.ts` 的调用方已被 `loop.ts:694` 的 `mode !== "plan"` 排除，永远取不到 `plan` 键）。

> 这条是本次二次核查的**最重要补充**：原文档把 plan 当作"不受影响的独立通道"排除在视野外，实际它是同一 bug 的第三个实例，且是三个 mode 里**唯一真正需要文案注入**的那个。漏掉它会导致删附件后 plan 的最强约束句（"覆盖所有其他指令"）静默消失 —— 这才是真正的安全回归。

## 7.2 【最终方案】P1 — deferred-tools 改增量 delta 通道（对标 CC `deferred_tools_delta`）

**取原 §7 的方案 A 的方向 + CC 的粒度**：留在 user reminder 通道，但从"每轮全量"改为"仅增量"。

### 动作

1. **新建 `src/tool/deferred-tools-delta.ts`**（纯函数，对标 `mcp/instructions-delta.ts` 的形态）：
   ```ts
   export function getDeferredToolsDelta(
     currentDeferred: string[],
     announced: Set<string>,
   ): { addedNames: string[]; removedNames: string[] } | null {
     const cur = new Set(currentDeferred);
     const added = currentDeferred.filter((n) => !announced.has(n));
     // 已播报过、但现在不在延迟池里 → 分两种：
     //   ① 被 tool_search 激活了（已可直接调用）→ 不报 removed，否则等于告诉模型"没了"（CC 明确注释此坑）
     //   ② server 断连、整个工具消失 → 报 removed
     const removed = [...announced].filter((n) => !cur.has(n) && !stillInPool(n));
     if (added.length === 0 && removed.length === 0) return null;
     return { addedNames: added, removedNames: removed };
   }
   ```
   `stillInPool` 已有现成原语，不需要新增 registry 方法——`toolRegistry.get(name) !== undefined`（`registry.ts:196`）即"该工具仍在池中"。调用方按 `(name) => toolRegistry.get(name) !== undefined` 注入即可，delta 模块本身保持纯函数（不依赖 registry，便于单测）。

   > `stillInPool` 的必要性直接来自 CC 的注释（`toolSearch.ts:640-644`）：
   > *"A name that was announced but has since stopped being deferred — yet is still in the base pool — is NOT reported as removed. It's now loaded directly, so telling the model 'no longer available' would be wrong."*
   > 我们的 `registry.activateTool()`（`registry.ts:420`）正是这个场景：激活后 `isToolDeferred` 转 false，若不加这个判据，**每次 tool_search 成功都会误报一条"该工具已不可用"**，与刚返回的 schema 直接矛盾。

2. **`loop.ts:1065-1078` 改为走 delta**：
   ```ts
   if (toolSearchEnabled && deps.getDeferredToolsDelta) {
     const delta = deps.getDeferredToolsDelta(toolRegistry.deferredToolNames());
     if (delta) {
       finalMessages = injectReminders(finalMessages, [renderDeferredDelta(delta)]);
     }
   }
   ```
   首轮 `announced` 为空 → 全量作为 `added` 发一次（与 CC `isInitial` 语义一致）；后续 MCP 迟到连接只发新增的那几个。

3. **`announced` 去重集挂在 `App` 上**，完全复用 `announcedMcpServers` 的现成模式（`app.ts:372` 定义、`:867` 累加、`:1735` / `:6186` 在 `/clear` 时清空）——三处都要同步加 `announcedDeferredTools`。

### 收益量化（按活体复现的第 4 轮数据）

| | 现状 | 改后 |
|---|------|------|
| 首轮 | 100+ 工具名 | 100+ 工具名（首轮不可避免，模型必须知道有什么） |
| 第 2 轮起（工具集不变） | 100+ 工具名 | **0** |
| MCP server 迟到连接 | 100+ 工具名 | 仅新增的 N 个 |
| tool_search 激活一个工具后 | 100+ 工具名 | **0**（且不误报 removed） |

按 8 轮对话、每个工具名约 8 token 估算：现状 ≈ 6400 token，改后 ≈ 800 token，**降幅约 87%**。这是本次三个修复里唯一有明确 token 收益的一项，直接命中北极星"更省"。

### 已知局限（明确记录）

**去重状态放内存 Set，compact 后会丢失 → 触发一次全量重播。** CC 的做法更强——它扫历史消息里的 `deferred_tools_delta` 附件重建 `announced`（`toolSearch.ts:657-663`），天然与上下文同生命周期。

我们暂不做"扫历史"，因为本项目的 reminder 是**拼进 user 消息文本**的，没有 CC 那种带类型的结构化 attachment 可扫。评估：

- compact 是低频事件，且 compact 后模型上下文确实丢了工具列表，**重播一次是正确行为**，不是 bug。
- 若将来要做到 CC 那个强度，正确路径是先引入结构化 attachment 层（本项目缺这一层，是与 CC 最大的架构差距），而不是给 delta 打补丁。**这条应单独立项，不塞进本次修复。**

## 7.3 【最终方案】P2 — 修正 §三 归因 + 落一条防回归约束

### 7.3.1 修正归因

§三核查结论（`:310`）关于"harness 回显机制"的解释是错的，代码里无此机制。真实原因是 `openai.ts:277-291` 把 system 动态区搬回 user 消息。§6.5.5 已记录，无需再改代码，但**这条认知必须固化**——否则下次又会有人基于"放动态区就不占 user turn"设计方案。

### 7.3.2 建议补一条守卫（可选，但推荐）

`system-prompt.ts` 里加一条注释级不变量 + 一个单测：

```
// 多 provider 不变量：DYNAMIC_BOUNDARY 之后的内容在 OpenAI 族会被
// openai.ts prependSystemMessage 搬到 messages 末尾、以 role:"user" 落地。
// 因此「放动态区」≠「不占 user turn」。任何以此为前提的优化在本项目不成立。
// 要真正减少 user turn 占用，只有两条路：① 不注入；② 走增量 delta 只发变化量。
```

配一个单测断言：动态区非空时，OpenAI provider 的 `convertMessages` 输出里必然多一条 user 消息。这把一个反复踩的隐性前提变成显式约束。

### 7.3.3 CLAUDE.md 全文每轮重发 —— 本次不修，但要记账

§6.5.4 的实测显示 CLAUDE.md 全文落在**动态区**（因为 `generateClaudeMdAttachment:182` 没标 `cacheStability`）。这意味着：

- Anthropic 族：CLAUDE.md 在动态 cache block，会话内可缓存，代价可接受。
- OpenAI 族：**CLAUDE.md 全文每轮以 user 消息重发**，且因为它在 `messages` 末尾变化位置，会持续影响前缀缓存。

本项目 CLAUDE.md 很长（项目级 + 全局级），这可能是"更省"方向上最大的一块。**但这是独立问题（附件缓存分区标记缺失），不属于"重复注入"bug，不在本次修复范围。** 建议单独立项：给 `generateClaudeMdAttachment` / `generateSkillListingAttachment` / `generateDenyRulesAttachment` 补 `stableAttachment` 标记（它们内容跨请求稳定，本就该进静态区），只留 date / git-status / mcpToolGuide 在动态区。

> 注意：这个改动**不能顺手做进本次修复**——把 CLAUDE.md 移入静态区会改变 cache 分区边界，需要独立验证 `cache_read` / `cache_creation` 指标不劣化（本项目有 `bun scripts/trace-digest.ts` 可度量）。混在一起改会让两边的效果都测不准。

## 八、与上一份文档的关系

本文档排查的是"重复注入"（同一内容多通道/多轮重复注入到上下文）。
上一份文档（`上下文注入淹没用户指令-reminder前置拼接根因与修复方案.md`）排查的是"排列顺序"（reminder 前置淹没真实用户指令）。

两者是同一现象的两面：
- **重复注入**（本文档）：同一内容注入多次 → 浪费 token + 信息冗余
- **排列顺序**（上一份）：注入内容前置 → 淹没真实用户指令 → 弱模型跑偏

修复时两者要一起考虑（以 2026-07-30 修订后的方案为准）：
- P0（上一份）：`reminder-inject.ts:47` 拼接顺序反过来（用户指令在前）— **CC 印证此方向**（`processTextPrompt.ts:84` `[userMessage, ...attachmentMessages]`）
- P0（本文档 §7.1）：权限模式去双通道，**删 system 附件、保留 reminder**
- P1（本文档 §7.2）：deferred-tools 改**增量 delta**（不是搬去 system 动态区）

三个修复叠加，才能既不重复注入、又不淹没用户指令。三者都收敛到同一条架构原则：**运行时易变的上下文走 user 侧增量通道（按需、增量、后置），system prompt 只留配置态稳定内容。** 这与 CC 的架构方向一致，且在多 provider 下是唯一真正省 token 的路径（§6.5.4）。
